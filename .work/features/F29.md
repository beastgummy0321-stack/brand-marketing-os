# Outcome
The learning loop closes on real data. The last ended period is settled in one batch: every ad with enough sample is graded against its own campaign's cap, 划算 is written to the brand notebook as effective and 太貴／沒賣出 as ineffective, imported campaigns included, with the angle confirmed on one page. An automatically paired A/B comparison that reaches its thresholds proposes pausing the loser through the normal approval flow and writes the result. Every judgement uses one ruler (the cap grade); a rejected cleanup comes back only when the grade gets worse. Screens never show a failed read as empty, every section of a campaign reads one "has data / why not" state, and background work shows its queue position. Cleanup ads can be unticked, an ad row can raise a "replace this ad" material request, the period and the month review download as CSV, a daily digest lands in the in-app inbox, and launch settings become choice fields that readback compares with a Meta read. The screens listed below match `docs/design/ads/prototype-v10-ads-center.html`.

## Contracts (every issue uses exactly these names; paths are under `/api/ads` unless absolute)
- **A. Grades and one ruler (I01).** `grade` keys are unchanged; `grade_label` becomes 划算／偏貴／太貴／**沒賣出**／**剛開始、數字還不夠** (below the sample gate)／資料不足／未判斷. Triage items gain `previous_grade: grade|null` (the previous equal-length window graded by the same rules; null when not covered, below the gate or unknown) and `grade_move: {from, to}|null` (both graded, different). A `worse` row is raised only when `grade_move.from == "on_target"` and `to` is `watch` or `over`. `class`／`change_pct`／`previous` stay as the trend note and no decision reads `class`. One grading function serves triage and `app/ads/period_grades.py::grade_period(conn, org_id, brand_id, start, end)` → rows `{campaign_id, campaign_name, origin, entity_id, name, group_name|null, thumbnail_url|null, spend|null, results|null, cost_per_result|null, cap|null, break_even|null, grade, grade_label}` for every ad with spend in the window (active or closed), same sample gate as §6.17/§6.32.
- **B. Rejected cleanup memory (I01).** `ads_change_set.decision_grades jsonb NULL` = `{"<entity_id>": {"grade", "cost_per_result"|null, "cap"|null}}`, written by `decide(... "rejected")` for every pause item of a `source: "cleanup"` set, and by `approve` for the set's `plan_json.declined_ids` (the proposal ads the user unticked). `POST …/campaigns/{c}/changes` accepts `declined_ids: string[]` only with `source: "cleanup"`. The newest memory per ad wins; an ad in memory re-enters a cleanup only when its current grade ranks worse (on_target < watch < over < wasted), and then carries `rejected_before: {grade, grade_label, at, reason|null, change_set_id}` in `cleanup.ads[]` (null otherwise). `decision_grades` null = no memory.

Month summary (I01).** `GET …/month-summary?month=` gains `grades: {spent|null, buckets: [{grade, amount, count, ads: [{entity_id, name, thumbnail_url, spend}]}], rows: [grade_period row], missing: [{campaign_id, name, missing_days}]}` from `grade_period`; 有效 = `on_target` only. It gains `rejected: {worse: [{change_set_id, campaign_id, campaign_name, title, at, reason|null, ads: [{entity_id, name, thumbnail_url, was, now}]}], same_count: int}`. ## Agent choices (reversible; not asked)
- Settle and the month review share `grade_period`, so step 1 of the settle equals the month review of that month. Only the latest ended month is offered. A learning's text carries no numbers (so identical conclusions promote confidence, F27 Contract D): ineffective reuses `「<angle>」對這群受眾無效`, effective is `「<angle>」對這群受眾有效`; the screen shows the cost beside it. A failed angle read falls back to 自訂 only (F27 precedent). This also restores the 沒賣出 learning F28 lost through cleanup.
- The 還太新 glossary sentence states the ruled gate (spend ≥ 3 × cap, or ≥ 10 results over ≥ 7 days), not the prototype's "3 筆".
- CSV is built in the browser from the numbers the screen already shows (no endpoint).
- The month review is rebuilt fully to v10 because the rulings change most of its content. The publish flow gets only its three v10 settings blocks (list, platform, verify) mounted in the current publish page; the full publish rebuild stays in the next UI batch. The assets-tab 素材需求 card of v10 waits for the assets screen batch; the request shows on the detail row and in the existing material panel.
- The new-campaign `#/new/2` wait state is not built: brief parsing is synchronous, not a queued job.
- The confirmed-plan comparison (`…/comparison`, legacy workspace performance tab) stays as it is apart from the removed gate; auto pairs reuse its judge core.
- Queue positions count every tenant's jobs (one shared worker), but other tenants appear only as a number.
- Home decision order: cleanup, worse, settle, refresh_creative (prototype order); the settle card spans the row.

## Unresolved (proposed defaults apply unless the user overrides before dispatch)
1. **What "上一期" is — RULED by the user 2026-09-25: the calendar month.** The ruling cites `schedule/period.py:405`, but `campaign_period` has no caller in today's UI (`settleSchedulePeriod` is unused), so a period-based to-do would never appear. Default: the calendar month (same window as the month review and the monthly budget), owned by `app/ads`; `schedule/period.py` is not changed.
2. **Unticked cleanup ads.** Default: an unticked ad is remembered like a rejection at its grade at approval and returns only when worse; otherwise tomorrow's cleanup re-proposes it.
3. **A/B window and stop rule.** Default: pairs are judged without an explicit plan confirmation, on the window from the later ad's first delivery day to the last complete day; the old "group hit its daily budget → don't judge" stop is dropped for auto pairs, because real delivery spends the full daily budget every day and the pair would never be judged. The 7-day / 10-each / 10% thresholds stay. Imported campaigns have no pairs (no coordinates).
4. **Where the preselected launch values come from.** Default: program rules, no model call: event from the result kind, lowest cost, automatic placement, 18–65+, all genders, the brand's country (TW when unknown), and the pixel when the account has exactly one. Location choices are countries only.
5. **The free-text launch fields v10 does not show** (landing URL, attribution, audience source/window/exclusions/ID). Default: they stay per ad set in the list's folded 進階設定; landing URL and the retarget audience ID keep their required rule, the rest become optional.
6. **One-click "換掉這一則".** Default: mode `workbench_image`, title 「換掉：<ad name>」; it can be cancelled until an approved change set uses it.
