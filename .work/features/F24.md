# Outcome
The last v7 ads-centre screens: the home campaign card's two abnormal states (「暫時讀取不到」 with a real 重新讀取, 「資料不足，先不判斷」 → the wait page `waitPage()`), the shell header 「最近同步 M/D HH:MM・N 項待處理」 chip, and the 每月回顧 page `month()` — all on existing data (`triage`, `campaigns`, `monthly-budget`, `orders`, `sync`) plus one read-only enrichment of the triage/campaign payloads. Nothing writes to a platform.
# Decisions
- User-confirmed 2026-09-22 (option A for batch C, option A for batch D): abnormal states come from EXISTING facts only — sync-job status per account, sync coverage vs the judgement window, all-ads-insufficient; the 「Meta 權限失效」 row is drawn only from the real `connections[].state === "disconnected"` fact; the 「系統剛恢復」 banner is NOT built (no reliable signal). Monthly review reads existing APIs only, no aggregation endpoint; multi-currency never summed (「多幣別，不合計」). User goal: every prototype screen of the ads centre lands this conversation.
- I01 (read-only payload additions, no migration): `triage.classify()` and `GET .../triage` gain `data: {sync: {state: "ok"|"syncing"|"failed"|"disconnected"|"never", error: string|null, last_success_at: string|null}, coverage: {start, end} | null, missing_days: string[]}`; `GET .../campaigns` cards gain the same `data.sync` object. Rules: `state = "never"` when the campaign has no `context_json.external_sync`; `"disconnected"` when any of the campaign's (platform, source_account) pairs is not in the platform reader's bound accounts (same check as `external_repository.external_view` → `connections[].state`); else `"failed"` when any section has `status in {"error","partial"}` (those are the values `record_sync` writes — `external_sync.py:446,552`; there is no "failed"); else `"syncing"` when any section is `"syncing"`; else `"ok"`. `error` = the first failing section's `error` (may be null — the state, not the message, drives the UI); `last_success_at` = the newest section `last_success_at` — note a failed sync keeps the OLD value (`external_repository.py:176-178`), so consumers must not read it as "recent". `coverage` = `_coverage(campaign)` as ISO strings; `missing_days` = the days of the campaign's judgement window (`window_days` back from the account cutoff — the same window `classify()` uses) that fall outside `[coverage.start, coverage.end]`, at most 31, empty when coverage is null (then the card says 「尚未同步」 rather than listing days).
- Home card state (I02, `home/CampaignCard.tsx`, prototype `ccard`): `sync.state === "failed"` → grey card 「暫時讀取不到」, chip 「已保存的紀錄都還在」, button 「重新讀取」 = the existing `syncCampaign` helper with its default body `{}` (default 30-day range covers the 28-day window; a browser-local `end` can be refused as "in the future" by the org clock), then poll `GET .../sync-jobs/:id` until `status ∉ {pending, running}` and reload the card; `"syncing"` → the same grey card with chip 「讀取中」 and the button disabled; `"disconnected"` → same grey card but chip 「廣告帳戶未連接」 and button 「去連接」 → `/brands/:brandId/ads/connections`; `"never"` → today's card (no state). Otherwise 「資料不足，先不判斷」 (warn) when the campaign has ≥ 1 classified ad and every one is `insufficient`, OR `missing_days.length > 0` — chip = 「缺 N 天資料」 when days are missing; else 「尚未同步成效」 when `coverage === null`; else by the dominant `reason_code` of the insufficient ads: `below_sample_gate` → 「樣本還不夠」, `no_previous_window` → 「缺前一期可比資料」, `result_unknown_days` → 「成果數未知」; button 「去處理」 → wait page. Campaigns with `no_target` only keep the existing 「設定目標」 card. Triage request failure keeps today's error state.
- Wait page (I03, route `/brands/:brandId/ads/campaigns/:campaignId/wait`): hero warn 「資料不足，這個活動先不判斷」 + campaign name, chip 「平台照常投放，不受影響」; rows only for facts that exist: disconnected → 「廣告帳戶未連接」／「重新連接後會自動補資料」／「去連接」 → connections page; `missing_days` → 「缺 M/D、M/D（N 天）」／「同步恢復後自動補」／chip 「自動」; orders latest date (F21 rule: first non-null `order_date` on page 1) before `coverage.end` → 「商城報表只到 M/D」／「補到 M/D 才能對照訂單」／「補報表」 → `/brands/:brandId/orders`; all-insufficient with no missing days → one row per distinct `reason_code` present: `below_sample_gate` 「樣本還不夠」／「每則廣告的花費或成果數還沒過門檻，累積中」; `no_previous_window` 「缺前一期可比資料」／「預設只同步 30 天，28 天窗沒有前一期可比；手動同步更早的區間才能補」／「重新檢查」 does not fix this; `result_unknown_days` 「成果數未知」／「平台沒回報這幾天的成果」; all chip 「自動」. 「最近 7 天」 card = `DayTiles` over the 7 days ending at `coverage.end ?? today`, `missing` = `missing_days`; subtitle 「之前的紀錄仍可查看」 → the workspace. Bar: back 「投放中心」, primary 「重新檢查」 = the same `syncCampaign({})` + poll (until `status ∉ {pending, running}`) + reload (disabled while a job is pending or running; `never` shows 「尚未同步」 and the button still works).
- Header chip (I02, `AdsHomePage.tsx` header area — not the shell; the shell is outside this feature): 「最近同步 M/D HH:MM」 = the newest `data.sync.last_success_at` among campaigns whose `state === "ok"` only (a failed sync keeps its old timestamp), browser-local time; none → 「尚未同步」. When any campaign is failed/disconnected the chip is warn and appends 「・N 個活動讀取異常」. 「N 項待處理」 = the home's open-item count — warn when N > 0, neutral when 0; the whole thing links to `/brands/:brandId/ads/connections`.
- Monthly review (I04, route `/brands/:brandId/ads/month`, prototype `month()`): title 「M 月回顧」; the month segmented control offers this month and last month, driving ONLY the budget card (`getMonthlyBudget(month)`); the other sections are labelled with their real windows. Cards: 全品牌花費 = `known_spend` of `amount` (meter); `amount === null` → 「月總額 尚未設定」, hatched meter; `known_spend === null` (budget `issues` with no spend evidence, `month_budget.py:214`) → 「花費未核實」 + `uncertainties[0]`, no meter; 商城訂單 = `orders.summary.net_revenue` labelled with the response's own window when it returns `since`/`until`, else 「近 31 天實收」 (the stats window is `until - 30 … until` inclusive, machine date, `orders/repository.py:319-321`), no previous-month comparison (not available) — card omitted when the request fails. 各活動 rows = the home's campaign cards (non-closed): name → detail page, 花費 = the sum of the campaign's triage items' `current.spend` ONLY when every item shares the same `window.days` (label 「近 N 天」); items with different windows → 「各廣告期間不同，未合計」; no currency is attached (triage carries none) — plain numbers, as the home does; meter = cost_per_result vs target with chip 達標／未達標 (cost ≤ target → 達標) or 未判斷 when either is null / no target. 素材 = three tiles groups by triage class: 有效 = `better`, 無效・已停 = `stop_loss`, 還看不出 = flat + insufficient; thumbnails from `thumbnail_url` (null → neutral tile). 記入品牌學習 and 「✦ 下月建議」 = grey `ReservedSlotCard`s (no brand-level learnings GET; no suggestion backend). Bar: back 「投放中心」. Home 「每月回顧」 button → this route.
- Lead work before dispatch: `DayTiles` added to `patterns/ReviewPieces.tsx` and mapped in `ui-evidence.cjs`; references in `.harness/scratch/F24/ref/` (wait via `--hash wait/mid`, month, home).
- Constraints: as F22/F23; typecheck = `npm run build` (`npx tsc --noEmit -p .` is a no-op in this repo); ports 8731＋issue; docs before `integrate`.
- Pre-dispatch challenge 2026-09-22 (160 s, read-only): eight corrections folded in above (sync status vocabulary error/partial/syncing; per-ad windows not summed blindly; syncCampaign default body + poll until not pending/running; insufficient reasons by reason_code; coverage null chip; header chip ignores failed timestamps; known_spend null; orders 31-day window). Sound: disconnected is a DB read; never = no external_sync; zero-ad campaigns are not 資料不足; missing_days matches `_window_covered`; last-month budget view; net_revenue semantics; thumbnails.
# Acceptance
- A campaign whose sync failed shows the grey card and 重新讀取 really starts a sync; a campaign with missing coverage days shows the warn card and the wait page lists the missing days and the orders gap; the header chip shows the newest sync time and the open count; the monthly review renders every section from real responses, honest labels for windows and gaps.
