# Outcome
The eighteen P1 bugs on the 2026-09-26 priority board are gone at their causes: the wizard keeps what the user entered and chose, every background-job status tells the truth (queued, failed before the AI call, failed after it), Meta connection errors say what to fix, image selection holds one creative per ad and the learning reads the creative and coordinates that actually ran, the brand-home 判讀 remembers adoptions, a zero-order day is not "missing", deleting a brand works and leaves nothing behind, user-facing text carries no internal notes, the test suite is stable under `-n 4`, and long names fit at 1024.

# Decisions
**User rulings** (2026-09-26, `docs/backlog/handoff-after-f30.md` Priority board):
- Order: bugs and the ad closed loop first; items 1–18 are one feature batch.
- Item 6: ad coordinates stay editable after dispatch; learning reads the coordinates snapshot taken at dispatch.
- Item 9: keep the brand-home 判讀 (cockpit diagnosis) and fix its three bugs; retiring it is a later discussion.
- Standing: nothing writes to a platform; no issue, doc or report asks the user to run real ads.

**Agent choices** (reversible; not asked):
- Item 1: the offerings step's two choices (賣什麼, 廣告帶來的是什麼) are persisted on the draft, because `close_rate` cannot tell 先詢問 from 留資料 and misreads a product sold by inquiry as a service. Sell-ways show in creation order where "first 賣法" matters (offerings, `budget._economics_for`); `list_products` keeps name order (brief truncation and wizard options depend on it).
- Item 2: the start step's text fields are kept in browser storage per user and brand (or "new"), restored with one line 「幫你留著上次填的」, cleared on successful submit. Photos are not restored (server-side temporary tokens).
- Items 3, 14, 15: one status rule (Contract J), not per-endpoint patches. Item 3's table-format failure gets one automatic re-ask inside the same job; a second failure keeps today's 「格式要你看一下」 path.
- Item 5: the Meta parent-id guard also refuses ids another org bound in the ads center, through a check the ads module registers into `app/meta` (meta may not import ads, `LAYER_ORDER`).
- Item 7: for ads-dispatched image sets, image selections are capped at the set's required count; a selection beyond it is refused, not swapped. Copy multi-select and free jobs are unchanged.
- Item 8: a version with failed checks (❌) can still be selected after an explicit confirm, same pattern as `claim_warning`; the server does not block. A prose-drift check stays out of scope.
- Item 10: orders coverage ends at the later of the latest order date and the day before the latest import (org timezone), mirroring the spend rule "a read proves a day once the day was over when the read finished". Risk: importing an old export last would mark later empty days ok.
- Item 11: the ads-center bind endpoint has no frontend caller and launch readback (F30-I12) replaced it, so the dead path is deleted (route, client, adapter `bind` verb) instead of fixing its message.
- Item 12: a newly matched campaign gets a muted static line under the cockpit campaign table (no new data).
- Item 13: `llm_task` and `audit_log` stay on brand delete on purpose, listed with reasons in the coverage test's exemption list; the four dead tables are dropped.
- Item 18: bug fixes to existing kit pieces; no new prototype.
- Docs: issues do not edit docs; the lead's crank closeout writes the item 6 and item 9 rulings and the Contract J rule into their domain pages and deletes the absorbed backlog files.

## Contracts (every issue uses exactly these names)
- **J. Job status (F31-I02).** `app.background.job_outcome(lock) -> "active" | "failed" | "succeeded" | None` reads the newest procrastinate job carrying that `queueing_lock` (None: no job ever, and always in memory-queue mode). Every status reader in `app/intake` and `app/brand_web` (intake scan／question／paste_fix／research, persona generation, product scan, brand report) decides, first match: outcome `active` → running (even when an older `llm_task` row exists); outcome `failed` → failed, with the `llm_task` error when that job wrote a row, else 「背景工作沒有完成：背景程式可能沒有接到這個工作，請再試一次；一直這樣請確認背景程式有在跑。」; otherwise today's `llm_task`-row rule. A handler whose post-processing (apply, save) fails after a successful AI call sends its failure notice and then re-raises, so the job ends `failed`. Response shapes do not change.
- **K. Diagnosis adopted flag (F31-I06).** Each suggestion in `GET /api/schedule/brands/{b}/diagnosis` (and the POST response) gains `adopted: boolean`, computed by the same key function `_run_diagnosis_adopt` dedupes on (`rule_type` + `adopt_content`). Frontend `DiagnosisSuggestion.adopted: boolean`.
- **L. Selection cap and failed checks (F31-I04).** `POST …/sets/{s}/versions/{v}/select` on an `image_prompt` version of a set whose `source_ref` has `ads_ad_id`, when that part already has as many selected versions as the set requires → 409 `selection_full` 「這一則只能選 {n} 張，先取消目前選的那張再選。」. Each version in the set payload gains `validation_warning: {lines: string[]} | null` (its ❌ lines; null when none).
- **M. Offerings choice (F31-I01).** `GET /api/intake/brands/{b}/offerings` gains `choice: {sell_type: "product"|"service"|"both", ad_delivery: "direct"|"ask"|"lead"} | null`; the save body accepts `choice` and stores it in `intake_draft.offerings_choice_json` (migration `20260927000001_intake_offerings_choice.sql`, nullable jsonb). A successful save advances the draft to step 4. A draft without `choice` falls back to today's inference.
- **N. Meta reads (F31-I03).** `GET /api/meta/brands/{b}/spend` gains `data_pulled_at: string|null` (newest `pulled_at` of the rows it sums; null only with no rows) and `attribution_label: string|null` (Chinese label of those rows' attribution window, one mapping in `app/meta`); `last_pull_at` is unchanged. `POST /api/meta/token`: a Graph rejection never shows Graph's own text; code 100 (and any permission error on `me/adaccounts`) → 400 `meta_token_missing_scope` 「這把權杖看不到廣告帳戶，通常是產生權杖時沒有勾 ads_read 權限。請重新產生一把有勾 ads_read 的權杖再貼上。」; other codes → `meta_token_rejected` 「Meta 拒絕了這個權杖（代碼 N）。請確認權杖沒有過期、是從正確的帳號產生的。」.
- **O. What ran (F31-I05).** One ads function returns, per `ads_ad`, the workbench outputs frozen in its latest approved launch version (`copy` / `image_prompt` output ids and the set they came from), or None before any approved launch. Learning coordinates of an ad = the `coordinates_snapshot_json` of that set, normalised to keys; an ad with no dispatched set uses its current coordinates. Every ads learning reader (visual learning, experiments, A/B pairs, learning scope) reads these two, never `adopted_output` or the ad's current `*_key` after launch. If the approved launch snapshot does not carry output ids per ad, one nullable column is added by `20260927000006_ads_live_creative.sql`, written at launch approval.

## Constraints (all issues)
- Every issue adds at least one regression test that fails on `master` before its fix; worker reports name it.
- Gate commands as `uv run python -m <tool>`; frontend typecheck = `cd frontend && npm run build` (`tsc --noEmit` is a no-op here). Worker logs go to `%TEMP%/claude/`, never the worktree. Worktrees have no `.env`. Kill processes by PID or port only.
- New backend tests match their module's `owns` pattern (`test_ads*`, `test_workbench*`, `test_schedule*`, `test_intake*`); a test file that matches no module imports only public or legacy facades.
- A shared frontend type that gains a required field makes its issue edit every test factory that builds it (grep the type name across `frontend/src/**/*.test.tsx`).
- Legacy files are touched only to fix the bug at hand or add a facade function; no new capability grows there.
- Migrations: fixed file names in the issues; `grep -rn "REFERENCES <table>" supabase/migrations/` before a drop; the lead applies each migration to the dev DB (54322) and registers it before merging that issue.
- New procrastinate task types are not expected; if one appears, the worker restarts its own worker process before its checks and says so.
