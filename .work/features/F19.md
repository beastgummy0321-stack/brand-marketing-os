# Outcome
The ads-centre home (`/brands/:brandId/ads`) is rebuilt to the approved v7 prototype: one brand-level decision queue (停損／變差) on the left, the month budget on the right, one card per campaign below with its own target and five-class triage strip, and a target-setting page the cards link to. It consumes the already-shipped `queue`, `triage`, `target` and `monthly-budget` APIs. Frontend first: no backend work except the one small queue-payload enrichment in I01.
# Decisions
- User-confirmed 2026-09-21: frontend before any further backend; plan of five issues approved, including the target page (option 1). Workers may use the installed design skills (`impeccable:*`, `frontend-design`).
- User-confirmed (`docs/design-system.md` §1.7): rebuild the information hierarchy from the reference, then wire data. Do not re-skin the old page; no explanatory paragraphs, tutorial text or stacked disclaimers. Text budget per screen: one title, one purpose line, labels.
- Reference: `docs/design/ads/prototype-v7-ads-center.html` — `home()` (≈ lines 193–218) and the target screen (≈ lines 326–345). Open it in a browser; do not copy its inline styles — use the kit, tokens and `components/ads/patterns`.
- Capabilities the backend does not have are shown as grey, non-clickable 「接上後開放」 placeholders (`ReservedSlotCard` style): pause proposal, 可加預算, 補素材, 每月回顧. Never fake them, never add backend for them.
- Not in this batch, do not build or fake: campaign detail page, data-connection page, six-step repair flow restyle, monthly review, the "系統暫停正在補資料" banner, the "資料不足，先不判斷" campaign-card state (no backend state exists for these two).
- Shared contract (frozen in I01, consumed by I02–I05): `frontend/src/lib/adsTriageApi.ts` exports `getQueue`, `refreshQueue`, `getTriage`, `getTarget`, `putTarget` and their types. Class enum `stop_loss | worse | better | flat | insufficient | no_target`; labels come from the backend `label` field — the frontend does not re-word them. Each listed queue item carries `triage` (its current triage item; rows whose ad moved off 停損／變差 stay filtered out by the backend, F18 behaviour unchanged).
- Plan amendment 2026-09-21 (found by I02 + I05): no Chinese label or option list for `result_kind` exists anywhere. F19-I06 adds it in `app/ads/result_kinds.py` and exposes `result_label` / `result_kinds`; I03 and I04 wait for it. The frontend never maps or prints a raw `result_kind`.
- Core stays platform-neutral: no platform name, brand or industry literal in the new components.
- Every UI issue ends with evidence: side-by-side screenshots (v7 screen vs built screen) at 1024 and 1920 plus the §1.7 five-question check, saved under `.harness/scratch/F19/<issue>/` and summarised in the worker report. Screenshots via `playwright-cli`; helper files go to `%TEMP%`, not the repo.
- Constraints: 800-line file cap; run npm only with `cd frontend &&`; gate commands use `uv run python -m <tool>`; merges are serial (e2e port 8720).
# Acceptance
- Home shows real queue items with a to-target meter, only the first open row has the primary button, campaign filter works, empty queue says 「都處理完了」.
- Each campaign card shows target cost + basis, the five-colour strip and legend from real triage counts; the no-target and read-failure states render as in v7.
- Target page reads and saves through `GET/PUT …/target` with `expected_revision`; `missing` reasons are shown as-is.
- loading / empty / error states exist for every new block; keyboard reachable; no horizontal overflow at 1024 and 1920.
- Human acceptance on real synced data, restarted backend.
