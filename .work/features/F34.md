# Outcome
A brand can declare which advertising regime applies to it (first value: 台灣食品). For such a brand, every place the user reads ad copy the program wrote or the user uploaded shows a soft reminder when the text contains wording the 食安法 §28 rules (衛福部認定準則 §4／§5, 健康食品管理法 §6) treat as medical efficacy, physiological-function or health-food claims. Nothing is blocked, nothing is re-asked, and no prompt gains a new constraint. Brands with no regime are untouched. The word table is program data with a source per row, like `app/ads/calendar_tw.py`.

# Decisions
**User rulings** (2026-09-27, dig of drill-6 gap #9):
- 1A: per-brand 「適用法規」 flag, set in the intake start step or the brand profile page; first value 台灣食品 only; brands without it are unaffected.
- 2B: user-uploaded copy is warned, never blocked.
- Extra: generated copy is also warn-only — no fix round, no ❌, no new prompt constraint (the user: more prompt limits make copy generic). The reminder is for the human reading the copy.

**Verified state** (at `3e16ba50`): no statutory list exists; `brand.industry` was dropped 2026-08-29; the existing 「健康類法規」 methodology switch (`compute_methodology_switches`) is inferred from a confirmed `brand_fact.fact_type='regulatory'`, not a user choice, and names no regime. The shared text check is `workbench.validate_claims` → `claims.unsupported` (warn-only, shown as `version.claim_warning` in `SetStudioPage.tsx`); ads reaches it from `asset_suggestion_policy.violations`. Launch approval reads copy through `handoff_assignment.material_snapshot` and is left alone (warn-only means it has nothing to refuse).

**Agent choices** (reversible):
- Column `brand.regulatory_regime TEXT NULL CHECK (IN ('food_tw'))`; NULL means 不適用／未設定 (one meaning; unlike `advertising_history` nothing needs to tell "unasked" apart). Writer is a small file mirroring `advertising_history.py`, with a `repository.py` facade for tests. Route mirrors the advertising-history PUT.
- The regulation defines categories, not a word list (§4: 與事實不符／無證據／維持或改變器官組織生理外觀功能／公文書字號、「健康」品名; §5: 預防改善減輕診斷治療疾病／降低致病體內成分／中藥材效能). The table therefore holds curated trigger patterns per category with the article as `basis`, plus 附件一's 27 「通常得使用之詞句」 verbatim as allowed phrases stripped before matching. 附件二 (nutrient-function phrases, allowed only when the nutrient is present and labelled) is not modelled this round.
- Substring／regex match, no semantics. Bare 改善／預防／減輕／緩解／舒緩 fire only within 6 characters before a symptom or disease word (`ponytail:` naive heuristic; the ceiling is a tokenizer nobody asked for).
- Three reminder surfaces: workbench version list (`statutory_warning` beside `claim_warning`, same one-click confirm), ads placement list (`statutory_warning` per placement, shown on the card), ads 補文案 result `notes`. `review_policy` recommendation copy is not checked here: it lands in placements before anyone acts on it.
- The wizard asks with an optional checkbox (unchecked = NULL); the profile page uses a select. Neither is persisted in the start step's kept-text draft.
- Merge order is sequential: I02's tests set the column I01 adds; I03 consumes I02's facade fields. The lead applies I01's migration to the shared dev DB (54322) before I01 merges (merge smoke hits that DB).

**Rejected routes**: deriving the regime from `fact_type='regulatory'` facts (LLM-extracted, regime-less, not the user's choice — ruling 1A); blocking or re-asking (rulings 2B + extra); fetching the regulation at runtime or asking the LLM for the list (same reason as the calendar, F33 2A); a brand-wide default of 台灣食品 (a coaching brand writing 改善體態 would be warned for a law that does not apply).

## Contracts (every issue uses exactly these names)
- **R. Regime flag (F34-I01 writes; I02／I03 read).** `brand.regulatory_regime` is `'food_tw'` or NULL. `app.brand_intelligence.repository.set_regulatory_regime(conn, brand_id, value: str | None, *, actor) -> dict` is the writer facade (NULL clears). `PUT /api/library/brands/{brand_id}/regulatory-regime` with `{"value": "food_tw" | null}` returns `{"data": {"regulatory_regime": ...}}`, 400 on any other value. `GET /api/library/brands/{brand_id}` `brand.regulatory_regime` carries it; `LibraryBrandProfile.regulatory_regime: "food_tw" | null`.
- **S. Statutory check (F34-I02 writes; I03 reads).** `workbench.validate_claims(conn, org_id, brand_id, product_id, value)` returns, in addition to today's keys, `statutory_hits: list[{"term": str, "tier": "medical" | "function" | "health_food", "basis": str}]` and `statutory_warning: {"terms": [{"term": str, "tier_label": str}], "sentence": str, "href": str} | None`. Both are `[]`／`None` when the brand's `regulatory_regime` is NULL. `tier_label` is the short label the prototype shows on the chip (醫療效能／改變生理功能／未取得許可不得使用); `sentence` is 「食品廣告通常不能這樣講（食安法第 28 條）。確認無誤仍可選定。」 (workbench) — the ads side replaces the last clause with 「確認無誤仍可確認安排。」; `href` is `https://law.moj.gov.tw/LawClass/LawAll.aspx?pcode=L0040140`. Workbench versions gain `statutory_warning` with the same shape next to `claim_warning`. For the 補文案 `notes` (plain strings) the note is 「食安法提醒：」 + the terms joined by 「、」 + the sentence.
- **UI spec = the prototype** (design-system §1.7): `.harness/scratch/prototype/f34-statutory/index.html`, one hash per screen — `#/start` 精靈起點, `#/profile` 品牌資料, `#/studio` 工作檯版本, `#/assets` 投放中心素材卡. The reminder piece is `.statute` (`data-slot="statute-note"`): warning tint block, 「食安法提醒」 label, one chip per term with its tier label, one sentence, link 「衛福部認定準則」; on the studio screen the existing confirm row (確認無誤，選定此版／返回查看) opens inside the block. The 「新增」 purple tags are prototype-only. Shots at 1024／1920 in `shots/`.

- Workbench version list, ads placement list and 補文案 notes carry the reminder for a `food_tw` brand; selecting／confirming still works.
