# Outcome

檔期規劃 becomes 投放中心: a Campaign is a real object that carries why it exists (`goal_text`),
what it is for (`objective`) and how it will be judged (`success_criterion`), and the whole loop
closes on rows instead of JSON blobs — strategy → delivery plan (Campaign → 通路 → 投放組 → 廣告)
→ one 任務包 into 素材工作檯 → publish through a channel adapter (manual or simulated) + bind →
daily outcome rows attributed by the bound entity → 結案 judges against the campaign's own success
criterion → one learning row in 品牌智庫 → the next campaign's strategy reads it. Five tabs exist at
minimal fidelity; the old four-stage page is gone, with no parallel run.

This is feature 1 of 3 (phasing A). Feature 2 = 投放中心首頁的工作佇列＋建議／採用／為什麼／更新鈕.
Feature 3 = 發布前檢查／批次操作／Inspector／完整 Campaign 清單／圖級細緻度. The prototype is the
shared visual reference for all three; anything it shows that belongs to feature 2 or 3 stays out.

## The two the planner decided (delegated by the user, 2026-09-12)

- **New managed module `ads`, not a reshape of `schedule`.** Reason and boundary: `ARCHITECTURE.md`
  §2, §4, §6.1. `schedule` keeps its package because 經營概況 still reads its 判讀 surfaces; what
  retires in F03 is its page, its route and its sidebar entry. No issue in F03 edits `app/schedule/`
  except to delete the frontend and its route.
- **`learning_ledger` is revived where it is** (brand_intelligence, legacy), with
  `record_learning` / `list_learnings` added to `app/brand_intelligence/repository.py` and `ads`
  calling those — `ARCHITECTURE.md` §3. An ads-owned `ads_learning` table was rejected: learning is
  brand knowledge shown in 品牌智庫. The other four dead tables are not touched in this feature.
- **The ledger API as shipped in F03-I02** (reviewed 2026-09-12), for its two readers:
  `record_learning(conn, brand_id, *, actor, learning_text, applicability_scope, confidence,
  sample_size, source_cycle_id=None, product_id=None, platform=None, needs_revalidation=False,
  learned_at=None) -> dict` (append-only, validates `confidence` and a non-empty sentence,
  `sample_size` is TEXT — pass the bucket as a string) and
  `list_learnings(conn, brand_id, *, product_id=None, include_expired=False, limit=50)`
  (newest `learned_at` first, `expired` hidden by default, `SELECT *` so `needs_revalidation`
  comes through). Two things the callers must not get wrong:
  - **F03-I05 calls `list_learnings(conn, brand_id)` with no `product_id`.** The `product_id`
    filter is an equality filter, so passing it drops every brand-level learning — which is most
    of them. Filter per offering in Python if the prompt ever needs it.
  - **F03-I12: `record_learning` commits on its own** (file convention). Close in the order
    `record_learning(...)` → one `UPDATE` that sets `verdict`, `verdict_json`, `status='closed'`,
    `closed_at` and the learning ids. The duplicate guard stays `status='closed'` on the campaign
    row; do not query the ledger for it (`ads` gets no ledger filter by `source_cycle_id`).

## The golden path this feature must close

brand → offering → goal (the brief) → strategy → delivery plan → pack → artifacts → publish
(manual or simulated) + bind → outcome → verdict against `success_criterion` → learning →
the next campaign's strategy reads the learning. Every issue's `# Objective` names which link it
serves, where its input comes from, where its output goes, what trace it leaves, and whether it is
core or pluggable (`ARCHITECTURE.md` §0).

## Shape decisions an issue must not re-invent

- **Tables** (`ads` owns all five, one migration file, `<timestamp>_ads_*.sql`): `ads_campaign`
  (goal/objective/success criterion/status/dates/budget), `ads_delivery_group` (channel key, role,
  daily budget, binding columns), `ads_ad` (coordinates, binding columns, readiness), `ads_action`
  (every platform-bound change), `ads_outcome_daily` (one row per bound entity per day).
  The 通路 level is a column on the group, not a table (§6.2).
- **Binding lives on the row**, not in a map table: `external_id` / `external_name` /
  `external_status` / `local_state` columns on `ads_campaign`, `ads_delivery_group` **and** `ads_ad`
  — all three levels, because Meta's lookups are hierarchical (`ad_set_ids_by_exact_name` needs the
  platform campaign id, `ad_ids_by_exact_name` needs the ad-set id), so the campaign node is bound
  first and the checklist is 逐節點 from the top. `channel_entity_map` belongs to `schedule` and is
  not read or written by `ads`.
- **One source of truth for money after 採用**: the group daily budgets are the truth.
  `ads_campaign.budget_planned` records the scenario amount the user adopted (for the record and for
  the 依據 caption) and is never recomputed; the total shown on screen is
  `sum(group.daily_budget) × days`, computed in one place. They may differ by less than a day's
  rounding — the screen says which is which, nothing silently overwrites the other.
- **Readiness in F03 is pack-level or manual**: `pack_for_source` (approved / not) OR the ad's own
  「素材已就位」 tick. Per-set counts on the ads side are feature-3 fidelity; no new workbench public
  entry is added for them. `briefs_for_source` still gives the per-ad brief id for a deep link.
- **Matching is by exact name** through `app/meta/repository.py`'s `campaign_ids_by_exact_name` /
  `ad_set_ids_by_exact_name` / `ad_ids_by_exact_name`; the failure wording rules of
  `app/schedule/binding.py` (no-account-bound message wins alone; per-node reasons; dedup; one
  message for the batch) are reused as behaviour, re-implemented small in `ads`, never imported.
- **Outcome ingest** reads `meta_entity_spend` only through `app/meta/repository.py`
  (`daily_entity_spend`); the simulated adapter writes `ads_outcome_daily` directly. No module
  writes another module's table.
- **Money totals belong to the group level** (planner, F03-I01 review): `ads_outcome_daily` holds
  rows at both `entity_kind='group'` and `'ad'` (ad rows exist for 廣告層花費占比, ruling 7), so any
  campaign-level total — 成效 tab, 結案 verdict against `success_target` — sums **only** the
  `group` rows. Summing both levels double-counts. The one place that derives it is
  `app/ads/repository.py::_outcome_totals`; nothing else re-sums.
- **A null success target is legal** (planner, 2026-09-12, settling the F03-I03 block against the
  merged F03-I01 schema): the model returns `success_target = null` with its reason in
  `success_basis` when it cannot defend a number from the data it was given — an invented number is
  the failure, a missing one is not. `ads_campaign.success_target` is made nullable by
  `supabase/migrations/20260913000002_ads_success_target_nullable.sql` (F03-I18; the applied
  `…0001` file is not edited) with **no** CHECK tying it to a status — a campaign may run to the end
  and close without one. Consequences other issues must follow: the **結案 verdict** (F03-I12)
  returns 看不出 when the target is null, with `verdict_json` saying the target was never set — it
  never treats null as 達成 or 未達成; the **策略 tab** (F03-I14) renders 「尚未設定成功條件」 in the
  成功條件 card instead of a number (and the edit affordance is how the user sets one); `create_campaign`
  accepts `None` but still rejects a present-but-non-numeric value.
- **The draft PATCH cannot create a state the create path refuses** (planner, F03-I03 review).
  `PATCH /api/ads/brands/{brand_id}/campaigns/{campaign_id}` shipped in F03-I03 as a plain column
  write with no cross-field or state check; **F03-I19** closes three holes and no later issue
  re-opens them:
  1. `start_date` / `end_date` are validated **after merging the patch onto the stored row** (a
     patch may send only one of the two), with the same refusal as the create path — the screen
     must not be able to produce `end < start`, which silently erases `budget_total`
     (`_budget_total` returns `None` when `days <= 0`) and makes the 結案 verdict meaningless.
  2. `name`, `start_date` and `end_date` are refused once `local_state != 'unbound'`: a bound
     name is exactly what exact-name matching resolves against, and a change to a bound node is an
     `ads_action` (§6.5), not a field edit. `success_metric` / `success_target` / `success_basis` /
     `constraints_json` / `product_ids` stay editable at **every** status — that is what F03-I14's
     成功條件 edit affordance needs on a campaign that is already running.
  3. `context_json.product_ids` is only ever a reference that resolves: the ids the model returns
     (F03-I03) are filtered against this brand's own `product` rows before they are stored, and the
     ids a patch sends are refused if they are not this brand's. F03-I05 reads those ids per brand,
     so an unresolvable id silently drops a product out of the strategy prompt instead of erroring.
  API error `code`s stay snake_case machine tokens (`dates_required`, `end_before_start`,
  `campaign_bound`, `product_unknown`) and the Traditional Chinese sentence is the `message` — the
  create endpoint currently keys two of them by the Chinese sentence itself; F03-I19 fixes that too.
  `frontend/src/lib/adsApi.ts` reads `message` only, so no frontend issue is affected.
- **The budget engine's `history` input is pre-aggregated by its caller** (planner, F03-I04 review).
  `app/ads/budget.py` is a pure calculator: it never queries spend. `scenarios(conn, org_id,
  brand_id, *, product_ids, days, history)` takes
  `history = {"cpa": float, "last_daily_budget": float, "sample_days": int, "sample_ads": int}`
  — or `None`/no `last_daily_budget`, which is what puts it in 冷啟動 mode. Consequences:
  - **F03-I05 builds that dict** (`app/ads/repository.py::budget_history(conn, brand_id)`, returning
    `None` when the brand has no settled spend): `cpa` = median of daily CPA over the last 30 days of
    `ads_outcome_daily` for this brand, **summing only `entity_kind='group'` rows** (the double-count
    rule above); `last_daily_budget` = the most recently closed campaign's `sum(group.daily_budget)`;
    `sample_days` / `sample_ads` = how many outcome days and how many distinct bound ads that median
    came from. Never pass a partial dict: no `cpa` means cold start, not a caption citing a CPA that
    does not exist. F03-I11 does not build it.
  - `daily` and `total` are both whole NT$ and `total = daily × days` exactly, so **F03-I06's
    `round(budget_planned / days)` returns the adopted daily unchanged**. Nothing re-derives one
    from the other.
  - `split(total, weights)` floors each share and gives the whole remainder to the largest share, so
    the table sums to `total` to the yuan. Amounts come from here; the model only returns
    percentages.
  - **A caption must name the arithmetic that produced its own number** — the history scenarios are
    `上一期日預算 × 0.6/1/1.6`, and the 30-day median CPA is context in `basis`, not a factor. Shipped
    in F03-I04 with a caption that reads 「近 30 天 CPA 中位數 x …」; **F03-I05 corrects that string**
    (it already touches this path) to 「上一期日預算 NT$<n> ×<mult>」 and adds the falsifier that no
    caption mentions a CPA median when `history["cpa"]` is absent.
- **The approval scope string is `"ads_campaign"`** (planner, F03-I06 review). `ads` gets its own
  `scope_type` in the shared `approval` table, separate from schedule's `"schedule_tree"`; the one
  definition is `app/ads/plan.py::APPROVAL_SCOPE_TYPE` and every later issue **imports that constant**
  rather than retyping the string. How it behaves in F03, deliberately: `app/core/approval.py::latest`
  returns `None` when the brand has never been approved, and **no F03 endpoint writes an approval
  row** — so the brake is inert on a fresh brand and only bites once one exists. That is accepted
  (ruling 10: 手動發布沒有硬擋; the money ceiling is a ceiling, not a publish gate), and the brake is
  falsified by a test that writes the approval directly. **F03-I09** is where an approval is written:
  when the user confirms 手動發布 for a campaign, write one `approval.approve(..., scope_type=
  plan.APPROVAL_SCOPE_TYPE, scope_ref=<campaign_id>, amount=<sum(daily) × days>,
  max_daily_amount=<sum(group.daily_budget)>)`, so a later raise on 投放結構 is measured against what
  the user actually signed off. Known ceiling, not a bug to fix in F03: the approval is **per brand**,
  not per campaign (`latest()` filters brand + scope_type only), so two live campaigns can each pass

- **`ads_action` is written for bound rows only** (as shipped in F03-I06, confirmed by review).

# Acceptance

One walk, on a restarted backend, with the `simulated` adapter and test data (the system is
unpublished; `supabase db reset` and rebuild is allowed):

1. 側欄「投放中心」 opens the campaign list; a brand with nothing shows an honest empty and one
   「建立 Campaign」 entry.
2. 建立 Campaign: one sentence, start and end date, optional constraints → a draft Campaign exists
   with `goal_text`, a derived `objective`, a `success_criterion` (metric, target, basis) and the
   ids of the brand/product rows it used; every derived field is editable and labelled 系統帶入.
3. 策略: one recommended strategy with the 新客／再行銷／探索 split and three budget scenarios;
   with no history every scenario carries 冷啟動估算 and 「哪些是推估」 says so; 查看策略依據 lists
   the brand facts, the offering price with its effective date, and the learnings used.
4. 採用策略 writes the delivery plan as rows — one channel (Meta), 投放組 with daily budgets, 廣告
   with coordinates and tracking names; the budget is edited on 投放結構 and the displayed campaign
   total (`sum(daily) × days`) follows it; the ad level shows no budget field.
5. 素材: one pack lands in 素材工作檯 with one 素材組 per 廣告, a summary and an origin line pointing
   back; 核准整包 turns that pack's ads 已就位（工作檯）; an ad outside the pack is ticked
   素材已就位 by hand and records who and when.
6. 發布: the normal path says 自動發布未接上; 手動發布 gives the copyable checklist 逐節點 from the
   campaign node down and binds by exact name; 模擬發布 binds fake entities **and writes the daily
   outcome rows for the days already elapsed**, so the next step needs no command line.
7. 成效: daily spend / purchases / CPA / ROAS (conservative main, optimistic in the caption) with
   every number captioned; before publish it reads 還沒有成效資料, never 0.
8. 結案 (manual now, automatic at end+7d proven by a test): the verdict compares the outcome with
   `success_criterion` and is allowed to be 看不出; one learning row is written at 已觀察 with its
   evidence, its sample and its source campaign, and shows up in 品牌智庫.
9. The next campaign's strategy prompt includes that learning and 查看策略依據 names it.
10. Every change that was meant to reach a platform (publish, bind, budget edit after publish) has
    an `ads_action` row with before/after/who/sync state, and the undo of one of them writes a
    reverse action.
