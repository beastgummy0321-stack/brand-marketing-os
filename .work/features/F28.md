# Outcome
Every campaign is judged against ONE cost-per-result cap set on the strategy tab; ads are graded 划算／偏貴／太貴／白花 against it; cleanup closes the right ads (白花 first, then the most expensive over-cap ones, never 划算) as one decision; an over-cap budget needs an explicit confirmation; an approved launch whose plan changed can be re-approved or reverted; an interrupted background job is re-queued once. The home, strategy tab, campaign detail, cleanup proposal and stale-launch screens match `docs/design/ads/prototype-v9-ads-center.html`.

## Contracts (every issue uses exactly these names)
- **Cap storage (I01).** Canonical store = `ads_campaign.target_cost` with `target_basis='own'`. `success_metric`／`success_target`／`success_basis` stay as columns but no code reads or writes them and no API returns them. `target_basis` allows only `own`／`break_even`／NULL. Cap view (target GET, campaign detail `cap`, triage `target`): `{value|null, basis: "own"|"break_even"|null, own_value|null, break_even|null, price|null, product_id|null, result_kind|null, result_label, missing: ("product"|"product_cost"|"result_kind")[], revision}`. `break_even` and `price` come from product economics even when an own cap is set (ruler 打平 mark, ROAS 參考 = price ÷ cap).
- **Grades (I02).** Per active ad, on the triage item: `grade: "on_target"|"watch"|"over"|"wasted"|"insufficient"|"no_target"`, `grade_label` (划算／偏貴／太貴／白花／還太新、看不準 when below the sample gate, 資料不足 for any other insufficient reason／未判斷). Same window steps and sample gate as today (§6.17: spend ≥ 3 × cap, or ≥ 10 results over ≥ 7 days); a missing previous window no longer blocks a grade. `class`／`change_pct`／`previous` keep their meaning as the trend note.
- **Queue (I02).** `stop_loss` rows are no longer raised (the kind stays readable for existing rows). `cleanup` payload keeps its existing keys and adds `ads[].{grade, cost_per_result, spend, result_count, daily_spend}`, `keep: [same shape]`, `short: int`, `daily_saving|null`, `scale_owner_id|null`; a cleanup row is raised when a campaign has a 白花 ad or is over capacity with a closable ad. `worse` rows keep the trend trigger but are not raised for an ad inside its campaign's cleanup `ads`. `scale_budget` qualifies an owner by grades (all active graded ads 划算, 還太新 allowed, at least one 划算) plus the existing month-budget fit; +20% unchanged.
- **Budget scenarios (I03).** Result gains `budget_cap|null` (= `constraints_json.budget`); every row gains `over_cap|null` (amount above the cap); a row `{key: "cap", label: "照預算上限"}` is added when a cap exists; `recommended` points at `cap` when the old recommended row is over the cap. Cold start multiplies the resolved cap (no `TARGET_CPA_RATIO`). Row labels: cold start 最低／穩定成長／積極, history 保守／照上一期／積極 (keys unchanged). `POST …/strategy/scenario` accepts `confirm_over_cap: bool`; over the cap without it → 409 `over_cap_unconfirmed`; a confirmed choice is recorded in `budget_basis_json.over_cap_confirmation {by, at, total, cap, over}`.
- **Stale launch (I04).** `GET …/handoff` gains `launch_stale: null | {change_set_id, approved_at, changed_at|null, content_hash, diff: [{kind: "campaign"|"group"|"ad", item_id|null, name, field, field_label, before, after}], unchanged_count, revertible: bool, revert_blocker|null}`, computed on read (not only after a check). `POST …/handoff/launch/reapprove {change_set_id, content_hash}` and `POST …/handoff/launch/revert {change_set_id, content_hash}`.
- **Home overview (I06).** `GET /api/ads/brands/{b}/home?month=YYYY-MM` → `{month, day_of_month, days_in_month, currency|null, spent|null, money: {purchases|null, cost_per_purchase|null, cap: {value, basis}|null, earn|null, earn_missing: string[], excluded: [{campaign_id, name, reason}], previous_same_period: {days, purchases|null, cost_per_purchase|null}|null}, pace: {budget_amount|null, available|null, daily: [{day, cumulative}], projected_month_end|null}, quality: {buckets: [{grade, amount, count, ads: [{entity_id, name, thumbnail_url, spend}]}]}, timeline: [{date, kind: "today"|"month_review"|"campaign_start"|"campaign_end", campaign_id|null, name|null, ready|null}], campaigns: [{campaign_id, name, origin, status, month_spend|null, purchases|null, cost_per_purchase|null, cap: {value, basis}|null, active_ads, daily_budget|null, missing_days: [], sync_state, draft: {start_date, cap_missing, ads_total, ads_ready, approved}|null}], sync: {last_success_at|null, next_at|null}}`. Client and types in the new `frontend/src/lib/adsHomeApi.ts`.

## Agent choices (reversible; not asked)
- The cap is edited on the strategy tab for every campaign, imported ones included; `/campaigns/:id/target` redirects to `?tab=strategy`; product and result-kind choice move into that block's fold.
- The brief prompt extracts only a cost-per-purchase cap; a ROAS or count in the sentence is not converted; a reply without `cap` still parses (the e2e scripted provider in legacy `app/llm/providers.py` is not touched).
- Plan snapshots and review premises drop the target (the cap is not a platform setting, so changing it never makes a handoff stale). Rows approved before I01 compare stale once on the dev DB; that is test data and I04 is the exit.
- Learning cohort = same brand, same `result_kind`, same verdict. Closeout judges cost per result against the resolved cap.
- Home: one 已花 number for the whole screen; quality buckets sum exactly to it (spend not on a graded active ad lands in bucket `ungraded`). Earn/cost-per-purchase cover purchase campaigns only; other campaigns are listed in `excluded`. Decisions on home: open `cleanup`, `worse`, `refresh_creative` rows (in that order), 3 shown, the rest behind one fold. The pace card keeps a 調整 link to the existing monthly-budget editor.
- Re-approve supersedes the old launch set with a new version; items whose expected fields are unchanged keep their verification; the month-budget preflight runs again. Revert refuses with a named reason when a diffed value cannot be written back exactly.
- R3: jobs with their own domain recovery (`background.ads_review_round`) keep it; strand counting is durable (procrastinate's own job records), never in memory.
