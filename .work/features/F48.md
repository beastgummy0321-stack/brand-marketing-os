# Outcome
Drill ruler dimensions 1／3／4 (judgement, budget, planning facts). Six defect generators from the 2026-10-04 audit
(`docs/backlog/audit-2026-10-04/README.md` W1–W6, decisions 1–14 user-confirmed 2026-10-04) disappear, each with a
machine check that goes red if the pattern returns:
1. **W1 one grading／learning ruler** — `learning_rank` + `triage.grade_window` are the only rulers; settle, closeout verdict,
   month review, A/B and cleanup derive from them; sample size is shown, never a hidden gate; one `ads_learnings.write()`
   every ledger row goes through, always with `product_id`; 「留下」 carries the approved creative into the next plan;
   the API serves thresholds／labels／sentences and the frontend prints them.
2. **W2 one budget calculator** — `app/ads/budget.py` is both directions (total⇄daily, split, month portion); adopt rounds
   the total; no re-split on read; no browser arithmetic; PATCH after adopt gated; a new total after adoption re-splits
   the ad sets and says so.
3. **W3 planner_context** — one `planner_context()` every planner (brief／strategy／plan／create_ad／update_ad) reads:
   product name＋kind, facts, forbidden claims (both stores), offers with sentences, customer groups, product-scoped
   learnings, previous `learning_goals`; hand-made ads obey the same menus.
4. **W4 one claims guard** — `claims.validate(product_id, text)` strips registered names, reads both forbidden stores,
   is product-scoped; workbench (warn) and slot (block) give the same verdict; a statutory hit is never stored as
   forbidden; the offer an ad was written for is one resolver; ad names pass the same check.
5. **W5 strategy facts from the program** — group／offer／number sentences are built from structure and closeout rows;
   the model writes connecting prose without numbers; the frontend prints backend sentences.
6. **W6 capacity and pause reason** — the plan respects `can_support` + 1 explore slot; pause／cleanup／scale reasons are
   built from the ad's own triage grade.

Out of scope (features B–D chain on this branch): lifecycle／queue／sync／slot states (W7–W10, W17), time／input rules／
readiness／background (W11–W14), http／figure／wizard／platform gate (W15–W19). A W1–W6 fix that needs one of those makes
the minimal local change and notes the sibling in Evidence.

Agent choices (settled so workers do not invent them; recorded in `docs/architecture/ads.md` §6.50 at crank closeout):
- **Contract R — one ruler (backend).** `app/ads/learning_rank.py` and `app/ads/triage.py::grade_window` are the only two
  functions that turn (spend, results, cap) into a judgement; every constant they use lives in those two files
  (`triage`: `WATCH_BAND`, `STOP_LOSS_SPEND_MULTIPLE` (renamed in meaning: the 沒賣出 threshold, not a gate), `MIN_RESULT_EVENTS`,
  `WINDOW_STEPS`, new `BREAK_EVEN_BAND = 0.02`; `learning_rank`: `SAMPLE_FEW`, `NEAR_BEST`). Rules:
  grade — a window with a known cost (results ≥ 1, spend known, one currency) is always graded 划算 ≤ T／偏貴 ≤ 1.2T／太貴 > 1.2T;
  known 0 results with spend ≥ 3T = 沒賣出; known 0 results with spend < 3T = `too_new` 「剛開始、數字還不夠」 (a label, no cost
  exists yet, never closable); unknown／mixed-currency = 資料不足; no cap = 未判斷. `reason_code` `below_sample_gate` is
  renamed `too_new` everywhere it is emitted or read (`triage_scale`, `WaitPage` sentence table included).
  sample — every graded item carries `sample {sales, few: sales < SAMPLE_FEW, too_new: days < WINDOW_STEPS[0] and sales <
  MIN_RESULT_EVENTS}`; screens print 「樣本少」／「還太新」 beside the grade; no decision reads these flags except the two
  named below.
  ordering／verdict — `learning_rank.rank` is unchanged (sold by cost asc, 沒賣出 after; keep ≤ cap, keep_relative within
  NEAR_BEST when nothing is under the cap, else replace). Cleanup (`triage_capacity.cleanup_candidates`) ranks the campaign's
  graded active items with `learning_rank.rank` and closes from the bottom: every 沒賣出, then `replace` sold rows most
  expensive first while over capacity; `keep`／`keep_relative`／ungraded never close; `_CLOSE_RANK`／`_KEEP_RANK` go. Each
  `ads`／`keep` entry carries `rank, of, sales, few, verdict, verdict_label, flags, reason_text` and the list is served in
  that order (the frontend never re-sorts).
  derived rulers — settle fate: `keep`／`keep_relative` → effective, `replace` → ineffective, unranked → skip (the scope gains
  `group=<customer_group_id|none>`); closeout verdict: 達成 if actual ≤ cap else 未達成, `sample_bucket` kept only as the shown
  `verdict_json.sample` {purchases, days, bucket}; `learning._confidence` counts same-direction campaigns whose purchases ≥
  `MIN_RESULT_EVENTS` (the one place sample size changes a level, and it is a confidence level, not a verdict); visual
  learning writes 低-sample rows with `sample_size` = bucket instead of skipping, and skips only `purchases is None`
  (「成效未追蹤」); `month_summary._verdict` = `triage.cost_grade` on_target → met; `experiments.DEFAULT_RULES.min_days` =
  `WINDOW_STEPS[0]`, `min_conversions_each` = `MIN_RESULT_EVENTS` (imported, not literal; `relative_difference` stays the A/B
  band). Scale-up keeps 「every active ad 划算」 and adds a stated reason: an owner whose summed sales < `MIN_RESULT_EVENTS`
  is not proposed and the queue read says 「樣本少，先不加碼」 (it is a money action, and the reason is shown).
  reason texts — `triage_pause.view` serves `pause.reason_text`, cleanup entries `reason_text`, scale rows `scale.reason_text`,
  each built from that ad's own grade and numbers (「每筆 X 對上限 Y，太貴」／「花了 X 一筆都沒賣出」／「第 r／n 名…」); the
  frontend's `PAUSE_REASON`／`CLEANUP_PAUSE_REASON`／`BUDGET_REASON` constants are deleted.
- **Contract R-API — rules served.** `GET /api/ads/brands/{brand_id}/rules` → `{"grade": {watch_band, unsold_spend_multiple,
  min_results, min_days, sample_few, near_best, break_even_band}, "ab": {min_days, min_conversions_each, relative_difference},
  "labels": {"grade": {on_target, watch, over, wasted, too_new, no_data, no_target}, "verdict": {keep, keep_relative, replace},
  "flags": {few, relative, relative_no_cap}}, "glossary": {cap, on_target, watch, over, wasted, thin, money, notebook,
  break_even}}` — every value read from the two ruler modules (a backend test asserts equality); glossary sentences are
  built by the program from the constants (today's `glossary.ts` wording), `break_even` without the value (the frontend
  appends 「（這裡是 X）」). Frontend: `useAdsRules()` in `components/ads/patterns/rules.ts` (module cache, one fetch per page
  load, tests seed a fixture) is the only reader; every meter axis, legend, hint, glossary sentence and verdict word comes
  from it; while loading, words print without numbers (no fallback literal). `GRADE_LABEL`／`NO_OFFER`／`SAMPLE_FEW`
  frontend constants go; branches use `grade`／`reason_code`／`verdict`／`offer_key` (slots serve `offer_key`), never a label.
- **Contract W — one learning writer.** `app/ads/ads_learnings.write(conn, org_id, brand_id, *, product_id, text, scope,
  confidence, sample_size, source_cycle_id, source_track, needs_revalidation=False, platform=None)` is the only caller of
  `bi_repo.record_learning` in `app/ads`. `product_id` is a required keyword: the campaign's sell-way

- **Contract K — 留下 carries the creative (decision 2).** At `plan.adopt_strategy`, before the model is asked, the program
  carries every `keep`／`keep_relative` row of the newest closed campaign of this sell-way (rank order, up to the ad
  ceiling of Contract C) as **carried ads**: same seven coordinates, same name, `customer_group_id`, `scene`,
  `coordinates_snapshot_json.carried_from = {campaign_id, ad_id}` (no migration), in the new group whose role equals the
  previous ad's group role (role absent → the `new` group, else the first group). The previous ad's creative — its

- **Contract C — capacity ceiling (decision 4).** `triage_capacity.can_support(daily_budget, cap)` (pure, extracted from

  `_MAX_ADS_PER_GROUP` stays an upper bound. The plan prompt states 「這期每天 X，撐得起 N 則（另加 1 則探索）；最多 M 則」; a
  reply with more ads than the ceiling is refused like the scene rule; the strategy prompt gets the same capacity line so
  its allocation can say why more roles. The structure tab prints the served `capacity {daily, cap, can_support, ceiling}`.
- **Contract M — one money calculator.** `budget.whole(x)` = half-up whole number (`floor(x + 0.5)`), the only rounding of a
  money figure in `app/ads` (`learning_rank.whole` and `wizard_options`' copy call it; every bare `round(` on money goes).
  `budget.daily_of(total, days)` = `floor(total / days)` — the one exception to half-up, so the structure never commits more
  than the chosen total and never trips the cap gate by rounding; `budget.total_of(daily_sum, days)` = `daily_sum × days`
  (exact). Scenario rows: `daily` = `whole(...)`, `total` = `total_of(daily, days)` (cap row: `daily_of(cap, days)`, so
  `over_cap` is 0 by construction). `select_scenario` stores the chosen `budget_planned` (a custom total unchanged) and the
  campaign read serves `budget_preview {daily, total, chosen}` = `daily_of` → `total_of`, with `note` 「每天要是整數，這期
  實際 X」 when `total ≠ chosen`. `adopt_strategy` splits `daily_of(budget_planned, days)` with `budget.split` and then
  rewrites `budget_planned := total_of(Σ group daily, days)` (adopt rounds the total). `repository._budget_total` =
  `total_of` (no `round(…, 2)`), so after adopt `budget_total == budget_planned` by construction. `reconcile_campaign`
  recomputes allocation amounts only while `budget_planned is None` (projection); after selection the stored amounts stand;
  after adoption amounts = per-role Σ group daily × days. `update_campaign` refuses `start_date`／`end_date`／`product_ids`／
  `customer_group_ids`／a `constraints_json.platform` change once `status != 'draft'` → 409 `plan_already_adopted` (the budget
  cap stays editable, §6.32). `select_scenario` on a `ready` campaign with unbound groups re-splits every group's
  `daily_budget` by the stored allocation pcts (`_check_budget_ceiling` applies), rewrites `budget_planned`, and returns
  `resplit [{group_id, before, after}]`; with any bound group → 409 `campaign_bound`. Month portion: `month_fit.extra` keeps its
  number and gains `extra_basis {month, days, period_total}`; the card prints 「{N} 月的 {days} 天要花 X（整期 Y）」.
  Frontend: `currentBudgetTotal`, `StrategyTab.amountOf`, `ScenarioBars`' `Math.round(total×pct)` and the 差額 KPI go; after a
  group PATCH the tab re-reads the campaign. Scanner: no `Math.round(` over total／budget／amount／pct in `components/ads/**` or
  `lib/ads*.ts`; no comment matching `mirrors|same (formula|rule) as|同一套` that names `app/`.
