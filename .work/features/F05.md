# Outcome

一個新品牌走完建檔精靈之後，系統手上有投放需要的每一項地基：至少一項要賣的東西（商品或服務）
連著售價／成本／運費（服務再加成交率）、一個已設定的成效目標、一個已接上而且指定給這個品牌的
廣告帳戶，以及系統自己跑出來的品牌知識——不必再叫使用者去外部 AI 貼一段東西回來，也不必自己
繞到商品頁補金額。精靈的最後一頁與投放中心的「建立 Campaign」入口讀同一份程式算出來的
可投放檢查表，缺什麼寫在畫面上、按鈕直接帶去補；不擋人，只是不再讓人在第七站才發現地基是空的。
同時，核心迴圈不再寫死 Meta：通路清單與成效目標的名字都從資料來，`app/ads` 裡再出現平台字串
會被測試擋下來。有帳戶歷史的品牌，預算建議讀得到近 30 天的真實花費；沒有的，誠實走冷啟動估算。

# Decisions

## 使用者的話（原文，這一輪的方向）

- 「AI 先做，人再決策：理解目標後直接產出可執行方案，使用者主要負責看懂、修改、確認。新手極簡，
  熟手可下鑽：預設畫面乾淨，專業設定需要時才展開；不是兩套模式，而是同一份資料的不同深度。
  系統吸收複雜度：使用者不需要理解 Meta / Google 的底層結構，也能完成合理投放。從投放到學習形成
  閉環。避免過度工程：不複製 Ads Manager、不堆 Dashboard、狀態機、模式、抽象層或規則；能刪就刪，
  先解決真實問題。」
- 「從一開始的品牌建檔頁面開始，應該就先詢問業主的業務類型，有無產品、產品幾項等等。現在是非常
  雜亂品牌與產品一起抓一起掃，使用者漏填一堆系統也不會知道。品牌也沒有強制 sku 組數或金額等。
  我需要一開始就把地基打好而不是現在東缺西缺，少東西還要使用者回頭繞迷宮補。必要資訊如 Meta
  Token、GA4 等成效回收工具也要一併放入。建檔填資料與基本的金額毛利等詳細營運參數。廣告中心有
  排過就 Agent 自己抓歷史數據建議金額，沒排程過就由系統算出最佳試驗金額去做投放。其餘動作與現在
  保持不變。」
- 「不要寫死平台，必須要先前區隔開來。」
- 「使用者」＝身分（老闆／行銷／代理商），不做角色系統，文案一律稱「你」。

## 已經定案、工人不得重開

1. **不預設**（已寫進 `ARCHITECTURE.md` §0）：核心迴圈沒有平台／客戶類型／使用者角色／成效來源的
   分支；那些是列上的鍵。差異住在 `app/ads/adapters/**` 與 `app/ads/channels.py`；畫面上的名詞來自
   資料自己的 label。不做平台抽象層、不做 Google／TikTok 接入、不做角色系統。
2. **一次轉換的價值只有一個家**（§8 第 1 條）：`product_economics` ＋新的可空欄位 `close_rate`
   （成交率）。`(售價 − 單位變動成本 − 運費) × 成交率`，`close_rate` 為 NULL 就是商品（×1，行為與
   F05 之前完全一樣）。服務／名單填成交率與每單毛利，運費填 0（「沒有運費」與「不知道運費」是兩件
   事）。不開新表、不開第二套 API 形狀，寫入一律走既有的 `save_product_economics`。
3. **沒有品牌層的「業務類型」欄位**：商品／服務／兩者是精靈步驟 3 的一個控制項，決定畫面顯示哪些
   欄位；留在資料庫裡的答案就是那些 offering 列本身。（`brand.industry` 2026-08-29 因為沒有讀者被
   刪掉，再加一個只有畫面自己讀的欄位就是重蹈覆轍。）
4. **成效來源就是既有的 `brand.conversion_goal`**（purchase／lead／booking／awareness），精靈步驟 4
   設定它。不新增 `success_metric` 的 lead 值——「每筆名單成本」與 CPA 是同一個算式的兩個名字，
   會變的只有 **label**。這一條與收到的範圍第 7 點（新開 migration 擴充 `success_metric` CHECK）
   不同：規劃師改判，理由是新增分支違反同一輪剛定下的「不預設」，而 label 由資料決定既便宜又誠實。
   使用者要的「每筆名單成本」照樣會出現在畫面上（F05-I09）。
5. **可投放檢查表歸 `app/ads`**（§8 第 3 條）：`app/ads/readiness.py`、公開入口
   `app.ads.launch_readiness`、端點 `GET /api/ads/brands/{brand_id}/readiness`。三項擋人的
   （至少一項要賣的東西且填了數字／廣告目標已設定／廣告帳戶已接上並指定給這個品牌）＋一行不擋人的
   （品牌知識條數）。**不擋人**：缺東西時主要按鈕變「先補齊地基」，「還是要先建立」仍在。
   沒有「N 條 confirmed 事實」門檻。
6. **精靈五步**：1 起始輸入 · 2 初步印象 · 3 賣什麼與數字 · 4 接工具 · 5 品牌知識（問答 → 系統自己
   跑研究 → 真相卡 → 完成）。完成的觸發點不動（待確認清單清空 → `state.complete_draft`），所以
   「接工具」排在品牌知識之前。
7. **精靈的事實寫入者**（§8 第 4 條，2026-09-14 實測）：`create_items` 全專案只有 `state.py:284`
   一個呼叫端，資料來源是貼回那一步——**外部 AI 的貼回是 `brand_fact`／`product_fact` 的唯一寫入
   者**。實測：常春健康（有貼回）11 列 items、4 brand_fact ＋ 3 product_fact 全 confirmed，但
   `product_economics` 0 列；MOVE Daily 停在步驟 3（`has_paste = f`）→ items 0、facts 0，金額是
   使用者自己繞到商品頁補的。修法是讓系統自己跑，回覆餵給**同一個解析器**
   （`state.apply_paste` → `paste_parse` → `create_items`）：不新增第二個解析器、不新增第二個
   事實寫入者。提示詞不是照抄交接包那份（見下一條）。
8. **預算的歷史來源**（§8 第 5 條）：`budget_history` 回傳帶 `source`；沒有已結案的迴圈花費就退回
   讀這個品牌自己綁的廣告帳戶（近 30 天每日花費＋CPA，經 `channels.py` → `app.meta.repository
   .spend_summary`，帶品牌的 `conversion_goal`）。什麼都沒追蹤 → 誠實冷啟動。**模型不讀廣告歷史**
   （ADR 0067），數字一律程式算，模型只負責把依據講成人話。
9. **`intake` 升格為受管模組**（`ARCHITECTURE.md` §2）：升格前先量過，七條違規全是「早就存在但沒
   宣告」的 import，靠補四個 legacy facade 與兩個測試檔解決，**沒有搬動任何程式**。`uv run python
   tools/check_architecture.py` 目前 exit 0。
10. **檔案大小是慣例不是閘門**：2026-09-10 起機器不再量行數
    （`app/tests/test_architecture_boundaries.py:16-19` 明寫那些 ratchet 已移除）。但慣例照守：
    `app/intake/routes_api.py` 已經 716 行、`app/brand_intelligence/repository.py` 1,455 行，
    精靈的新後端一律開新小檔（既有慣例：`routes_t2_api.py`、`advertising_history.py`、
    `personas.py`）。沒有人會因為多寫兩行被閘門擋下來——會被擋的是審查。
11. **e2e 閘門只掛會改畫面流程／版面的票**（I04／I05／I06／I07）。純後端票跑 `npm test`（vitest）
    就好——F04 的先例（F04-I25）就是這樣，而且 8720 一次只能有一個 e2e：**帶 e2e 的票一次只
    finish／merge 一張**。
12. **帶 migration 的票（I01）合併前**要先手動把那支 migration 套進開發庫 54322 並登記，否則
    merge smoke 會紅燈、worktree 直接被丟掉。
13. 工具一律用 `uv run python -m <tool>` 叫（Windows Smart App Control 會擋 worktree 裡的
    `pytest.exe`／`pyright.exe`）；跑 pytest 前 `unset BRAND_OS_LLM_PROVIDER`。

14. **這一輪不開網路搜尋**（規劃師的假設，**使用者可翻案**）：系統自己跑的品牌調研沒有工具、
    沒有網路搜尋——`gateway.TaskOptions.tools` 預設 `None`，正式程式沒有任何一處掛
    `providers.WEB_SEARCH_TOOL`（ADR 0048 延後、按次計費）。所以它**不照抄交接包那份提示詞**
    （`script.build_prompt` 要求逐一附來源網址、挖 5 句以上逐字顧客原話，那是寫給能上網的外部
    AI 的；照抄＝要模型編造）。做法：程式用既有的 `app.core.net.fetch_url` 抓**使用者自己填的
    網址**，把文字交給模型；提示詞明文禁止編造來源；顧客原話這一輪不產，畫面維持誠實的
    「累積中」，要補就走進階摺疊的外部 AI 路徑。要開網路搜尋是使用者的裁決，翻案就重切 F05-I06。**使用者 2026-09-14 裁決：「暫時不開」**——這一條在 F05 內是定案。
15. **精靈步驟表整個 F05 只改兩次**：F05-I04 一次（今天的問答／交接包／貼回合併成第 4 步
    「品牌知識」，四格）、F05-I05 一次（插入「接工具」，成為最終五格）。F05-I06 不碰那張表，
    只換第 5 步的內容。步數只准有一個出處——`IntakeWizard.tsx:102` 那個寫死的 `Math.min(5, …)`
    在 I04 就要改成 `Math.min(STEP_LABELS.length, …)`。中繼狀態（四格、第 4 步是舊的三段串）
    是刻意的，每一步都跑得起來、都能合併。

16. **產品有層級：一個產品、很多賣法**（`ARCHITECTURE.md` §8 第 1 條）。`product.parent_id` 可空、
    自我參照、**只有一層**（子不能再有子，寫在 `create_product` 裡擋，CHECK 看不到別的列）。
    子＝賣法（單瓶／3 入組／5 入組／隨身包），`name` 存完整顯示名「<母產品名> · <賣法>」。
    **知識掛母產品**（事實、宣稱、商品照、座標），**金額掛賣法**（`product_economics` 一個賣法一列）。
    一支解析器 `knowledge_product_id()` ＝ `COALESCE(parent_id, id)`，三個既有讀者改吃它。
    預算取 Campaign 選的 `product_id`；選到母產品就用它的**第一個子**（精靈先寫「單品」）。
    結案與學習以母產品彙總——F05 只記規則、不做畫面。**不做**：變體表、入數欄位、組合價自動換算。
17. **不知道就標假設，假設永遠帶著來源**（§8 第 3 條）。「不知道」按下去才把基準值填進欄位
    （沒按之前欄位是空的，不預填），那一列記進 `product_economics.assumptions_json`；使用者一改，
    標記就消失。基準值住在 `app/brand_intelligence/benchmarks.py`，每一條帶 label、值、來源名稱、
    來源網址、抓取日期，證據在 `.harness/scratch/research-onboarding.md`：
    **毛利率 45%**（NYU Damodaran，美國上市公司分業毛利率，資料日 2026-01，取中位鄰域當起點）、
    **運費 NT$80**（本站慣例，**沒有外部來源**，畫面要標「常見值」不是「來源」）、
    **成交率 20%**（HubSpot 2024 全業平均成交率）。畫面一律印「美國 2025 基準，起點用 · 來源：…」。
    **台灣沒有可引用的一手數字**（research 檔逐條查證過，ECPay 的數字自己註明轉引自美國 WordStream），
    所以不假裝有；正確的取代路徑是這個品牌自己的結案數字（F06），不是更好看的部落格。
    **模型永遠不提供這些數字。**
18. **可投放檢查表三色**（§8 第 5 條）：綠／黃／紅。黃＝這一項成立、但站在假設值或還在補的資料上
    （economics 有 `assumptions_json`，或帳戶綁好但 37 個月補拉還沒跑完）。每一列都寫為什麼是這個
    顏色；黃列有「去改」直接跳回該步驟。主要按鈕跟著最差的顏色走：
    紅「先補齊地基」／黃「進入投放中心（有假設值）」／綠「進入投放中心」；「還是要先建立」只在紅時出現。
    假設值也要出現在策略依據的句子裡（「用的是假設成交率 20%」）。
19. **原型是視覺唯一真相**：`.harness/scratch/prototype/intake-foundation/index.html`（已核准）。
    F05-I06／I07／I08／I10 的畫面照它做，視覺閘門在規劃師 review 時用它並排比對。它**不是生產程式**，
    不要 import、不要複製 Alpine。原型沒畫到的一處：步驟三商品區在原型裡是平的 SKU 列表，
    實作要照第 16 條做成「母產品標題列＋賣法列」（母產品一列、底下每個賣法一列、
    預設先給一列「單品」、可「＋新增賣法」與「複製這列」）。
20. **精靈裡使用者自己的錢一律 NT$**（售價／成本／運費／名單價值／預算）。**唯一的例外是右欄的
    AI 花費儀表**：它的數字原生是美元（`pricing.calculate_cost()`），而**本專案沒有匯率常數**
    ——票 M2 已經裁決過不要寫死匯率（`app/intake/script.py:19-34`：寫死的匯率會過期，等於在誠實
    狀態上開洞）。所以儀表維持 US$，但標題改成「這次建檔的 AI 花費（美元計價）」，讓它不可能被
    誤讀成你的貨款。要改成 NT$ 需要使用者給一個匯率常數與來源。

25. **沒有「陽春路徑」了**（2026-09-14 實機走查，`.work/ready/F05-I15.md`）：`state.start_or_quick()`
    在描述／網址／照片皆空時不建草稿、把人丟回經營概況——那是 F05 之前的真相（精靈只有掃描＋
    問答，沒東西掃就沒事做）。F05 之後第 3／4／5 步跟掃描無關，所以改成**精靈永遠有草稿**：
    沒東西可掃就照 `scan_skip` 把初掃標成做完、草稿直接落在第 3 步，**這條路徑上不准有任何
    模型呼叫**（「不花錢」的性質原封不動）。完成的去向不變。`quick` 這個回應欄位自此恆為
    `false`，留著只因為 `intakeApi.ts` 還在讀；哪張票下次動 `IntakeWizard.tsx`／`intakeApi.ts`
    就順手把它與那個三元導向一起刪掉，不另開票。F05-I15 審票（2026-09-14）放行，但留下五行舊真相註解（`frontend/e2e/smoke.spec.ts:36,42`、`frontend/e2e/width-overflow.spec.ts:16,57`、`app/intake/routes_api.py:8` 仍寫「陽春路徑」）——同樣規則：下次動到那幾個檔的票順手刪掉，不另開票、不為此重跑 e2e 閘門。

## 不做（有人手癢就指這裡）
