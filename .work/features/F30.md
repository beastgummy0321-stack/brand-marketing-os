# Outcome
Every remaining ads-center screen matches its approved prototype on real data: the new-campaign wizard (`#/new/1`, `#/new/2`), the campaign workspace's stage rail and its overview, structure and changes tabs (strategy leftovers and the perf tab included), the assets tab with its 素材需求 card, the full three-step publish page, and the connections page — all in `docs/design/ads/prototype-v10-ads-center.html`. When the fact check rejects the model's review text, the 變差 flow stays usable: the evidence shows, direction and copy unlock, and the user can ask the AI once more (`docs/design/ads/prototype-v10-ai-blocked.html`).

# Decisions
**User rulings** (/dig and /carve 2026-09-25):
- AI text blocked → the round stays usable without an AI recommendation, direction and copy unlock (copy starts from the platform's current copy), 「再請 AI 看一次」 re-runs the same evidence, and the negation list widens. Prototype approved.
- The wizard's 預算上限 is **this campaign's spending cap** (`constraints_json.budget`), not the brand's monthly allowance; the label reads 「這個活動最多花」.
- Objectives are one merged cross-platform list (Contract C). Only objectives the backend already supports are selectable; 互動, App 推廣 and 來店 are reserved seats shown as 「尚未開放」, not built.
- Ads without ready material: **pending user confirmation of the recommendation in Unresolved 1** (default applies).
- The rule text for the review fix goes to `docs/architecture/ads.md` in the crank closeout (lead only).

## Contracts (paths under `/api/ads/brands/{b}` unless absolute; every issue uses exactly these names)
- **A. Review AI rejection (I01).** In `review_jobs.apply_saved_task`, a succeeded task whose output fails parsing, the size cap or `review_policy.validate` makes the round `status='ready'`, `error=NULL`, `result_json={recommendations: [], limitations: evidence.limitations, causality: "unavailable", rejected: {reason}}`. A provider failure (task not succeeded) keeps today's `failed`/`unknown`. `unsupported_claim` also accepts 不足以, 無法判斷, 無法判定, 未能 as negations (the digit rule stays). `POST …/campaigns/{c}/reviews/{id}/retry` → `{review, monitor}` (same shape as create): allowed when `decision IS NULL` and (`status='failed'` or `result_json.rejected` is set), else 409 `review_unavailable`. It submits a new round from the old `evidence_json` plus `retry_of: <old id>` (a new digest; a repeated call returns the same retry round; `retry_of` is not sent to the model), with the old entity, window and `previous_id`, and reserves AI cost like any round. The retry round replaces the old one wherever the entity's current round is read (triage proposal `review_id`, review monitor, `workspace`). Frontend: `ReviewRound.result_json.rejected?: {reason: string} | null` (optional like its siblings), `retryReview(brand, campaign, reviewId)`.
- **B. Wizard options (I04).** `GET …/new-campaign/options` → `{products: [{id, name, price|null, currency|null, thumbnail_url|null, has_cost}], objectives: [objective]}`; products = active, not archived, ordered by name; `has_cost` = the current effective unit variable cost is set. Built in `app/ads` through the products legacy facade (no new code in legacy).
- **C. Objective catalog (I04).** One table in `app/ads` (also the allowed set in `brief.py`): `{key, label, description, available, platforms: {meta, google_ads}}` —
  購買 (銷售業績 / 銷售, available), 名單 (潛在顧客 / 潛在客戶, available), 流量 (流量 / 網站流量, available), 知名度 (知名度 / 品牌認知度和觸及率, available), 互動 (互動 / YouTube 觸及、觀看與互動, reserved), App 推廣 (應用程式推廣 / 應用程式推廣, reserved), 來店 (null / 來店客數與本地推廣, reserved). 加購物車 stays accepted but unlisted (a Sales optimisation event, not an objective). Grading families are unchanged (`repository.objective_family`).
- **D. Structured create (I04).** `POST …/campaigns` accepts `{product_ids: [id], objective, start_date, end_date, budget: number > 0}` with `goal_text` optional (composed server-side from the picks when absent); an unavailable objective is 400 `objective_unavailable`; `budget` is stored as a number. Parsing stays synchronous (no queue). `PATCH` accepts `audience_hint`.
- **E. Workspace reads (I06).** New `lib/adsWorkspaceApi.ts`; no shared type grows.
  - `GET …/campaigns/{c}/workspace` → `{stage: {key: "plan"|"assets"|"launch"|"read"|"decide"|"review", done: string[]}, pending_count|null, daily_budget|null, active_ads, can_support|null, next_sync_at|null, totals: null|{start, end, currency, spend|null, results|null, cost_per_result|null}, draft: null|{cap_set, budget_set, slots_ready, slots_total, launch_checked, launch_total}}`. Stage from one function `app/ads/campaign_stage.py::stage`: draft → launch if the launch is approved, assets if a cap is set, else plan; launched → read when `data_status` is not ready, decide when the campaign has open queue items, else read; closed → review. `totals` = the campaign's last 14 complete days in the org timezone, one window (never the triage 7/14/28 widening). A failed sub-read makes its field null, never 0.
  - `GET …/campaigns/{c}/structure` → `{groups: [{group_id|null, name, daily_budget|null, ads: [{ad_id|null, entity_id|null, name, thumbnail_url|null, grade|null, grade_label|null, cost_per_result|null, results|null, closing, missing_material}]}]}` (app-built: plan groups; imported: platform ad sets). `closing` = an approved pause not yet confirmed.
  - `GET …/campaigns/{c}/timeline` → `{rows: [{change_set_id, title, at, state: "verified"|"platform"|"check"|"rejected"|"draft"|"stale", reason|null, checked, total, version|null}], truncated}` ordered by `created_at DESC, id DESC`; superseded and deferred sets omitted; `state` uses the home `_handoff` rule plus `launch_stale`.
- **F. Assets slots (I10).** `GET …/campaigns/{c}/slots` → `{ready, total, groups: [{group_id|null, name, slots: [{ad_id|null, entity_id|null, name, state: "ready"|"missing"|"in_progress", thumbnail_url|null, confirmed, replace_task_id|null}]}], requests: [{task_id, replaces: {entity_id, name|null, thumbnail_url|null}, created_at, state_label}], requests_truncated}` — a slot is one planned ad (app-built) or one platform ad (imported). `requests` are the open 換掉這一則 tasks only; `state_label` from the task's own state (等素材工作檯／有候選圖／已採用). `POST …/campaigns/{c}/slots/{ad_id}/upload` binds an uploaded user asset to that planned ad (reuses the user-asset placement path).
- **G. Launch (I12).** New types in `lib/adsLaunchApi.ts`.
  - The launch batch contains only planned ads whose material is ready (Unresolved 1); the others stay in the plan, returned as `deferred_ads: [{ad_id, name, group_name}]`, and go out with a later version.
  - `GET …/campaigns/{c}/launch` → `{step: "list"|"platform"|"verify"|"stale", version|null, approved_at|null, summary: {campaigns, groups, ads, daily_total|null, start|null, end|null, cap|null, slots_ready, slots_total}, items: [{id, kind, name, parent_name|null, fields: [{key, label, value}], state: "todo"|"built"|"verified"|"mismatch"|"unknown"|"changed", mismatches: [{key, label, expected, observed|null}], unreadable: [{key, label, confirmed}]}], deferred_ads, read_at|null, settings_readback}` — items of this batch only (no new-ad handoffs).
  - `POST …/launch/readback` reads back every `built` item of the batch in one call, matching each to a platform object by exact name under its expected parent; not found or ambiguous leaves it `built` with a reason.
  - `POST …/launch/items/{id}/unreport` clears a report while the item is not verified.
  - A required field the platform read cannot see (e.g. landing URL) is listed in `unreadable` and confirmed per field through `POST …/launch/items/{id}/confirm {key}`; an item is `verified` when every readable field matches and every unreadable one is confirmed. Mismatch observed values are stored with the check.
- **H. Connections (I14).** `GET …/connections` → `{attention_count, sources: [{key, kind: "ad_account"|"orders"|"product_costs"|"platform", platform|null, name, state: "ok"|"auth_expired"|"failed"|"never"|"missing_days"|"missing_cost"|"unsupported", note, last_success_at|null, missing_days: string[], affected_campaigns: [{id, name}], action: null|{label, href}}], calendar: {month, today, rows: [{source_key, label, days: [{date, state: "ok"|"missing"|"none"|"future"}]}]}}`. One row per bound account per platform from the ads sync state (never a min across accounts); an account never synced is `never`, not ok; auth expiry via the existing auth-error classifier. A day counts `ok` by pull coverage, not by spend rows (a zero-spend day is ok). Orders coverage via the orders facade (`none` before the first import); product costs via the products facade; platforms without a reader are `unsupported`. Dates in the org timezone.

## Unresolved (defaults apply unless the user overrides before dispatch)
1. **Ads without ready material at launch.** Default: they are not in the launch batch; they stay in the plan as 待補 and go out with a later launch version when the material arrives. Reason: the decision lives in the shared core, not the manual adapter, and a future automatic Meta publish cannot create an ad without a creative, so an "empty ad" path would have to be undone then.

## Constraints (all issues)
- Nothing writes to a platform (§6.4); no issue, doc or report asks the user to run real ads.
- Gate commands as `uv run python -m <tool>`; frontend typecheck = `cd frontend && npm run build`. Worker logs go to `%TEMP%/claude/`, never the worktree. Workers run the full `app/tests/test_ads*.py` before reporting (verify does not run the whole suite).
- Frontend files are capped at 800 lines: `lib/adsApi.ts` (775) takes no new code; new types go in new or existing `lib/ads*Api.ts` files. New backend tests are `app/tests/test_ads_*.py`. New capability never lands in legacy; `app/ads` reaches products and orders through their facades.
- A shared frontend type that gains a required field makes its issue edit every test factory that builds it (grep the type name across `frontend/src/**/*.test.tsx`). The contracts above avoid growing `CampaignDetail`, `TriageItem`, `ChangeSet`, `HandoffWorkspace` on purpose.
- `do_not_touch` never uses a wildcard over a sibling of a touch file.
- UI issues follow design-system §1.7: the prototype HTML is the spec, kit pieces only (I03; a missing piece blocks, it is not hand-rolled), real-shaped fixtures, side-by-side at 1024 and 1920, worker self-check. Every read failure shows `ReadFailed` with 重試, never empty data.
- Migrations only if an issue's contract needs a column; its file name is fixed in the issue, and the lead applies it to the dev DB (54322) before merging that issue.
- Docs: issues do not edit docs; the lead's crank closeout reconciles `docs/architecture/ads.md` and `docs/design-system.md` once.

# Acceptance
- A review whose model text contains 「不足以判斷…造成」 is `ready` with its recommendation; one whose text is rejected is `ready` with `rejected`, and direction, copy and completion work; retry creates exactly one new round and the queue follows it.
- A campaign is created from product + objective + dates + a numeric cap with no free text; a reserved objective is refused.
- Stage, 14-day totals, structure grades and timeline states come from the new reads on real-shaped fixtures (draft, gap, live, closed); no field turns a failed read into 0.
- A launch with one ad lacking material freezes only the ready ads, lists the deferred one, and a readback verifies built items without the user picking platform objects; a landing URL confirmed by the user lets the ad set reach verified.
- The connections page shows one row per account with its own last read; an account never synced is not ok; a zero-spend day is not missing.
- Every screen in the table has side-by-side evidence at 1024 and 1920.

# Evidence
- Probe 2026-09-25 (dev DB): the only two `failed` review rounds were rejected for 「不足以判斷／判定…造成變化」 hedges; `submit` dedupes on `UNIQUE(org_id,brand_id,campaign_id,evidence_hash)`, so a failed round can never be retried today.
- Gap checks 2026-09-25 (five read-only agents): the wizard create requires `goal_text` and takes no product ids (`brief.py:208`, `routes.py:162`); product list lacks price/thumbnail; no per-account connection status is exposed (`ads_external_sync_job` holds it); `/spend.last_pull_at` is a min that hides never-synced accounts; launch items stay `unknown` because `landing_url` is required but unreadable (`handoff_check.py:105`); `report` cannot be cleared; handoff `items` mix new-ad handoffs; the workspace stage and 14-day campaign totals do not exist; `change-control` has no tie-break or truncation flag.
- Objective lists: Meta ODAX (知名度, 流量, 互動, 潛在顧客, 應用程式推廣, 銷售業績) — facebook.com/business/help/1438417719786914; Google Ads (Sales, Leads, Website traffic, Product and brand consideration → renamed YouTube reach, views and engagements, Brand awareness and reach, App promotion, Local store visits) — support.google.com/google-ads/answer/7450050.
