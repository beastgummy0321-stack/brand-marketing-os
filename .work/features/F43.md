# Outcome
Everything the owner knows about each **product** is asked once, in a five-step product onboarding (prototype
`.harness/scratch/prototype/f41-onboarding/index.html` routes `#/p1`–`#/p5`, `#/plist`, `#/bundle`, `#/home` product block,
`#/new`; launch config `prototype`, port 8741; user 「可以，切票」 2026-09-30), and a campaign only picks what it sells.
1. **Product = knowledge**: what it is (intro, ingredients/mechanism, difference, product photos, product page URL), 1–3 customer
   groups (who · 1–2 of the six `pain` keys · a customer quote · when used), product proof (`fact_key`), claims 可以講／不能講 with
   食安法 flags.
2. **Sell-way = what a campaign sells**: name, components (product × qty; a cross-product bundle has several), price, list price
   (default Σ component single prices), cost (default Σ), shipping cost, break-even = price − cost − shipping (F05 formula incl.
   close rate for lead/booking), cap per sale (default = break-even), landing URL (default = product page).
3. **Offers derived** from the sell-way too: list price > price → 組合加贈 (qty > 1 or several components) or 折扣 (single);
   combined with F42's brand policies in `available_offer_keys`; the copy guard accepts the sell-way's price sentence.
4. **Planner and strategy read the sell-way's customer groups**; every reader of product knowledge reads all knowledge products of a
   sell-way (a bundle has several).
5. **New campaign** asks only sell-way, goal, dates, budget; platform / audience (customer groups) / cap / landing come from brand +
   sell-way, overridable in 「進階：這期不一樣」 with their source named; copy-from-previous-campaign is removed.
6. **Product surfaces**: 經營概況 top block 「你的商品」, the products page (products + bundles), 新增組合; readiness's product row
   links to 建第一個商品.

# Decisions
User-confirmed (dig + prototype review 2026-09-30; source `docs/backlog/intake-rebuild-discovery.md`, F42 Decisions):
- Product onboarding per product / per bundle, repeatable, prominent block on top of 經營概況; every step AI-prefilled + confirmed;
  every AI-judged block has 自訂.
- The target model above (product = knowledge, sell-way = campaign unit with components; bundle = sell-way with several products).
- One sell-way per campaign.
- The new-campaign page asks only sell-way, goal, dates, budget (supersedes F40's 「新活動預帶上一期」 for platform/audience/cap/landing;
  the F40 period default — the day after the previous campaign's end — stays).
- `intake.md` §8 rule 1 「no bundle auto-arithmetic」 and the 「one level only / no bundles」 limits are superseded.
Agent choices (settled so workers do not invent them):
- **Storage** (extend the stores readers already use, like F05/F38):
  | fact | store |
  |---|---|
  | knowledge product | `product` row, `parent_id` NULL, no components; new `page_url`; new `onboarding_step` (NULL = done, 1–5 = 建到一半; such a product and its sell-ways are not pickable) |
  | intro / mechanism / difference | `product_fact` `core_info` / `mechanism` / `differentiation`, confirmed |
  | product photos | `official_asset` with `product_id` (today's 商品照 path) |
  | customer groups | new table `product_customer_group` (product, position 1–3, who, `pain_keys` 1–2 of the six, quote, when_used, source) |
  | product proof | `product_fact` `proof` + new `product_fact.fact_key` (same CHECKs as `brand_fact`) |
  | claims | `claim` `approved` / `forbidden` with `product_id` |
  | sell-way | `product` row; single-product sell-way keeps `parent_id` = its product and name 「〈商品〉 · 〈賣法〉」 (F05); a bundle has `parent_id` NULL and its own name; new `landing_url` (NULL = first component's `page_url`) |
  | components | new table `product_component` (sell_way_id, product_id, qty > 0); every sell-way has ≥1 row |
  | money | `product_economics` of the sell-way + new `list_price`, `cap_per_sale` (NULL = derived / break-even); bundle cost NULL = Σ components |
  | product prefill | new `intake_product_prefill` (intake-owned; never a confirmed fact) |
  New tables live with `brand_intelligence` (the owner of `product`), written only through the facade — the same exception §3
  records for `learning_ledger`; readers keep going through `app/brand_intelligence/repository.py`. `review: planner` on I01.
- **One resolver each**: `knowledge_product_ids(conn, brand, product_id)` replaces `knowledge_product_id` at its four callers;
  `get_product_economics` returns effective values (derived list price / bundle cost filled, `derived_fields` named) so budget,
  targets, learning and the wizard read one number.
- **Campaign defaults** (brief): platform = the brand's bound channel (plan default, unchanged); `context_json.customer_group_ids`
  = all groups of the sell-way's knowledge products; cap = the sell-way's `cap_per_sale` stored as the campaign's own cap with
  `field_sources.cap = "sell_way"` (NULL → break-even as today); `context_json.landing_url` = sell-way landing; objective = the
  brand's conversion goal. Overrides in the fold write `field_sources = "user"`. `audience_hint` stays readable for old campaigns.
- **Planner wiring**: strategy and delivery-plan prompts get a 【這個賣法的顧客】 section (≤3 groups per knowledge product, ≤6 in all,
  pain keys with labels, quote, when); one department rule each: an ad's `pain` comes from a listed group when groups exist. No
  vocabulary filter on `pain`.
- **Brand-scan products** (F42 prefill) appear on the products page as 「AI 讀到了，還沒確認」 suggestion cards; 「繼續建檔」 creates the
  product then — no row exists before the user acts.
- Lead/booking brands: the sell-way table shows 成交率 (F05 rule 2 unchanged); goods brands do not see it.
- The old product detail page (`/brands/:b/products/:p`) stays reachable and unchanged; its entry points move to product onboarding.
- 食安法 flags on product claims come from `app.workbench.validate_claims` (public entry); the ARCHITECTURE manifest's
  `intake.may_depend_on` gained `workbench` at carve for this one call (planner review on F43-I05; closeout adds the §2 sentence).
Unresolved (for the user, before this feature is authorized):

  products)? Recommend yes, as a follow-up cleanup issue; not in this plan.
- Brand-level 人物誌 (personas) vs product customer groups: keep both, or retire personas? Recommend keep until a drill shows overlap.
