# Outcome
Every screen and control of `docs/design/ads/prototype-v7-ads-center.html` (with `prototype-v8-active-only.html` superseding it where it changes the same parts) works on real data — no grey 「接上後開放」 placeholder left in the ads centre except Google Ads, and no control that only toasts. Plus problems 2 and 3 of the 2026-09-22 audit.
# Decisions
- User-confirmed 2026-09-22 (all "照建議"): ladder thresholds; angle candidates by AI + 自訂; capacity = 每日預算 ÷（目標成本 × 2）, cleanup pauses the lowest 7-day spend; recovery banner on a > 2 h worker gap; 換一張圖／用現成素材 both go workbench/upload → pick → new-ad change set (old ad paused only after the new one is verified live); ladder continues across the replacement lineage; the prepare page recommends by ladder unless AI says observe; learning promotion 1 = 觀察到 (observed), 2 = 可能成立 (likely), ≥ 3 = 成立 (validated); verify timeline cells are real (spend stopped next day, delivery started, auto re-review +3 d budget / +7 d copy and new ad); objective-derived campaign chips (銷售 購 / 互動 互 / 流量 流 / other = first character); multi-item cleanup sets render in the three flow pages; dynamic-creative copy is SUPPORTED as a set of variants; queue auto refresh daily; Google Ads NOT built; audit problem 1 (queue row width at 1280–1700) deferred. The user wants no pause until done, then merge to main, then a final closed-loop test.
- Assumptions the lead took (reversible, from the prototype): real thumbnails in queue rows and confirm cards; campaign card chips 「每日 X」 and 「約撐得起 N 則」; the 「最近同步・N 項待處理」 chip moves to the global top bar; non-sales review pages show 「這條素材的紀錄」 instead of the commerce card; monthly review uses the calendar month; 採用 goes to the item's action, 略過 hides it for that month; recovery banner steps are derived from real records and queue buttons read 「補完資料後更新」 while recovering; the wait page shows 「Meta 讀取權限失效」 when the sync error is an auth error.

## Contracts (backend → frontend; every issue implements exactly these names)
- A. Ladder and history (triage item of every ACTIVE ad): `ladder: {step: 0|1|2, copy_changes: int, image_changes: int, lineage_from: string|null}`; `history: [{change_set_id, kind: "copy"|"new_ad"|"budget"|"pause", approved_at, verified_at|null, cost_before|null, cost_after|null}]` (≤ 10, newest first; this ad and its lineage predecessors). copy_changes = confirmed `copy` items on this ad or its lineage; image_changes = confirmed `new_ad` items whose `replaces_entity_id` is in this ad's lineage; step = 2 if image_changes ≥ 1 else 1 if copy_changes ≥ 1 else 0; lineage_from = the ad this ad replaced (a confirmed new_ad item bound to this ad whose set carries `replaces_entity_id`). cost_before/after = cost per result over the 7 days before approved_at / after verified_at (null when fewer than 7 known days).
- B. Copy variants: the Meta adapter writes `creative.fields.copy_variants = {titles: string[], bodies: string[]}` for dynamic creatives (from `asset_feed_spec`). A `copy` change item on a dynamic ad takes `after: {titles: [...], bodies: [...]}` (1–10 each, non-empty strings ≤ 10000); image/video ads keep `{title?, body?}`; carousel stays refused. Review GET `evidence_json.conditions.copy_editable = {ok: bool, mode: "single"|"variants"|null, reason: string|null}` computed at read time. Verify compares variant sets order-insensitively; the handoff snapshot lists every variant.
- C. Angles: `GET /api/ads/brands/{b}/campaigns/{c}/entities/{e}/angles` → `{status: "pending"|"ready"|"failed", candidates: string[], error: string|null}`; the first GET enqueues one background LLM task through the existing gateway (review_jobs pattern), cached per (entity, copy hash); input = only this ad's own copy text and the brand name; output = exactly 3 phrases ≤ 12 characters, schema-validated. A `pause` change item may carry `angle: string` (≤ 40 chars, free text allowed), part of the content hash.
- D. Learnings: when a pause item with `angle` reaches `confirmed`, write ONE learning (idempotent per item) via the existing `brand_intelligence.repository.record_learning`: text 「「<angle>」對這群受眾無效」, confidence by promotion (count of earlier ads learnings of the brand with the same text: 0 → observed, 1 → likely, ≥ 2 → validated), source_cycle_id = change set id, source_track "ads". The set item view gains `learning: {recorded: bool, confidence: string|null, count: int}`. `GET /api/ads/brands/{b}/learnings` → `{learnings: [{id, text, confidence, count, campaign_id|null, campaign_name|null, learned_at}]}` (ads track, newest first, ≤ 50).
- E. Replacement: `POST …/new-ad-handoffs` accepts optional `replaces_entity_id` (an ACTIVE ad of the same campaign) stored in plan_json; the set view exposes `replaces: {entity_id, name}|null` and, once the new_ad item is `confirmed`, `follow_up: {kind: "pause_old", entity_id}` unless a non-superseded pause set for that entity exists.
- F. Capacity and cleanup: per campaign `capacity = {daily_budget|null, currency|null, target|null, can_support|null, active_ads}`; daily_budget = sum of the ACTIVE daily budget owners' `budget_amount` (one currency, else null; owner lookup as `triage_scale`); can_support = floor(daily_budget / (target × 2)) when both known and target > 0. Exposed on the triage response and on campaign cards (`data.capacity`). Cleanup rule: can_support ≥ 1 and active_ads > can_support → propose pausing the (active_ads − can_support) active ads with the lowest 7-day spend, excluding ads that have a stop_loss row; queue kind `cleanup` (category `ads_triage_cleanup`, informational, label 「廣告清理待決定」, dedupe `ads-triage:cleanup:<campaign>:<window_end>`), payload `cleanup: {campaign_id, campaign_name, can_support, active_ads, ads: [{entity_id, name, thumbnail_url, spend_7d}]}`; proposal = the newest non-superseded pause set with `plan_json.source == "cleanup"` for that campaign (kind "cleanup", same shape as the pause proposal, `multi: true`).
- G. Month summary: `GET /api/ads/brands/{b}/month-summary?month=YYYY-MM` → `{month, currency|null, total_spend|null, campaigns: [{campaign_id, name, objective, spend|null, result_count|null, result_label, cost_per_result|null, target|null, verdict: "met"|"missed"|"unjudged"}], orders: {this_net, this_count, previous_net, previous_count, change_pct}|null, closed_this_month: int|null, closed_tracking_since: date|null, suggestions: [{key, kind: "refresh"|"cleanup"|"no_target", campaign_id, campaign_name, objective, title, why, action_url}]}`. Spend/results = calendar-month sums of `ads_external_daily` over ALL the campaign's ads (active and closed), one currency else null; verdict met if cost ≤ target, missed if >, unjudged if either unknown. Orders via the existing public `app.orders.commerce_evidence.review_evidence` for the two calendar months (no new capability in the legacy module). closed_this_month counts ads whose `status_changed_at` falls in the month and whose status is closed; null for months before tracking started (`closed_tracking_since`). Suggestions: refresh rows → 「補 N 則新素材」, cleanup rows → 「清掉 N 則沒被投放的廣告」, active campaigns without a target → 「替「X」設目標」; `POST …/month-summary/suggestions/{key}/dismiss?month=` stores the key in `ads_campaign.context_json.month_dismissed[month]`; dismissed keys are excluded.
- H. Timeline: every change item view gains `timeline: {spend_stopped: bool|null, delivery_started: bool|null, next_review_at: date|null}` — pause: spend_stopped = the first full day after verified_at has synced spend 0 (null until that day is synced); copy/new_ad: delivery_started = impressions > 0 on any day after verified_at; next_review_at = the review monitor's scheduled date for the entity. Approving a budget set schedules the existing review monitor at approved + 3 days; copy and new_ad at + 7 days.
- I. Refresh, auth, status: a daily periodic job (after the 05:00 sync) runs `refresh_queue` for every brand; the campaign `data.sync.state` gains `"auth_expired"` when the failing section's error code is an auth error per an adapter function `is_auth_error(platform, code)` (Meta 190 / 102 / 463 / 467); `GET /api/ads/brands/{b}/status-summary` → `{last_success_at|null (newest among campaigns in state ok), failing_campaigns: int, open_items: int (open ads_triage_* rows)}`.
- J. Runtime records (one migration, ads-owned): table `ads_runtime_event(kind text, brand_id text null, at timestamptz)` (+ index, 48 h prune) — kinds `beat` (written every minute by the existing per-minute ads periodic task) and `queue_refresh` (written by refresh_queue); column `ads_external_entity.status_changed_at timestamptz` set by `upsert_entity` whenever the active/closed category of `native_status` changes (`ad_status.is_closed`).
- K. Recovery: `GET /api/ads/brands/{b}/recovery` → `{recovering: bool, gap: {start, end, minutes}|null, steps: [{key, label, state: "done"|"active"|"todo"}]}`; a gap = two consecutive beats > 120 minutes apart; recovering while such a gap ended in the last 24 h and a step is not done; steps in order 重新連線 (a beat after the gap), 確認讀取權限 (no campaign disconnected / auth_expired), 補 N 小時的資料 (every sync job of the brand has last_success_at > gap.end), 重新判斷廣告 (a queue_refresh event after gap.end), 核對你回報的操作 (every reported-but-not-final item was checked after gap.end); the first not-done step is "active".

## Pre-dispatch corrections (2026-09-22 challenge, 274 s; AUTHORITATIVE — they override the contract text above where they differ)
1. H: nothing is scheduled at approve (the review monitor only takes ads, only "now", and would trigger paid LLM rounds). `next_review_at` is computed at read time: budget = approved_at + 3 days, copy/new_ad = verified_at + 7 days (null until verified). On that date the daily queue refresh re-judges the ad with post-change data — that is the 「自動重看」. `spend_stopped` = true when the first full day after verified_at is inside the campaign's synced coverage (`triage._coverage`) and has no row or spend 0; false when spend > 0; null while not covered.
2. I: raw Meta codes never reach `app/ads` (`app/meta/repository.py:871-873` stores `permission_denied`); `auth_expired` = a failing section whose stored error_code is `permission_denied` (the adapter function maps stored codes, not numbers). Add `auth_expired` to `triage._SYNC_STATES_RAISING_INSUFFICIENT`.
3. J: `ads_runtime_event` gets a nullable `org_id` (null for beats), the same GRANT and RLS policy pattern as the other ads tables (`org_id IS NULL OR org_id = <claim>`); `queue_refresh` rows carry org_id and brand_id.
4. F: `daily_budget` is null when ANY active ad has no daily budget owner; cleanup never proposes an ad whose 7-day window is not fully covered or an ad in an open replacement lineage (new ad not yet verified, or old ad awaiting its follow-up pause); while a campaign has an open cleanup row its refresh_creative row is not raised (cleanup first).
5. E / I14: the material task and the new-ad handoff carry the review link ONLY when the round has a `new_test` recommendation (`handoff_new_ad._review` requires it); otherwise only `replaces_entity_id` is sent.
6. G: month sums read only `metric_scope = 'ad'` rows and exclude the monthly-budget rows (`meta_read.py:525-538`); the summary adds `days_covered` and `days_elapsed` for the month; the orders comparison is like-for-like — this month so far vs the same number of days of the previous month (`change_pct` null when either side is unknown); the dismiss write uses `jsonb_set` on `context_json`.
7. B: `copy_editable.ok = false` (reason 「商品目錄素材沒有可改的文字」) for dynamic creatives with only `product_set_id`; titles and bodies may each be 0–5 items (Meta's per-type maximum), at least one non-empty item overall; the handoff states 「只改文字，圖片與影片不動」; `build_item`'s key whitelist also allows `angle` (contract C).
8. D: call the learning write AFTER `check` commits (`record_learning` commits by itself); idempotency by an existing learning whose `source_cycle_id` = the change ITEM id (not the set id); automatic runtime re-checks must not duplicate.
9. C: the e2e scripted provider does not know the new task type — angles read `failed` there and the page falls back to 「＋ 自訂」 (acceptable); one LLM call per ad per copy hash, started when a pause confirm page opens.
12. J/K (after F27-I00 merged): correction 3 was wrong — the tenant isolation gates require NOT NULL org_id and brand_id on every table; F27-I24 makes `ads_runtime_event` fully tenant-scoped (one beat per active brand per minute) and K reads the brand's own beats.
10. K step 3 is judged per sync SECTION from `context_json.external_sync` (a section's own last_success_at > gap.end), not from the job-level last_success_at.
11. A: count by the item kind in `plan_json` (not `ads_action.kind`); lineage through `ads_handoff_item.entity_id` where `action_id` = the new_ad item id; an ad's history lists only items that target that ad (copy, pause, the new_ad that replaced it) — budget items target owners and are not listed.
