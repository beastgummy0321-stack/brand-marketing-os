# Outcome

素材工作檯 is rebuilt as four screens over one information model — 任務包 → 素材組 → 產物 → 版本.
A pack arrives from an upstream module (檔期規劃 today) or from 自由創作, both through the same
handoff contract and the same workspace. The user sees what is left to do on the 入口, opens a pack
to see per-set progress, opens a set to generate and 選定 versions, and 核准整包 when the pack is
done — which the upstream reads as 「可以下一步」 without ever being blocked by it. The old
`.workspace-split` workbench page is retired.

## What is settled here so no issue re-invents it

- **Model and states**: `ARCHITECTURE.md` §5.1–§5.3. A version is one row; a copy round writes 5
  rows, an image-prompt round writes 1 (the ①＋② pair), a script round one per script. Rounds are
  history — newest first, no round switcher.
- **Handoff contract**: `ARCHITECTURE.md` §5.4. 檔期規劃 sends one pack per tree, one set per
  deepest node, `required_outputs = {"copy": 1, "image_prompt": 1}`, `constraints.copy_length` from
  the node, `constraints.promotion_note` from the period. `submit_brief` stops being public.
- **Approval signal**: `ARCHITECTURE.md` §5.5. State read (`pack_for_source`), never a callback —
  the workbench must not import `app.schedule`. 檔期規劃's 核准 button keeps working with a
  skippable warning; the schedule page redesign itself is out of scope.
- **`adopted_output` keeps its meaning and its shape**: the earliest selected version of that part,
  else the latest version, plus `is_adopted`. Multi-select does not change what the schedule reads;
  no new read for 「all selected versions」 until something needs it.
- **A version row carries the whole round's body** (settled at F02-I02 review, 2026-09-12). A copy
  round writes 5 rows that share one `body_json` — the entire reply including all 5 `sets` — and
  differ only by `version_index`; a `video_script` round does the same, one row per script. Reason:
  `schedule/state.py::_copy_summary` reads `adopted_output(...)["body_json"]["sets"]` and must still
  see all 5 (§5.6, and `state.py` is not edited in this feature). **The reader slices**: version
  *i* of a copy product is `body_json["sets"][i-1]`, done once in the API (`SetDetail.products
  [copy].versions[].body`), never in the browser. Same rule for `video_script` over `scripts`.
- **Dispatch follows `required_outputs`' keys** (settled at F02-I02 review). `submit_pack` derives
  `request["parts"]` from `required_outputs.keys()`, so one 檔期規劃 handoff fires one copy job and
  one image-prompt job per set at expansion time — §5.8 already allows an image prompt to run before
  any copy is selected, and §5.4 has the upstream sending the per-type generation counts, so the
  upstream must supply one. 檔期規劃 supplies `image_prompt_count` by §5.7's rule (`format` =
  彈性格式 → 10, otherwise 3) — the same numbers the retired `BriefDetail.tsx:244` prefilled; the
  studio's `POST …/products/image_prompt/run {count}` is where the user overrides it with a new
  round. This is not an editable-N regression: rounds are history and the first round is a draft.
- **The pack row's `summary_json`/`constraints_json` are partial by design.** 檔期規劃 fills 情境
  (the chosen plan's summary) and 重點訊息 (`promotion_note`); 角度／風格／目標受眾 are per-node
  coordinates and live on the set, not on the pack, so they stay empty for a dispatched pack.
  `constraints` that differ per node (`copy_length`) ride in the set's `request`;
  `workbench_pack.constraints_json` is pack-wide defaults and may be `{}`. F02-I03 renders the 摘要
  keys that are present, in §5.4's order, and omits the empty ones — it does not print a placeholder
  and does not go looking for a second source.
- **Copy contract**: `ARCHITECTURE.md` §5.6. `_copy_summary` keeps emitting index-aligned
  `bodies`／`headlines`／`descriptions`, so `CreativePackList.tsx` and the 素材準備 stage do not
  change in this feature.
- **API surface** (`/api/workbench`, brand-scoped, `require_actor` → `require_brand` → one
  repository call → wrap, exactly as `routes.py` does today). The brief-shaped endpoints are
  replaced, not kept in parallel; `GET /styles` stays:
  - `GET  /brands/{b}/packs?status=&q=&sort=` → `{packs: [PackCard]}`
  - `POST /brands/{b}/packs` → `{pack}` — 自由創作 only (`source_kind` forced to `free_job`);
    server names it 自由工作 #n
  - `GET  /brands/{b}/packs/{p}` → `{pack: PackDetail}`
  - `POST /brands/{b}/packs/{p}/completion` `{key, checked}` → `{pack}`
  - `POST /brands/{b}/packs/{p}/approve` → `{pack}`; 409 when a check is neither green nor ticked
  - `POST /brands/{b}/packs/{p}/close` → `{pack}`
  - `POST /brands/{b}/parse` `{free_text, defaults}` → `{parse: {parsed, note, spec}}` — 自由創作's
    one model call (F02-I06)
  - `GET  /brands/{b}/sets/{s}` → `{set: SetDetail}`
  - `POST /brands/{b}/sets/{s}/products/{part}/run` `{count}` → `{set}`
  - `POST /brands/{b}/sets/{s}/versions/{v}/select` and `DELETE` the same path → `{set}`
  PackCard carries what image 1 draws (source, status, name, subtitle, sets_done/sets_total, pct,
  next_step, counts per required type, updated_at); PackDetail adds meta strip, 摘要, 完成條件 and
  the set rows with their cells; SetDetail carries the sibling rail, the chips, the required parts
  in dispatch order, each product's versions and 生成設定, and `image_generation.connected: false`.
- **The derived strings and numbers the API ships** (settled at the F02-I03 review, 2026-09-12 —
  the frontend renders them, never recomputes them):
  - **入口 tile = 版本, not 素材組.** `counts[]` is one entry per 產物類型 any set of the pack
    requires; `required` = **Σ `required_outputs[type]` over those sets** (how many versions must be
    選定 in the whole pack) and `selected` = **Σ selected versions of that type**. Same unit as
    §5.3's cell (`已選定／需要`), so the 入口 tile and the 素材組進度 rows can never disagree, and a
    自由創作 pack asking for 「五張」 reads 0／5 — not 0／1. A per-set count would collide with
    `cells[].required`, which is versions.
  - `subtitle` = `summary.情境` (`""` when the upstream did not fill it — no placeholder).
  - `next_step.label` = `文案／圖片／腳本` ＋ `待生成` (no version) or `待選定` (versions, not enough
    selected); `set_name` ships separately and the screen joins them (image 1: 主力 C・圖片待選定).
  - `image_generation.reason` is one literal, owned by the API:
    「圖片生成服務未接上，這裡先保留席位；接上後同一個畫面直接顯示成果。」 F02-I05 moves it behind
    `image_port.py` unchanged; §5.11 — never a refusal.
  - `POST /packs` answers **201**; every other pack/set endpoint answers 200.
- **關閉任務包 means it leaves the 入口.** `POST …/packs/{p}/close` stamps `closed_at`, and
  `GET /packs` omits packs with a `closed_at` (no status pill for 已關閉, no extra state in §5.3).
  `GET /packs/{p}` still renders a closed pack, so an existing link never 404s. Without this the ⋯
  menu's only item does nothing the user can see.
- **`pack_for_source` returns `state`, not `status`.** Its result is the `workbench_pack` row plus
  `sets_total`／`sets_done`／`state`, where `state` is §5.3's Chinese word (待處理／進行中／待核准／
  已完成) — the English `pending|running|awaiting_approval|done` enum exists only inside
  `/api/workbench`'s own PackCard. F02-I04 passes `state` through as it is; it may not import
  `app.workbench.repository` to translate it.
- **`required_outputs` ≠ 產出數量.** `required_outputs[type]` is **how many versions must be 選定**
  before the product counts as 已完成 (§5.3); 產出數量 / `count` is **how many versions one
  generation round writes**; they are two fields and one never silently stands in for the other.
  檔期規劃 sends `{"copy": 1, "image_prompt": 1}` — one node is one ad. **自由創作 takes them from
  the parse: `required_outputs[type]` = the count the user asked for (「五張」 → 5), default 1 per
  requested type when no count was said, and the round's generation count is the same number** so
  one round can satisfy the pack (user ruling, 2026-09-12).
- **The `free` part is retired from new packs.** `free` exists today as a part name
  (`repository._PART_NAMES`, `jobs._METHODOLOGY_LABELS`, `app/departments/workbench/free.md`) and
  F02 also needs the word for 自由創作's origin. Ruling: (a) the pack column value is
  **`free_job`**, not `free`, so the two never collide; (b) `submit_pack` rejects `free` in any
  `required_outputs` — new packs only ask for `copy`／`image_prompt`／`video_script`; (c) the
  existing `free` code path and `free.md` are left alone for legacy rows (those briefs have no
  `pack_id`, so no new screen ever renders them) — deleting them is not this feature's job.
  Part labels are one map in the API, `copy`→文案, `image_prompt`→圖片, `video_script`→腳本.
- **The 生成設定 table's shape, settled at the F02-I09 block (2026-09-12)**: `ARCHITECTURE.md`
  §5.13. `SetDetail` gains a top-level `generation_settings`: an ordered list of `{label, text}`,
  always seven rows — 品牌／商品 (`<brand name> · <product name>`, 商品 half 「不指定」 when the set
  has no `product_id`), 平台, 尺寸, 風格 (the same values as `chips`), 人物, 場景 (the latest
  image-prompt round's structured reply `body_json["hero"]["person"]／["scene"]` — the model's own
  fields per §5.8, **not** `rendered.hero`, which is the assembled prompt string; 探索模式 has no
  `hero`, so 「—」), 主要訊息 (the pack summary's 重點訊息, its non-empty lines joined with 「；」).
  Empty ⇒ 「—」, never a placeholder and never a missing row. F02-I12 derives it in
  `app/workbench/repository.py::set_detail`; F02-I09 renders it verbatim and holds no map from
  label to source. This is a read-only mirror of what produced the current prompts, not an input
  form: 精準控制's 人物／場景 stay a form concern (F02-I09's 修改需求), and no second endpoint fetch
  is ever added to fill this table. `products[<part>].generation_settings` keeps its existing
  meaning (per-product run parameters) — same word, different field, different shape.

- **Text the user reads is produced once, by the side that owns the rule.** The set-table cell
  (`已選定／需要`／`未生成`／`—`) and the reserved-seat line 席位保留 are **derived in the backend and
  shipped as text** (`cells[].text`, `image_generation.reason`); the frontend renders the string it
  was given and contains no copy of either rule. Frontend verify greps assert the literal is
  **absent** from the TSX; that the user really sees it is F02-I11's e2e.
- **e2e asserts only what runs with no worker and no provider key** (settled at the F02-I11 block,
  2026-09-12). `POST /packs` and `POST …/products/{part}/run` only enqueue
  `background.workbench_generate`; the only thing that runs procrastinate jobs is the separate
  `python -m app.worker` process (`app/worker.py`), and neither `frontend/playwright.config.ts`'s
  `webServer` nor `.github/workflows/ci.yml` starts one. So during `npm run e2e` **no
  `workbench_output` row is ever written** and the 圖片 tab shows the 還沒有生成過 empty state.
  Rejected: starting a worker in the e2e `webServer` — the job body is an LLM call and CI's 8720
  backend has no provider key, so the round would fail instead of writing versions; the only
  env-selectable provider today is `codex_cli` (local, paid in quota, non-deterministic) and
  `FakeProvider` is a Python-level injection, not an env switch. Rejected: seeding a version row —
  nothing outside the job writes `workbench_output`, so it would take a test-only route or SQL
  fixture the e2e has no access to. Ruling: **the pack/set walk stays in e2e** (the fresh free-job
  pack's cells really are deterministic: `_cell()` emits all three parts, so a pack that requires
  only 圖片 renders 未生成 for 圖片 and 「—」 for 文案 and 腳本 in the same table), and the two
  version-dependent claims — prompt cards render from `versions[].prompt_cards`, and the 席位保留
  line the API owns is rendered, not re-spelt — are proven by a component test over a `SetDetail`
  payload (F02-I13), against the backend half that already asserts the payload
  (`app/tests/test_workbench_image_port.py` asserts both `prompt_cards` and the exact
  `image_generation` dict). Nothing here waits on an image API or costs anything in CI.

- **No fake adapter, backend first.** The queue runs one issue at a time, so the cheapest order is
  contract → endpoints → screens; a fake frontend adapter would only buy parallelism we cannot
  spend, and would then have to be removed. The frontend issues start once the endpoints exist
  (F02-I03); `workbenchApi.ts` is rewritten in F02-I07 together with the first screen, so the
  retired page keeps compiling until the issue that deletes it. `LENGTH_HINTS`／`LENGTH_LABELS`
  **stay in `workbenchApi.ts`** — `components/schedule/CreativePackList.tsx:6` imports them and
  that file does not change in this feature (§5.6), so the rewrite deletes the brief-shaped
  functions and types around them, not those two constants.
- **The four screen issues are a chain, not a fan-out.** F02-I07 → I08 → I09 → I10 all edit
  `App.tsx`, `workbenchApi.ts` and `components/workbench/**`; each adds only its own route, its own
  types and its own components. Parallelising them would buy nothing (the queue runs one at a time)
  and cost three merge conflicts in the same three files.
- **自由創作's 「AI 解析結果」 is a real model call** (user ruling, 2026-09-12, replacing the
  browser-local scan): **exactly one** `gateway.run_task` when the user presses 「建立自由工作」,
  none while typing. It goes through the existing provider path (`codex_cli` locally, the same
  abstraction `app/workbench/jobs.py` uses) with an **empty context** — this is shape extraction,
  not brand voice. The prompt is a **department task file** `app/departments/workbench/free_parse.md`,
  the same precedent as the copy contract, so `app/methodology/**` is still untouched by this
  feature. The endpoint is `POST /api/workbench/brands/{b}/parse` (F02-I06) and it returns
  `{parsed, note, spec}`; **a failed, timed-out or unparseable call is never a dead end** — it
  returns the caller's own defaults with `parsed: false` and the flow continues, which is also why
  CI (whose e2e backend has no provider key) can run the walk without spending anything.
- **The parse `spec` keys, settled at the F02-I06 review (2026-09-12)**: `topic`, `outputs`
  (`[{part, count}]`, `part` ∈ copy／image_prompt／video_script, `count` 1..30), `style_hint`,
  `platform`, `size`, `audience`, `key_message` — exactly §5's 「AI 解析結果」 table rows, `null`
  for anything the user did not say. **The `defaults` the frontend sends use these same seven
  keys** (the backend merges the model's non-null fields over them, key by key), and F02-I10's
  mapping to `POST /packs` renames the two that differ: `spec.style_hint` → `style_key`
  (already validated against `image_styles.json`, so it is either a real key or `null`),
  `spec.outputs[].count` → `required_outputs[part]` and the round's `count`. 精準控制's 人物／場景
  have no `spec` field — the form owns them and the parse never touches them.
- **One click = one `llm_task` row**: the parse call passes `max_retries=0`, so a timeout costs one
  row and one wait, not two — the gateway's default retry exists for background workers, and this
  is a person watching a spinner. The only failure that still reaches the browser as an error is
  `SpendCapExceededError` (raised before any row is written, app-wide behaviour for every AI route
  today); it is not one of 「a failed parse is not a dead end」's cases and F02-I10 does not special-case it.
- **Frontend shell**: reuse `AppShell`, `Topbar`, `Sidebar`, `Breadcrumb`, `PageHeader`,
  `EmptyState`, `CopyIconButton`, `ui/badge`, `ui/button`, `ui/tabs`, `ui/dialog`,
  `ui/dropdown-menu`, `ui/sheet`, `ui/input`, `ui/textarea`, `Skeleton` and the existing tokens.
  The pack rail and the set rail are **pack-local/set-local**, not the OS sidebar and not a new
  shared kit component. No new npm dependency is expected; anything else uses what is installed.
- **Routes** (`frontend/src/App.tsx`, path-based, `basename="/app"`):
  `/brands/:brandId/workbench`, `…/workbench/new`, `…/workbench/packs/:packId`,
  `…/workbench/packs/:packId/sets/:setId`.
- **`app/methodology/**` is not edited in this feature.** The image-prompt decisions (§5.7–§5.10)
  are unchanged, and the new copy contract lives in the department task file
  `app/departments/workbench/copy.md`, not in the shared prompt corpus. An issue that finds it must
  change a methodology file stops and reports — those edits move every task that reads them and
  carry `review: planner` of their own.
- **Gates** are `CLAUDE.md`'s: `uv run ruff check app`, `uv run python -m pyright`, the affected
  test files, `cd frontend && npx tsc -b --noEmit && npm run depcruise && npm run build`,
