# Outcome
The home queue's two placeholder rows become real: 「▲ 可加預算」 rows generated by the program from triage (`kinds_pending` → `kinds_available`) that lead into the F22 three-step flow with a `budget` change set (confirm → handoff → verify), and 「＋ 補素材」 rows that lead to the existing material workbench. Every open queue row now participates in 「下一件」 (the linear chain across kinds). The stop-loss row's button reads 「看提議」 as the prototype.
# Decisions
- User instruction 2026-09-22: land the two remaining queue kinds 100%. Plan shown once; the two program rules below are agent proposals challenged against the backend before dispatch — the user approves them with the plan.
- Rule A — scale_budget (per budget owner, i.e. the `ads_external_entity` that carries `budget_type == "daily"` and a non-null `budget_amount`: an adset, or the campaign when the campaign holds the budget): consider only the owner's ACTIVE ads (`native_status` not in {PAUSED, DELETED, ARCHIVED}; a paused ad from the stop-loss flow must not block the owner forever); every active ad must be classified `better` or `flat` (any other class — stop_loss, worse, insufficient of any reason, no_target, needs_resync — means no row); at least ONE active ad; NO pooling across ads (their `window.days` differ, `triage.py:298-320`): each active ad's own `current.cost_per_result ≤ target` AND `previous.cost_per_result ≤ target` (both are known for better/flat, `triage.py:325-339`) — that is 「穩定 2 個觀察期」; a `better` ad is NOT required (a long-stable all-flat owner qualifies); the campaign has a target. Proposal: `to = ceil(from × 1.2)` in the owner's currency; the row is raised only when `month_budget.view(conn, org, brand, month, additional=[the proposed budget item])` returns `available` not null and `≥ 0` — the SAME path `preflight` uses at approve (`month_budget.py:466-470`), so the row and the approval never disagree; `extra_needed` = the difference of `reserved_increases` between the view with and without the item. `amount === null` → no row. Category `ads_triage_scale_budget` (severity `informational`, label 「可加預算待決定」), dedupe key `ads-triage:scale_budget:<owner_id>:<window_end>`, same supersede rule as §6.18.
- Rule B — refresh_creative (per campaign with a target): skip the campaign when ANY ad is `needs_resync` (a data gap is not a creative shortage — the 資料不足 card owns that); `readable` = ACTIVE ads classified `better|flat|worse`; raise a row when `readable ≤ 2` and the campaign has ≥ 3 active ads with any classification. Category `ads_triage_refresh_creative` (informational, 「素材待補待決定」), dedupe key `ads-triage:refresh_creative:<campaign_id>:<window_end>`. No change set; the row's button goes to the workbench.
- Queue payload (I01): rows gain `kind_key: "stop_loss"|"worse"|"scale_budget"|"refresh_creative"`; scale rows carry `scale: {owner: {id, name, native_kind, native_id, ads_count, currency}, from, to, cost_per_result, previous_cost_per_result, target, window_days, month: {available, extra_needed}}` and `triage` = the owner's best `better` ad item; refresh rows carry `refresh: {campaign_id, campaign_name, readable_count, classified_count, thumbnails: string|null[] (≤4)}` and `triage` = the first readable ad's item, else the first classified ad's item (never null: rule B requires ≥ 3 classified ads). `proposal` for scale rows = the newest non-superseded change set whose items include `kind == "budget"` targeting the owner (same shape as the pause proposal, `kind:"budget"`); `null` for refresh rows. `kinds_available` becomes all four; `kinds_pending` = [].
- Home rows (I02, `home/QueueRow.tsx`, prototype `row()`): stop_loss → KindMark stop, button 「看提議」 (was 去處理); scale → KindMark up, title = owner name, meter = cost vs target (success), button 「看提議」 → `propose/budget/:ownerId`, later steps by `proposalAction` (budget branch = the pause branch on a budget set); refresh → KindMark fresh (add the `fresh` variant to `KindMark`: `bg-secondary text-secondary-foreground`, mark ＋), title 「能判讀的素材只剩 N 則」, tiles from `refresh.thumbnails` + hollow tiles up to 4, button 「準備新素材」 → `/brands/:brandId/ads/campaigns/:campaignId?tab=assets&material_new=1` (the same target `ReviewPanel` uses); refresh rows never count as done and are last in order. The header count counts scale rows like pause rows and refresh rows as open. `home/status.ts::isQueueItemDone` / `proposalAction` gain the two kinds; detail-page 「去處理」 unchanged.
- Confirm page budget propose mode (I03, `flow/ConfirmPage.tsx`, prototype `confirmPage()` budget branch): route `propose/budget/:entityId` reads the scale row by `scale.owner.id`; card = 💰 tile, KindMark up, 「<owner name>・同組 N 則一起受影響」, 每日預算 from → to + Chip ok 「+20%」; three columns: meter cost vs target with captions, 「主力穩定 2 個觀察期」 with the best ad's thumb, 「加碼後等 3–5 天再看」; second card 「本月預算放得下」 = the existing month budget bar with the extra segment (`getMonthlyBudget`, `extra = to − from × remaining days` from `scale.month.extra_needed`). Lazy create `{kind:"budget", target_id: owner.id, after:{daily_amount: to}, reason: "近兩期成本都在目標內，加碼 20% 擴量"}`, `operation_id = triage-budget:<ownerId>:<uuid>`; approve → handoff (budget rows already exist) → verify (budget already exists). 拒絕／暫緩 sheet as pause. When entered by `:setId` the page renders from the set (already works).
- 「下一件」 (I03): `flow/changeFlow.ts::nextOpenQueueItem(queue, currentEntityId)` = the first row with `!isQueueItemDone(row)` whose entity/owner is not the current one, in queue order, mapped through `proposalAction` (any kind, including review rows and refresh rows); ConfirmPage closed-state and VerifyPage both use it (VerifyPage already does — align to the helper).
- Meta adapter fix inside I01 (the month-budget gate is otherwise closed for every ABO campaign — `month_budget.py:151-161` delegates to child budgets only when the campaign row has `budget_type None` + `budget_raw.owner == "children_verified"`, and `meta_read.py:122-128` never writes that): in `meta_read.py`, a `campaign` object whose raw payload carries neither `daily_budget` nor `lifetime_budget` is, by Meta's own API semantics, an ad-set-budget (ABO) campaign → write `budget_type=None`, `budget_amount=None`, `budget_raw.owner="children_verified"`; ad sets keep today's behaviour. Platform knowledge stays in the adapter; shared core unchanged. Also `_inventory` requires a successful month sync within 24 h — outside that the row simply does not appear (honest).
- Gaps kept honest: the 「這則主打什麼？」 tags stay a ReservedSlotCard; `lifetime` budget owners never get a scale row (rule A requires daily); nothing is summed across ads or currencies; items do not carry `parent_native_id`, so I01 reads the ad→owner mapping from `ads_external_entity` in one brand-wide query.
- Lead work before dispatch: `KindMark` `fresh` variant + `ui-evidence.cjs` mapping; references `.harness/scratch/F25/ref/` (home rows, confirm-budget via `--hash q/scale/confirm`, handoff-budget, verify-budget).
- Constraints: as F24 (typecheck = `npm run build`; worktrees need `.env` + `frontend/.env` copied; uvicorn via `uv run python -m uvicorn`; kill only your own server by PID/port — never by image name; ports 8731＋issue; docs before `integrate`). Nothing writes to a platform.
- Pre-dispatch challenge 2026-09-22 (228 s, read-only): seven corrections folded in above (ABO delegation, no pooling, paused ads excluded, all-active-ads rule, refresh skips needs_resync, month check via the preflight path, parent mapping query); product choice taken: a `better` ad is not required. Sound: budget units are currency amounts end to end; `verify.check` compares `daily_amount` exactly; `build_item` accepts campaign/adset; informational rows are not archived away (live keys); workbench link exists (`MaterialTasksPanel.tsx:61`).
