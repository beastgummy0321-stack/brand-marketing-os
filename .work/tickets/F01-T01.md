# Outcome

A brief says what it wants in `request_json.parts` (any combination of copy / image_prompt /
video_script / free) and, when it wants copy, exactly one `copy_length`. `workbench_brief.kind`
stops being a switch and becomes a derived display label. Generating 短／中／長 in one round is
gone: one brief, one length, the band's existing count (短 5 / 中 3 / 長 2).

No migration: `parts`, `copy_length` and `promotion_note` live in the existing `request_json`
jsonb, and every value written to `kind` is already allowed by that column's CHECK.

# Acceptance

- `POST /api/workbench/brands/{brand}/briefs` with `request.parts = ["copy","image_prompt"]`
  creates one brief whose `kind` is `ad_creative`, queues both parts, and returns 201.
- A brief with `parts = ["copy"]` and `copy_length = "long"` produces one `workbench_output` whose
  `body_json.copy_length` is `long`, whose `long` list has 2 items in the 800-1000 band, and which
  carries no `short` or `medium` list.
- `POST .../parts/image_prompt/run` works on a brief that never asked for the image_prompt part and
  has no adopted copy headline (the old `on_image_texts_required` precondition is gone).
- The architecture checker stays green and the schedule side still reads copy through
  `workbench.adopted_output`.
- Tree expansion still dispatches one brief per deepest node after the contract tightens - the
  dispatch call site sends `parts` from the same issue that starts requiring it, so
  `app/tests/test_schedule.py` stays green throughout the ticket.
