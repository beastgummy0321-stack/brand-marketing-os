# Objective

策略頁（`docs/design/ads/05-strategy.png`）要的兩樣後端東西，一次備齊：

1. **「這輪想學到什麼」**——策略輸出多一個 `learning_goals[]`，跟 `why`／`unknowns` 並列存在
   `budget_basis_json.strategy` 裡，F05 的結案才答得出「上一輪想學的學到了沒」
   （ARCHITECTURE.md §6.1 第 12 條）。
2. **「調整建議」**——採用之前可以改三個角色的百分比，金額由程式重算（§6.1 第 14 條、
   F03「模型只回百分比，金額一律 `budget.split()`」）。

§0 連結：**strategy → delivery plan**。畫面是 F04-I14；型別跟後端一起改、一起 review。
**這張票不新增模型呼叫**：`learning_goals` 是同一次 `ads_strategy` 回覆多一個鍵。

# Done

## 1. `app/departments/ads/strategy.md`

交付內容新增一項，並在回覆範例加上對應的鍵：

- `learning_goals`：這一輪投放**想學到什麼**，字串陣列、**最多 3 條**、每條一句話。
  寫「哪些受眾／訊息組合帶來最多新客」這種**下一輪用得上的問題**，不要寫成預測、不要寫成
  對成效的保證，也不要重複 `unknowns`（`unknowns` 是「現在還不知道的事」，`learning_goals`
  是「這一輪打算去弄清楚的事」）。沒有就給 `[]`。

## 2. `app/ads/strategy.py`

- `_validate_reply` 回傳多一個 `"learning_goals": _str_list(data.get("learning_goals"))[:3]`
  （沿用既有 `_str_list`；超過 3 條就截斷，不報錯）。舊資料沒有這個鍵時，讀的那一側自己
  當空陣列——**不要**為此寫 migration 或回填。
- 新函式 `set_allocation(conn, org_id, brand_id, campaign_id, *, allocation, actor) -> dict`：
  - `allocation` 是 `[{"role": str, "pct": number}, …]`。
  - 取既有的 `budget_basis_json.strategy`；沒有 → `ValueError("strategy_not_generated")`。
  - 這個 Campaign 已經展開過投放結構（`repository` 查得到投放組）→
    `ValueError("plan_already_adopted")`：投放組的日預算才是採用後的真相（F03 決策 3），
    這裡不准回頭改分配。**用既有的查詢函式，不要新寫 SQL。**
  - 驗證：每個 `role` 都在 `_ROLES` 裡、不重複、**必須跟既有 allocation 的角色集合一模一樣**
    （不是新增角色的入口）、`pct >= 0`、總和落在 99～101 → 否則
    `ValueError("allocation_invalid")`。這一段的理由跟 `_validate_reply:142-151` 同一條，
    抽成一個小函式共用，不要複製第二份。
  - 每一項的 `rationale`／`label` 沿用既有那一項的值（角色的理由是模型寫的，使用者改的是比例）。
  - 金額：`total = campaign["budget_planned"]`，是 `None` 就用目前推薦情境的 `total`
    （`budget_basis_json.scenarios`），再走既有的 `_apply_amounts()`——**不要**自己乘除。
  - 寫回 `budget_basis_json`（只換 `strategy.allocation`），用既有的
    `ads_repo.save_strategy(...)`，回 `campaign_detail`。
- `generate()`／`select_scenario()` 的行為一個字不變。

