# Objective

Integration review of F02, 2026-09-12: the 素材組 studio ships four controls that reference image 3
draws and F02-I09's own Done spelt out, but three of them do nothing — 「到檔期規劃」 is absent,
an approved (locked) pack still offers 選定／再生成／完成, 「相似版本」 is `onSimilar={() => undefined}`
and 「修改需求」 opens a 「尚未接上表單」 note. `SetDetail` was missing the two pack facts the first
two need, which is exactly what F02-I09's "Blocked if" told the worker to report. Fix them in one
pass: same screen, same file, same verify.

# Done

- `repository.set_detail()` gains two top-level fields, both from the `pack_row` it already reads —
  no second query:
  - `source_kind`: the pack's `workbench_pack.source_kind`, passed through, never interpreted
    (`"schedule_node"` ／ `"free_job"`; the workbench still does not know what an upstream is).
  - `lock`: `{"locked": bool, "reason": str | None}` — `locked` is `pack.approved_at is not None`,
    `reason` is the pack-approved sentence when locked and `null` when not. Same shape and same rule
    as `image_generation` (F02 Decisions, "text the user reads is produced once, by the side that
    owns the rule"): the browser renders the string, never re-spells it.
  - The sentence 「這個任務包已核准，選定已鎖定。」 exists today twice in `app/workbench/routes.py`
    (`_RUN_PRODUCT_ERRORS`／`_SELECT_VERSION_ERRORS`, both `pack_approved` → 409). Make it one
    module-level constant in `repository.py` and have both tables and `lock.reason` read it. One
    definition, three readers.
- `workbenchApi.ts`: `SetDetail` gains the two fields (types only — the wrapper already unwraps
  `{set}`).
- `SetStudioPage.tsx`:
  - Header shows 「到檔期規劃」 **only when `source_kind === "schedule_node"`**; it links to
    `/brands/:brandId/schedule`, the existing per-brand route. There is no per-tree URL — do not
    invent one, do not read `source_ref`, do not add an endpoint.
  - When `lock.locked`: every 選定／取消選定 button, both 「再生成 N 張」 buttons and
    「完成此素材組」 are `disabled`, and `lock.reason` is rendered once as a plain line on the page.
    The API's 409 stays as it is — the server is still the guard, the UI just stops offering the
    click.
  - 「相似版本」 does what F02-I09 said: re-runs that version's own settings — call the existing run
    handler with the count that produced that version (`products[part].generation_settings.count`,
    falling back to the toolbar's current count when the version has none). No new endpoint.
  - 「修改需求」 switches the toolbar to 精準控制 prefilled with that same count, in place of the
    placeholder note. Delete `preciseFor`'s 「尚未接上表單」 block. The 生成設定 table stays
    read-only (ARCHITECTURE.md §5.13) — this is the toolbar, not that table.
- Nothing on the page reads as a refusal of image generation, and no text tells the user to run
  live ads to see a result (unchanged rule, the existing greps still hold).

# Verify

The commands above. The two real falsifiers:

- `app/tests/test_workbench_approve.py` (it already builds an approved pack): after 核准整包,
  `GET /sets/{s}` carries `lock.locked true` and `lock.reason` equal to the `pack_approved` 409
  message; before approval `locked` is `false` and `reason` is `null`; a dispatched set reports
  `source_kind == "schedule_node"` and a 自由創作 set `"free_job"`.
- `SetStudioPage.test.tsx` (extend the existing hand-built `SetDetail`, same fake as F02-I13):
  a `schedule_node` + `locked: true` payload renders a link whose href is
  `/brands/brd_1/schedule`, renders `lock.reason`, and leaves every 選定 button disabled;
  a `free_job` + unlocked payload renders no 到檔期規劃 link and enabled buttons; clicking
  「相似版本」 calls `runProduct` once with that version's count; clicking 「修改需求」 reveals the
  產出數量 input.
