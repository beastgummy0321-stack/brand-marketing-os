# Objective
Make results objective-aware. Insights `actions` are already fetched (`graph.py:556-558`) but everything except the first
purchase synonym is discarded (`graph.py:169-174`, `meta/repository.py:815-829`, `meta_read.py:168-171`);
`ads_external_daily` holds only purchases and revenue; `review_evidence.aggregate` hard-codes CPA and ROAS (`:44-49`).
A non-sales ad therefore cannot be judged and may be misjudged on incidental purchases.
# Done
- A new ads-prefixed migration adds platform-neutral `result_kind` (text) and `result_count` (numeric, NULL = unknown) to
  `ads_external_daily`; existing purchase and revenue columns and the uniqueness key are unchanged; old rows are NOT
  back-filled with guesses, they stay NULL until re-synced.
- The ads-owned Meta adapter (`meta_read.observation` already receives the raw `actions` list; `app/meta/**` is legacy and
  is not edited) maps campaign objective to result action type (sales to purchase, engagement to post engagement, traffic
  to link click or landing page view, leads to lead, and so on) in ONE table inside the adapter; unmapped objective = NULL.
- `aggregate` returns `result_count` and `cost_per_result` beside the existing purchase metrics; SALES outputs are identical
  to today (regression test).
- Review evidence and prompt name the campaign's own result; validator shape unchanged.
- Frontend API types gain the new optional fields only (no component change here).
- `CONTEXT.md` gains 成果 and 每次成果成本; ads.md records who owns the mapping.
- A SECOND migration `supabase/migrations/20260920000004_ads_result_definition.sql` adds two more nullable
  platform-neutral text columns to `ads_external_daily`: `result_action` (the specific platform action type that
  was counted, e.g. `post_engagement`) and `result_attribution` (the attribution setting the count was read
  under, supplied by the adapter as an opaque string). No back-fill. Never edit the applied
  `20260920000003_ads_result_metric.sql`; an applied migration is corrected by a new file.
  The adapter fills both whenever it fills `result_count`. Shared code never parses the Meta-formatted
  `attribution_key` string to learn the window.
- `aggregate()` additionally returns ONE result view per `(metric_scope, currency)`, computed over ALL rows of
  that entity and window regardless of `attribution_key`: `result_kind`, `result_action`, `result_attribution`,
  `result_count`, `cost_per_result`, `days_present`, `days_known`. `attribution_key`, the uniqueness key, the
  existing per-key series and every purchase metric stay exactly as today.
  Fail-closed rules, same family as the existing `len(known) == len(group)` rule:
  (i) rows whose known `result_kind`, `result_action` or `result_attribution` disagree ⇒ `result_count` and
  `cost_per_result` are None with reason `mixed_result_definition`; no "pick first" anywhere;
  (ii) any row in the window with spend but `result_count` None ⇒ both None with reason `result_unknown_days`
  (never a partial sum divided by partial or full spend);
  (iii) the spend in `cost_per_result` is the spend of exactly the rows counted.
- Previous-vs-current comparison for the campaign's own result uses this view, not the per-key series; review
  evidence and the prompt read the view.
# Verify
Targeted tests above, including an ENGAGEMENT fixture with incidental purchases proving it is not read as a purchase campaign.
Result-view tests: three ENGAGEMENT days all on `post_engagement` ⇒ one view, `result_count` 150; day 3 on
`page_engagement` ⇒ None with `mixed_result_definition`; an incidental-purchase day no longer splits the result;
a day with spend and no result action ⇒ None with `result_unknown_days`; a SALES view equal to the purchase
numbers when every day is known.
