# Objective
A planner refusal says which rule refused the model's reply, and a long planner call survives a reload and a double press
(feature Contract J, planner refusals and busy; audit W14; drill-11 R7 B3, B4; controls c2-01 「照上一期」 502 ×3 with one sentence;
faults F9 reload during 展開投放結構 → 「還沒有投放結構」 then 「已經展開過」). Today nine refusal sites raise one
`delivery_plan_failed` with no code or log, and the busy state lives only in the browser while the request keeps running.

# Done
1. `plan.REFUSALS`, `strategy.REFUSALS`, `brief.REFUSALS` = `{code: reason}` per Contract J (plan: `llm_failed`, `reply_unreadable`,
   `reply_invalid`, `menu_violation`, `offer_unused`, `name_forbidden`, `group_unbound`, `carried_changed`, `replace_rerun`;
   strategy／brief name each of their raise sites the same way). Each raise site raises a `ValueError` subclass carrying the code
   (its `str()` stays `delivery_plan_failed`／`strategy_failed`／`brief_parse_failed` for existing mappings); reasons are short
   plain sentences, e.g. `offer_unused` 「這期有優惠，AI 排的廣告都沒用上」, `replace_rerun` 「又排了上一期要換掉的組合」,
   `llm_failed` 「AI 這次沒有回覆（{error_code 的白話}）」.
2. Routes: the 502 body is `{code, reason, message}` with `message` = the module's failed sentence + 「（{reason}）」; each refusal is
   recorded on the task row with `gateway.record_refusal(conn, task_id, code, reason)` and logged at INFO with campaign id and code.
3. `app/ads/busy.py`: `claim(conn, campaign_id, kind)` (session `pg_try_advisory_lock` keyed by campaign; released in `finally`;
   not acquired → 409 `campaign_busy` 「上一次還在處理，等它好了再看。」) used by strategy generation, adoption (展開投放結構) and brief
   parse; `busy_state(conn, org, brand, campaign_id) -> {kind, since} | null` from the newest running `llm_task` of that campaign
   scope and task type (`ads_strategy`, `ads_delivery_plan`, `ads_brief_parse`) started within the call's timeout + 30 s. The campaign
   detail read serves `busy`; `lib/adsApi.ts` types `busy` and the refusal body (optional keys).
4. Tests: each plan refusal site yields its code in the 502 body and on the task row; two concurrent adopt calls → one runs, the
   other 409 `campaign_busy`; while an adopt runs the detail read serves `busy {kind: "plan"}`; a running row older than timeout +
   30 s is not busy; after the call `busy` is null.
