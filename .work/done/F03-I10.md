# Objective

The whole loop can be walked without any platform. §0: it serves the **action → outcome** links;
its input is the campaign's own rows; its output is bound entities and daily outcome rows
indistinguishable in shape from the real ones; its trace is the same `ads_action` rows the manual
adapter writes, marked as simulated; it is **pluggable** — delete it and the product still works,
but acceptance and drills lose their legs.

# Done

- `app/ads/adapters/simulated.py` implementing the same three methods as `manual`:
  - `describe` → one line saying this is 模擬發布（演練用）and what it will create; the word
    「示意資料」 is the vocabulary the UI will reuse (`docs/design-system.md` §1.3).
  - `publish` → writes fake `external_id`s (`sim_<short id>`), `external_name` = the row's own name,
    `external_status='ACTIVE'`, `local_state='bound'` on the campaign node, every group and every
    ad; campaign → `live`; one `ads_action` per row (`kind='publish'`,
    `sync_state='auto_synced'`, `platform_ref` = the fake id). **It then calls
    `generate_outcomes` for every day from `start_date` up to today** (nothing beyond today), so a
    person who clicks 模擬發布 in the browser lands on a 成效 tab with numbers — no command line in
    the walk. A campaign that starts in the future publishes with no outcome rows, and the 成效 tab
    honestly says 還沒有成效資料.
  - `bind` → idempotent no-op returning 「模擬發布已自動配對」.
  - `generate_outcomes(conn, …, campaign_id, *, until=None, seed=None)` → fills every missing day
    from the campaign's `start_date` to `min(end_date, until or today)` with `ads_outcome_daily`
    rows (idempotent: a day that already has rows is left alone), so it is safe to call from
    `publish`, from the 成效 tab's 更新 action (F03-I11's ingest route dispatches to it for a
    simulated campaign) and from `demo.py`. Rows carry
    `source='simulated'`, one row per bound ad per day, spend around the group's daily budget split
    across its ads, purchases and revenue drawn so that CPA and ROAS land in a believable range,
    **sparse by design** (some ad-days have no row, like the real data — `simulate_meta_spend.py`'s
    header documents the measured 81% sparsity). Deterministic under a fixed seed.
- `app/ads/demo.py` — `uv run python -m app.ads.demo --org <org> --brand <brand> [--days 14]`:
  creates or reuses a campaign, publishes it with the simulated adapter and fills the outcome days,
  so a person can see every screen with data in one command. Refuses to run when
  `BRAND_OS_ENV == "production"`, the same guard `app/tools/simulate_meta_spend.py` uses.
- `app/tests/test_ads_publish_simulated.py` (the falsifier): publishing binds every row (campaign
  node included) and moves the campaign to `live`; **publishing a campaign that started 5 days ago
  leaves 5 days of outcome rows without any further call** — that is the case the browser walk
  depends on; no row is dated after today or outside the campaign's range; a second
  `generate_outcomes` does not duplicate rows; the same seed gives the same numbers; nothing in the
  module writes to `meta_entity_spend`.

# Verify

`uv run python -m pytest app/tests/test_ads_publish_simulated.py -q` — determinism plus the
unique-key case; those are what let acceptance re-run the walk and get the same screens.

# Blocked if

`publish` cannot write outcome rows because the adapter has no access to the campaign dates (it
does — it is given the campaign). Do not move the generation into a route or the frontend: the
browser walk must reach 成效 with data after one click, and the CLI is a convenience, not the path.
