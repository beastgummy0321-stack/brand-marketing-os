# Objective

e2e must stop depending on a real model (user's decision 2026-09-14, F06.md Decisions「e2e 不再打真模型」;
ARCHITECTURE.md §7). Today the 8720 backend inherits `.env`'s `BRAND_OS_LLM_PROVIDER=codex_cli`, so the specs
sit on live Codex calls. The request itself makes three: `ads_brief_parse`, `ads_strategy`,
`workbench_free_parse`. A deferred job makes a fourth: `workbench_image_prompt`. An upstream outage
(「Selected model is at capacity」) turns the gate red regardless of the code.

The job path is worse. The e2e backend's `background.workbench_generate` jobs land in the dev database's shared
`public__queue`. From there the user's long-running `python -m app.worker` runs them, with real Codex and old
code: e2e-created brands carry `workbench_image_prompt` rows with provider `codex_cli`, yet 8720 starts no
worker. An env override on the e2e backend cannot reach that process.

The fix is two local-only switches, set only on the e2e backend: scripted model replies per `task_type`, and a
job queue that writes nothing. The user's own 8710 app and worker keep real Codex.

# Verify

Frontmatter commands, in order.
- **The pytest set** proves six things:
  - the guard;
  - the provider swap;
  - the loud miss, with no orphan row;
  - the memory job mode;
  - that no queue row is written;
  - every scripted reply passes its owning module's own validator.
- **`npm run e2e`** is the gate this issue exists to make reliable.
- **The last command** is the direct proof. It is scoped to the e2e accounts themselves (emails `smoke-`,
  `width-`, `layout-<digits>@example.com`) whose brands were created in the last 15 minutes, so the user's own
  8710 activity or another worktree cannot redden it.
  - It passes only if those brands made at least one model call;
  - every call is `scripted`;
  - `public__queue.procrastinate_jobs` holds zero jobs for them. That last part catches a mistyped queue switch
    even when the user's worker is stopped.
  - It uses only single quotes inside one double-quoted argument, because harness runs verify through cmd.exe.
  - Proven through `spawnSync(..., { shell: true })` on 2026-09-14: over a 3-day window it exits 1 with
    `not scripted: 336`, `jobs in shared queue: 102`.

Setup:
- Docker Desktop and `supabase start` must be up.
- Only one e2e-gated issue finishes/merges at a time.
- The user's 8710 app and worker may stay running; they are exactly what the memory job mode protects against.

# Blocked if

- **The webServer log shows `LookupError: scripted provider has no reply for task_type ...`.** e2e reaches a model
  call this issue did not find. Block with that line; choosing a reply's content is a planner decision.
- **A spec step waits on a background job's result and times out.** That step is not possible under this seam.
  Block with the step.
- **A smoke/width assertion fails because free parse now succeeds** (a step that only existed on the parse-failed
  branch). Block with the assertion line; do not edit assertions.
- **The last verify command exits 1.** Block with its printed line plus
  `SELECT task_type, provider, started_at FROM llm_task ORDER BY started_at DESC LIMIT 10`.
- **`app/tests/test_architecture_boundaries.py` or the checker objects** to `app.background` importing
  `app.core.config`. Block with the message.
- **e2e is red anywhere else.** Block with the log path. Do not rerun hoping for a different result: no model is
  left to be flaky.
