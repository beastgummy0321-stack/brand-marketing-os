# Objective

Integration review of F02, 2026-09-12: `pack.context` is part of the §5.4 handoff contract and two
screens read it — `PackDetail.meta.platform`／`meta.goal` and, through `chips.platform`, the
生成設定 table's 平台 row (ARCHITECTURE.md §5.13, the row reference image 3 fills with
「Meta 廣告」). **Nobody ever writes it.** This issue fixes the 自由創作 half: the page parses 平台
out of the free text, shows it in the 「AI 解析結果」 table, lets the user edit it in 精準控制 — and
then `specToCreateBody` drops it, so the value the user just read on screen disappears between two
screens. (The 檔期規劃 half is F02-I19; the two are independent.)

# Done

- `app/workbench/routes.py::NewFreePackRequest` gains `context: dict = {}` — default `{}` like
  every other field on the model (F02 Decisions, "request bodies on tenant routes never use
  Pydantic-required fields"), and `repository.create_free_pack()` passes it straight into the
  `pack` dict it hands to `submit_pack`. Stored, not interpreted: no new validation of the string,
  no new key list, the workbench still does not know what a platform means.
- `workbenchApi.ts::NewFreePackRequest` gains `context?: Record<string, unknown>` (planner review,
  2026-09-12: `workbenchApi.ts` is added to `touch` for this one line). That file is where the API
  surface is typed — a local `NewFreePackRequest & { context?: ... }` alias inside `FreeJobPage.tsx`
  leaves the shared type saying the field does not exist, so the next caller that types its body as
  `NewFreePackRequest` drops 平台 again without a compile error. Delete the local alias.
- `FreeJobPage.tsx::specToCreateBody` maps `spec.platform` → `context.platform` on the create body;
  omit the key when it is `null` (never send `""`). This stays the one piece of mapping logic on
  that page — nothing else about the two-click flow moves.
- Nothing downstream changes: `PackDetail.meta` and `chips`／`generation_settings` already read
  `context_json`.
- The two fields on this page the backend never receives get one honest hint line each, in the
  same pattern as the image seat line (`image_generation.reason`), rendered as small muted text
  directly under the control. Planner ruling 2026-09-12: **this copy lives in the TSX**, unlike the
  seat line — it describes a field the API never sees, so no backend owns the rule. Verbatim, no
  rewording, no third hint anywhere:
  - under 精準控制's 場景 field: 「場景還沒接上生成流程，這裡先保留席位；接上後同一個欄位直接生效。」
  - under the 參考圖 drop zone: 「參考圖還沒接上生成流程，這裡先保留席位；接上後同一張圖直接派上用場。」
  Neither is phrased as a refusal and neither mentions running live ads. The 場景 field and the
  file picker keep working exactly as they do today (`docs/backlog/issue-free-job-scene-field-goes-
  nowhere.md`, `issue-free-job-reference-image-never-uploaded.md` hold the real wiring) — this
  issue only stops the page from implying the values go somewhere.

# Verify

The commands above. Two falsifiers:

- `app/tests/test_workbench_pack_api.py`: `POST /packs` with `context: {"platform": "Meta 廣告"}`
  → `GET /packs/{p}` reports `meta.platform` as that string and `GET /sets/{s}` reports
  `chips.platform` and a 生成設定 平台 row whose `text` is that string (today both are 「—」／null).
  One test, both readers.
- `FreeJobPage.test.tsx`: the existing spec → create-body mapping test gains one case — a `spec`
  with `platform: "Meta"` produces `context.platform === "Meta"`; `platform: null` produces no
  `context.platform` key.

# Blocked if

`submit_pack` rejects or drops unknown `context` keys — that would mean the contract is narrower
than §5.4 reads. Stop and report rather than widening `submit_pack`'s validation from here.
