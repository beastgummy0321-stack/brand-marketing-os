# Objective

彈性 cannot come back. The user: 「Meta已經沒有所謂「彈性」選項，若排程仍然說這期要排彈性圖片，則視為BUG。」 F07-I03
disabled every `format/flexible` row, but old brands still see 彈性格式 in 品牌智庫 → 座標 → 格式, marked 已停用, with a
checkbox that re-enables it (`frontend/src/components/library/tabs/CoordinatesTab.tsx:207-224`). Decision 33 keeps
disable-not-delete: the row stays in the table so old tagged data keeps its label. The fix is at the API that
screen reads: the retired row is not listed and cannot be toggled. No frontend change is needed, because 品牌智庫 and
投放中心's ad editors both read `GET /api/schedule/brands/{brand_id}/coordinates`.
Never delete or overwrite anything under `data/`.

# Done

1. **`app/schedule/repository.py`**: one module constant `RETIRED_COORDINATES = frozenset({("format", "flexible")})`,
   with a one-line comment citing F07 Decision 33 and the migration `20260915000001_…disable_flexible.sql`.
2. **`list_coordinates(conn, org_id, brand_id, *, include_retired: bool = True)`**: when `include_retired` is False,
   rows whose `(dimension, key)` is in `RETIRED_COORDINATES` are left out. The default stays True, so the internal
   readers that resolve old labels (`binding.py:100`, `performance.py:107`, `jobs.py:422`, `history.py:197,277`)
   are unchanged and untouched.
3. **`set_coordinate_disabled`**: if the target row's `(dimension, key)` is retired, return `None` without writing,
   whether `disabled` is true or false. The disable route (`routes.py:578-589`) is unchanged and already answers 404
   `coordinate_not_found` for `None`. A retired coordinate is not found, both when listing and when toggling.
4. **`app/schedule/routes.py::list_brand_coordinates`** (`:556-560`) calls
   `list_coordinates(..., include_retired=False)`. Nothing else in the file changes.
5. **Tests** in `test_schedule_format_seed.py`. Rows follow `test_disable_flexible_migration_behaviour`
   (`_insert_flexible`); the HTTP client follows `app/tests/test_workbench_pack_api.py::_WorkbenchPackApiTestBase`
   (`TestClient(main.app)`). Use two fresh brands, seeded: brand A has a `format/flexible` row that is disabled,
   brand B has one that is enabled (a row someone re-enabled before this fix).
   - `GET /api/schedule/brands/{A and B}/coordinates` contains no `flexible` key, and still contains `single_image`,
     `carousel` and `video`.
   - `POST …/coordinates/{A's flexible id}/disable` with `{"disabled": false}` → 404 `coordinate_not_found`; the row's
     `disabled_at` read by SQL is unchanged. The same call with `{"disabled": true}` on B's row → 404, and B's
     `disabled_at` is still NULL.
   - `schedule_repo.list_coordinates(conn, org_id, A)` (default) still returns the `flexible` row;
     `include_retired=False` does not.
   - A's `single_image` row can still be disabled and re-enabled through the route (both 200), so the guard is scoped
     to the retired pair.
6. **Red proof.** Break each rule in memory only (`monkeypatch` of `schedule_repo.list_coordinates`,
   `set_coordinate_disabled` or `RETIRED_COORDINATES`, or a wrapper around the route's repository call). Never edit a
   file on disk. Report, per ID, which test went red.
   - `R01` the route hides the retired row → the route calls the default → the GET case goes red.
   - `R02` a retired row cannot be toggled → `set_coordinate_disabled` writes as before → the 404 case goes red.
   - `R03` the guard is scoped → match on `dimension == "format"` alone → the `single_image` toggle case goes red.
   - `R04` internal readers keep the row → default `include_retired=False` → the default-includes case goes red.
