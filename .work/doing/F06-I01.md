# Objective

The Campaign workspace gets **one** next-step rule that every tab reads (ARCHITECTURE.md §6.2
decision 15). Today the only producer is `OverviewTab.tsx::currentStageIndex`/`nextActionFor`, and
when every ad is ready it sends the user to 投放結構, a tab with no publish affordance. This issue
adds three things: the rule, the one server fact it needs (whether this campaign's pack exists, read
from the pack itself), and 總覽 and 策略 moved onto the rule. Later issues (F06-I02/I03) put the
same button on 投放結構／素材／成效.

The rule is navigation, not a judgment sentence (§6.2 decision 15, §6.1 decision 10 unchanged), so it
lives in the browser; it must not re-state server rules or judge how the campaign is doing.

# Done

1. **Backend fact `pack_id`, from the pack, not from rows.** Rows only carry a `pack_id` when the ad has
   a set in the pack, so an ad added after the handoff makes every row `null` while the pack exists
   (repro: dispatch A,B → delete A,B → add C). In `app/ads/assets.py`:
   - add `pack_id(conn, org_id, brand_id, campaign_id) -> str | None` = the id of
     `workbench.pack_for_source(conn, org_id, brand_id, PACK_SOURCE_KIND, _pack_source_ref(campaign_id))`
     or `None`. `dispatch_pack` uses it for its `pack_already_exists` check. `readiness()` keeps its own
     lookup, because it needs the pack row's `approved_at`.
   - `readiness_summary(rows: list, pack_id: str | None) -> dict` returns
     `{"ready_count", "total", "pack_id"}`; `ready_count`/`total` computed exactly as today.
   - `app/ads/routes.py`: `_with_readiness` (:54) and `get_assets` (:514) pass
     `assets.pack_id(web.conn, actor.org_id, brand_id, <campaign id>)` as the second argument. No other
     route changes.
   - `app/tests/test_ads_assets.py`:
     - `ApprovalFlipsReadinessTest` expects `{"ready_count": 2, "total": 2, "pack_id": pack_id}`.
     - `ManualTickTest` asserts `assets.pack_id(...)` is `None`.
     - New test class `PackIdSurvivesRebuiltAdsTest`: adopt → dispatch → delete both ads with `plan.delete_ad` →
       add one ad with `plan.create_ad` (same module as `delete_ad`) → `GET /api/ads/brands/{b}/campaigns/{c}`
       returns `campaign.asset_readiness == {"ready_count": 0, "total": 1, "pack_id": <the dispatched id>}`.
2. **Type.** `frontend/src/lib/adsApi.ts` `AssetReadinessSummary` gains `pack_id?: string | null;` with a

3. **The rule — new `frontend/src/components/ads/nextStep.tsx`.** Exports:
   - `type WorkspaceTab = "overview" | "strategy" | "structure" | "assets" | "performance"`
   - `type StepTarget = WorkspaceTab | "publish"`
   - `type StepId = "strategy_generate" | "strategy_adopt" | "add_ad" | "dispatch" | "make_assets" | "publish" | "performance"`
   - `interface NextStep { id: StepId; target: StepTarget; stageIndex: number; sentence: string; label: string }`
   - `function nextStep(c: CampaignDetail): NextStep` — first matching row wins, copy exactly as written
     (`adCount` = total ads across `c.groups`):

   | condition | id | target | stageIndex | sentence | label |
   |---|---|---|---|---|---|
   | `status === "closed"` | performance | performance | 5 | 已結案，結案紀錄在成效。 | 查看成效 → |
   | `status === "live"` | performance | performance | 4 | 投放中，每天的花費與結果在成效。 | 查看成效 → |
   | `status === "ended"` | performance | performance | 4 | 投放已結束，到成效看結果或結案。 | 查看成效 → |
   | no `budget_basis_json.strategy` | strategy_generate | strategy | 0 | 還沒有策略，先產生策略建議。 | 前往策略 → |
   | `groups.length === 0` | strategy_adopt | strategy | 1 | 策略已產生，確認後系統會建立投放結構。 | 前往策略 → |
   | `adCount === 0` | add_ad | structure | 2 | 投放結構裡還沒有廣告，先新增一則廣告。 | 前往投放結構 → |
