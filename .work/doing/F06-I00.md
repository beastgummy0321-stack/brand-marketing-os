# Objective

`width-overflow.spec.ts` waits on two real `codex_cli` model calls with budgets that are now smaller
than the calls themselves, so e2e is red whenever those steps run, regardless of the code under test.
Measured on 2026-09-14 (`llm_task`): every successful `ads_brief_parse` took 14.8–15.1 s against the
15 s default `expect` timeout at `:122` (`frontend/playwright.config.ts:27`); `ads_strategy` took 15.7 s
against 30 s at `:128`. The whole test also runs under the 60 s config test timeout
(`playwright.config.ts:26`). Size the waits to the measured latency, locally in this one test.

# Done

1. First statement inside the test body (`:25` callback): `test.setTimeout(180_000);` — two 60 s model
   waits plus the rest of the route walk do not fit the 60 s config budget.
2. `:122`: `await expect(page).toHaveURL(new RegExp(\`/app/brands/${brandId}/ads/new/[^/]+$\`), { timeout: 60_000 });`
3. `:128–131`: the `{ timeout: 30000 }` becomes `{ timeout: 60_000 }`.
4. One English comment directly above `:122`, e.g.
   `// Both waits sit on a real codex_cli call: ads_brief_parse measured ~15 s, ads_strategy ~16 s (llm_task, 2026-09-14).`
5. Nothing else changes: no selectors, assertions, routes, other specs, or `playwright.config.ts`.

# Verify

Frontmatter command. Only one e2e-gated issue finishes/merges at a time. Docker Desktop and
`supabase start` must be up before running it.

# Blocked if

- e2e is red and the latest `llm_task` rows for `codex_cli`
  (`select started_at, task_type, status, error from llm_task order by started_at desc limit 10`) show a
  capacity/outage error (e.g. 「Selected model is at capacity」) → rerun e2e once later; do not change code.
  Still failing after the rerun → block with those rows.
- `:122` or `:128` still times out at 60 s with healthy `llm_task` rows → block with the rows and durations;
  that is a latency regression, not a budget to raise again.
- e2e is red anywhere else → block with the log path; it is not this issue.
