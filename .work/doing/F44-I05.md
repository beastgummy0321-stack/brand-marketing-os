# Objective
The 素材 tab's blocked slot, as the prototype `.harness/scratch/prototype/f44-blocked-slot/index.html` (launch config `prototype`,
port 8741; open it and click 換一版文案 / 再檢查一次 / 換一張). The prototype is the layout spec; reference shots in its `shots/`.
Data: `GET …/slots` (Contract D in the feature: `state: "blocked"`, `blocked`, `offer_label`) and `POST …/slots/{ad_id}/recheck`.

# Done
1. `adsSlotsApi.ts`: `SlotState` gains `"blocked"`; `Slot` gains `blocked` and `offer_label` (optional for older fixtures);
   `recheckSlot(brand, campaign, adId)`.
2. Blocked tile: the two halves as a ready tile (thumbnail dimmed), the 「卡住」 chip (`bad` tone), and under both halves the
   reason — `blocked.text` with each of `blocked.terms` highlighted, 「另有 N 個原因」 when `more` > 0 — then the exit:
   `fix: "copy"` → 「換一版文案」 (the existing picker dialog → `chooseSlotCopy`) and 「到工作檯改文案 →」 when `workbench_href`;
   `fix: "file"` → 「換一張」 (the existing upload action); always 「再檢查一次」 (`recheckSlot`; 「檢查中…」 while busy; the returned
   slots replace the grid; a failed call says so inline).
3. Every planned slot's head shows the `offer_label` chip (accent tone when it is not 無優惠), as in the prototype.
4. Card head: 「x／y 格已備妥」 plus a 「N 格卡住」 chip when N > 0; a blocked slot's progress segment is the danger colour; the action
   bar hint reads 「N 格卡住，處理好才會進上架清單」 when N > 0.
5. Polling stays tied to `in_progress` only; a blocked slot does not keep the 3 s re-read alive.
6. Tests with real-shaped fixtures (one ready, one in progress, blocked `copy` with terms, blocked `file`, `more: 1`): the chip,
   highlighted terms, each exit calls the right API, recheck replaces the grid, no polling when only blocked slots remain.
   `ads-cold-start.spec.ts`: adjust only if its slot assertions change.
