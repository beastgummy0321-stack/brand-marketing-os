# Objective
Two read-only payload additions the flow pages need. No migration, no platform write, no new route.
# Done
1. `app/ads/triage.py::_queue_payload`: every row gains `proposal` — `null`, or `{change_set_id, campaign_id, kind, status, verification_state, reason, revisit_at}` of the change set that currently answers this row, chosen exactly by the rule in Feature Decisions ("Queue row state", as corrected by the pre-dispatch challenge). One query per brand (not per row); no write in `get_queue`.
2. `app/ads/change_control_data.py::get`: every item view gains `platform_url: str | None`, computed at read time from the item's `target` through a function in the adapter layer keyed by `target["platform"]` (unknown platform or missing ids → `None`). No platform literal outside `app/ads/adapters/`; nothing added to `plan_json`, `_TARGET` or any hash.
3. Frontend types only: `QueueItem.proposal` in `adsTriageApi.ts`, `ChangeItem.platform_url` in `adsChangeApi.ts`.
4. Tests: proposal null / draft / approved-pending / confirmed / rejected / deferred past `revisit_at` / superseded / another entity's set / another campaign's set; `platform_url` for a Meta ad and `None` for an unknown platform; content hash of an existing set unchanged.
5. `docs/architecture/ads.md` §6.22 (new, short): the two fields and the rule.
# Verify
Issue verify plus manifest gates.
# Blocked if
The proposal rule cannot be computed without a schema change, or the adapter layer has no read-side place for a per-platform function — stop and report.
