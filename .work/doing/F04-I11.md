# Objective

實測（`docs/backlog/issue-brief-parse-drops-explicit-target.md`，F03 驗收，真後端＋真模型）：
使用者寫「…希望 CPA 在 300 以內，預算三萬。」→ `success_target` 還是 `null`、預算整個掉了。
`brief_parse.md` 沒有要求「句子裡的數字要歸位」，也沒有一條帶數字的測試，所以沒人發現。

這張票把那句話讀完整：目標數字、預算上限、平台、時間都抓出來，每一格記得它是**你說的**還是
**系統帶入**（ARCHITECTURE.md §6.1 第 11 條）。這是 F04-I12「MarketingOS 理解如下」確認畫面的
資料契約，所以後端與 `adsApi.ts` 的型別一起改、一起 review。§0 連結：**goal（the brief）**。

**不加欄位、不開 migration**：預算與平台寫進既有的 `constraints_json`，日期寫進既有的
`start_date`／`end_date`，來源標記寫進既有的 `context_json.field_sources`。
**呼叫次數不變**：還是一次 `ads_brief_parse`；策略是第二次，由使用者按「產生策略建議」才發生。

# Done

## 1. `app/departments/ads/brief_parse.md`

- 新增一條不可違反的規則，**放在既有兩條之後、交付內容之前**：
  「**數字優先**：使用者句子裡出現的每一個數字，先歸位到它在修飾的欄位——指標的數字歸
  `success_target`、錢的數字歸 `budget_cap`（中文數字要換算成阿拉伯數字，例如「三萬」＝30000）。
  只有句子裡真的沒有提到這個數字時才填 `null`。這條規則勝過「沒有把握就填 null」：句子裡寫了
  就是有把握。」
- 交付內容新增四項（回覆範例同步）：
  - `budget_cap`：數字或 `null`（整個投放期間的預算上限；使用者說「每天 1000」時換算成
    「一天的錢」不是你的工作——這種情況填 `null`，並在 `notes` 說明）。
  - `platform`：`meta`／`google_ads`／`tiktok`／`shopee`／`momo` 五選一，或 `null`
    （使用者沒指名就 `null`，**不要**預設 meta）。
  - `period`：`null`、或 `{"kind": "month", "month": 9}`、或
    `{"kind": "range", "start": "YYYY-MM-DD", "end": "YYYY-MM-DD"}`。
    「9 月」就回 `{"kind":"month","month":9}`——**不要自己算年份或月底是幾號**，那是程式的事。
  - `audience_hint` 維持既有。
- prompt 裡「## 投放期間」那一段改成：使用者有填日期時照舊給；沒填時寫「（使用者沒有指定，
  請從句子判斷 `period`）」。另外固定加一行「今天是 {today}」（供模型判斷「這個月」「下個月」）。

## 2. `app/ads/brief.py`

- `_validate_reply` 收下四個新鍵，型別不對一律當 `null`（既有的寬鬆作風）：
  `budget_cap` 只收正數（`bool` 排除）、`platform` 只收 `app.ads.channels.CHANNELS` 裡的 key
  （import `channels`，**不要**自己複製一份清單）、`period` 只收上面兩種形狀。
- 新函式 `_resolve_period(period, *, today) -> tuple[date | None, date | None]`（純函式，
  **日曆算數在程式**，R7）：
  - `kind == "range"` → 直接讀兩個 ISO 日期，`end < start` 一律當沒解析到（回 `(None, None)`）。
  - `kind == "month"` → 年份 = `today.year if month >= today.month else today.year + 1`；
    起日 = 該月 1 號、訖日 = `calendar.monthrange` 的最後一天。一行註解說明為什麼往後不往前：
    使用者說「9 月」時是在排未來的檔期。
  - 其他 → `(None, None)`。
- `create_draft` 的日期規則（`_validate_dates` 拆成兩半，**不要**刪掉既有的錯誤碼）：
  1. 呼叫端給了 `start_date`／`end_date`（兩個都要）→ 照舊驗證，來源 `user`。
  2. 只給其中一個 → 照舊 `dates_required`。
  3. 兩個都沒給 → 用 `_resolve_period` 的結果；解析不出來就用
     `today` ～ `today + 30 天`。這一段的來源是 `system`。
  （`today` 用 `coresettings.today_for_org(conn, org_id=org_id)`，不要 `date.today()`。）
- `constraints_json`：使用者自己填的限制**永遠勝過**模型解析的（chips 是明說的）。
  `budget_cap` 只在 `constraints` 沒有 `budget` 鍵時寫進 `constraints["budget"]`；
  `platform` 同理寫 `constraints["platform"]`。
- `context_json` 新增 `field_sources`：六個鍵
  `{"product", "objective", "platform", "budget", "dates", "audience"}`，值是 `"user"` 或
  `"system"`。判定規則（寫成一張小 dict，不要散在各處）：
  - `product`：模型有回 `product_ids` 且過濾後非空 → `user`（他句子裡講了商品）；否則 `system`。
  - `objective`：解析成功（`parsed_ok`）→ `user`；落回預設值 → `system`。
  - `platform`／`budget`：來自使用者 chips 或模型從句子抓到 → `user`；完全沒有 → `system`。
  - `dates`：呼叫端自己填了日期（規則 1）**或**句子裡講了時間、`_resolve_period` 解析成功
    （規則 3 的前半）→ `user`；只有落到「今天 ～ +30 天」那個備援才是 `system`
    （ARCHITECTURE.md §6.1 第 11 條：句子裡沒講，系統才幫你填，那一格才標「系統帶入」）。
  - `audience`：`audience_hint` 非空 → `user`，否則 `system`。
- 回傳的 `detail` 照舊多一個 `parsed` 旗標；**不要**改 `campaign_detail` 的形狀。

## 2b. 使用者改過的那一格，來源要跟著變成「你說的」（`app/ads/repository.py`）

`field_sources` 只在建草稿時寫一次是不夠的：確認畫面（F04-I12）的六張卡全部走
`PATCH .../campaigns/{id}`，使用者把預算改成 30000 之後，那一格還印「系統帶入」就是說謊。
**翻轉寫在後端**（資料庫才是真相，畫面只是印它）：

`repository.update_campaign()` 裡，在既有的欄位寫入之後、同一次交易內，依這次 `updates`
真的帶到的鍵，把 `context_json["field_sources"]` 對應的那一格設成 `"user"`：

| `updates` 的鍵 | 要翻的 `field_sources` 格 |
|---|---|
| `product_ids` | `product` |
| `objective` | `objective` |
| `start_date` 或 `end_date` | `dates` |
| `constraints_json` 裡的 `platform` 有變 | `platform` |
| `constraints_json` 裡的 `budget` 有變 | `budget` |

- 寫成這個檔案裡的一張小 dict，**不要**散在各個 if 分支裡；`context_json` 本來就是這支函式
  在維護的（:149-158 已經在改 `product_ids`），順著同一段寫。
- `field_sources` 不存在（F04 之前建的舊草稿）時就當空 dict 起手，不回填、不 migration。
- 使用者把一格清空（例如把預算刪掉）→ 那一格仍然是 `user`：他親手做的決定也是他說的。
- **不動** `update_campaign` 的簽章、錯誤碼與既有的租戶／綁定檢查。
