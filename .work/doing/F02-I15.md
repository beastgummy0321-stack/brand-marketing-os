# Objective

`app/tests/test_workbench_parts.py` is the last file still speaking the retired brief contract:
all 7 tests POST `/api/workbench/brands/{b}/briefs` (line 50), a route F02-I03 removed
(`app/workbench/routes.py` header). Nobody owned this file in F02, so it is the 7 of the 9
failures on the full run. Rewrite it against 任務包 → 素材組, keeping only the behaviour that still
exists and is not already proven somewhere else. `app/tests/test_workbench_api.py` is the
precedent for how to do this (F02-I03 gutted it and said so in the docstring); follow that file's
shape — rewritten docstring, one class per surviving rule.

# Done

Rewrite the module docstring: this file now covers the **dispatch contract** (`submit_pack` →
`request_json.parts`, one job per required 產物類型) and the two request-level validations that
live nowhere else. Say in one line that the brief endpoints are gone (F02-I03) and that the old
`kind`/parts cases moved or were retired.

**Keep the existing `setUp`** (TestClient, `workbench_module.register_tasks()`, brand + product,
`ACTOR`); drop `_new_brief_body`/`_create` and call
`workbench_repo.submit_pack(web.conn, self.org_id, self.brand_id, pack)` directly — there is no
public dispatch route, `submit_pack` is the upstream's entry point. Mirror
`app/tests/test_workbench_pack.py:29-53` (`_submit_pack`/`_one_set`/`_briefs` helpers) rather than
inventing new ones.

Three cases, nothing more:

1. **Dispatch fires one job per `required_outputs` key** (F02 Decisions, "Dispatch follows
   `required_outputs`' keys"). One set with `{"copy": 1, "image_prompt": 1}` and
   `request: {"copy_length": "short", "image_prompt_count": 3}` → the written `workbench_brief`
   row has `request_json["parts"] == ["copy", "image_prompt"]` and **both**
   `background_module.is_active(f"workbench:{brief_id}:copy")` and `…:image_prompt"` are true.
   This is the assertion the old `MultiPartDerivesAdCreativeTest` was really making; it is not
   covered anywhere else (`test_workbench_pack.py` never looks at the queue).
2. **`copy_length_unknown`** — a set whose `request.copy_length` is `"extra_long"` makes
   `submit_pack` raise `ValueError("copy_length_unknown")` (`repository.submit_brief`). Assert the
   raise and the code, **nothing about what was or was not written**: that validation runs inside
   `submit_brief`, i.e. after `create_pack`, so the "rejected pack writes nothing" guarantee
   (`test_workbench_pack.py:270`) covers only the codes checked up front. Do not widen this issue
   into changing that order.
3. **An image-prompt round may run before any copy is selected** (ARCHITECTURE.md §5.8). Submit a
   set requiring both parts, `UPDATE workbench_brief SET status = 'done'` the same way the old
   `RunPartWithoutAdoptedCopyTest` did (no worker runs in tests), then
   `POST /api/workbench/brands/{b}/sets/{set_id}/products/image_prompt/run {"count": 2}` → 200,
   `workbench:{set_id}:image_prompt` active, and a direct `SELECT request_json` shows `parts`
   still `["copy", "image_prompt"]` — `run_part` records what was requested, not what was run.

Delete, do not rewrite:

- `SinglePartDerivesItsOwnKindTest` and the `kind == "ad_creative"` assertion — `workbench_brief.kind`
  is a display-only column with no reader in the pack model (no screen, no API field in F02's API
  surface). The derivation stays in `submit_brief`; it is no longer behaviour worth a test.
- `PartsAndCopyLengthValidationTest`'s three `parts_unknown` cases — already proven at the
  repository level (`test_workbench_pack.py:249-280`, including `part_retired`) and through the
  route (`test_workbench_pack_api.py:271-288`). Only `copy_length_unknown` survives, as case 2.

No new test file, no new helper module, no change to any other test file.
