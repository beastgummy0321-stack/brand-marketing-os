# Objective
Items 3, 14, 15: one job-status rule so no status endpoint reads done while its job is queued, failed before the AI call, or failed after it (Feature Contract J); the research step re-asks once when its table cannot be read.

# Done
1. `app.background.job_outcome(lock)` as a facade function over procrastinate's own job listing (no hand SQL on `procrastinate_jobs`; memory mode returns None).
2. Every status reader in `app/intake` and `app/brand_web` follows Contract J: `research.job_state` (no more `_idle_job` done with an empty stage after a failed queued job), `routes_api._job_state`, `persona_generation.generation_state`, `routes_products._research_state`, `routes_report_api._job_shape`. A running job reads running even when an older `llm_task` row exists.
3. Handlers re-raise after their failure notice when post-processing fails (`background_product_scan` moves `_apply_product_scan_result` inside the guarded block; paste_fix, persona, research and report likewise), so the job ends failed.
4. `research.run_research`: when `apply_paste` cannot read the reply, re-ask once through the same `ai._run` with the parse errors quoted; a second failure keeps the needs-review path; the re-ask counts against the draft's cost limit and is skipped when the limit blocks it.
5. Regression tests (red on master): queued job failed with no `llm_task` row → failed with the worker hint; post-processing exception → failed; a new job queued behind an old succeeded row → running; research first reply unreadable and second readable → done with exactly one extra call.
6. The report names any other status reader outside these two modules with the same shape (not changed here).

Issue verify plus manifest gates.

# Blocked if
procrastinate's listing cannot return finished jobs for a `queueing_lock` — stop and report.
