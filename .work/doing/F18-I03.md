# Objective
Turn triage results across a brand's campaigns into one decision queue through the existing `interrupts` inbox, plus a progress summary for the future home page.
# Done
1. Only `stop_loss` and `worse` exist in this batch. Both endpoints return `"kinds_available": ["stop_loss","worse"], "kinds_pending": ["scale_budget","refresh_creative"]`.
2. Two entries in `app/core/interrupts.py::CATEGORIES`, inserted before `ads_runtime_attention`: `ads_triage_stop_loss` → `{"severity": "money_loss", "label": "廣告停損待決定"}`; `ads_triage_worse` → `{"severity": "rule_warning", "label": "廣告變差待決定"}`. Messages respect `MAX_MESSAGE_LEN`.
3. `POST /api/ads/brands/{brand_id}/queue/refresh`: `triage.classify` for every non-closed campaign of the brand; `interrupts.enqueue(...)` one item per `stop_loss` / `worse` ad with `dedupe_key = f"ads-triage:{class}:{entity_id}:{window_end}"` and `action_url` pointing at the campaign; one transaction; returns the GET payload.
4. `GET /api/ads/brands/{brand_id}/queue`: read-only; open items via `interrupts.list_open(..., archive_stale=False)` for the two categories, plus `"counts"` per class across campaigns and `"total_ads"`.
5. Both routes live in `app/ads/triage_routes.py` and do their own `require_actor` + `require_brand`.
6. `docs/architecture/ads.md`: document the queue endpoints and the two categories.
7. Tests: enqueue idempotent within one window, raised again on a new `window_end`; a resolved item stays resolved until the window moves; 首頁待辦 ordering and counts unchanged for brands with no triage items.
