# Objective

One copy run produces one length - the one the brief asked for - and records which one.

Settled in ARCHITECTURE.md §5.5: the bands and their counts stay exactly as they are
(`validate.BODY_BANDS`: short 100-150 x5, medium 300-500 x3, long 800-1000 x2); only the number of
bands per run changes from three to one. `body_json` gains `"copy_length": "<band>"`.

# Done

- `prompts.copy_prompt(...)` takes `copy_length` and writes one shell-generated line into the
  worksheet section: `本次要出的長度：<中文標籤>（<lo>～<hi> 字，<count> 則）`, with the numbers read from
  `validate.BODY_BANDS` - never typed a second time.
- `app/departments/workbench/copy.md`: the fixed line 「本次要出的長度：短版／中版／長版都要。」 and the
  three-band bullet list are replaced by one instruction saying the shell names the length and the
  reply carries only that one top-level band key; the reply example shows one band. Everything else
  in the file (coordinates, headlines, descriptions, visual_tone, visual_concept, warnings, the two
  writing rules) is unchanged.
- `validate.check_copy(data, vocabulary, copy_length)` validates only the requested band; other band
  keys present in the reply are ignored, not reported. Headline, description, coordinate,
  visual_tone and visual_concept checks are unchanged.
- `jobs._run` reads `request_json.copy_length` (default `"short"`), passes it to the prompt builder
  and the validator, and writes `body["copy_length"]` next to the band list. `_shape_hint` keeps
  naming the band range for the fix round.
- New `app/tests/test_workbench_copy_length.py`: for each of the three lengths, a fake provider reply
  containing only that band passes validation and the stored `body_json` carries the matching
  `copy_length`; a reply carrying the wrong band fails with an item whose path is the requested band.
- Assertions in `test_workbench.py` that expect all three bands move to the new contract.
