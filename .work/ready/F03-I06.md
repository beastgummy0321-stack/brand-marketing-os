# Objective

採用策略 turns the strategy into real rows a person can edit. §0: it serves the **plan** link; its
input is the campaign's stored strategy and budget (nothing is re-asked); its output is
`ads_delivery_group` and `ads_ad` rows that the pack, the publish adapter and the outcome
attribution all key off; its trace is the `ads_action` row for every edit that happens after
publish and the `llm_task` row for the generated names; it is **core**.

# Done

- `app/departments/ads/delivery_plan.md` — the third and last new department file in F03. Given the
  strategy allocation, the brand facts and the coordinate vocabulary, it returns JSON only:
  `{groups: [{role, name, ads: [{name, coordinates: {audience, pain, angle, hook, proof, offer,
  format}}]}]}`. Shape limits stated in the file: ≤4 groups, ≤3 ads per group. Names are the
  tracking names the user will paste into the platform — readable, unique inside the campaign, no
  emoji, no platform jargon.
- `app/ads/plan.py` — `adopt_strategy(conn, org_id, brand_id, campaign_id, *, actor)`:
  calls `run_task` (`task_type="ads_delivery_plan"`), then writes the rows in one transaction —
  one `ads_delivery_group` per allocation role with `channel_key='meta'` (the only connected
  channel; the column exists so another channel is a row, not a code change), `daily_budget` from
  the strategy split ÷ days, and one `ads_ad` per leaf with its seven coordinates. Campaign moves
  `draft → ready`. Re-running on a campaign that already has rows **refuses** with a readable
  message unless the campaign is still `draft` (a second plan would orphan bound entities).
- Editing: `PATCH .../groups/{group_id}` (name, daily_budget, dates, role) and
  `PATCH .../ads/{ad_id}` (name, coordinates), plus `POST .../groups` / `POST .../ads` /
  `DELETE` for both. **Budget exists only on the group** — the ad payload has no budget field. Any
  edit to a row whose `local_state = 'bound'` also writes one `ads_action`
  (`kind='budget'|'date'|'pause'|'creative'`, before/after, `approved_by=actor`,
  `sync_state='pending_manual'`); an edit to an unbound row writes none (nothing to sync).
- A budget raise passes through `app/core/approval.py` exactly as the schedule flow does: the new
  daily total is checked against the brand's approved `max_daily_amount`, and over it the endpoint
  refuses with the existing error shape rather than silently allowing it.
- `frontend/src/lib/adsApi.ts` — types and calls for adopt + the edit endpoints.
- `app/tests/test_ads_plan.py` (the falsifier): adopting writes groups whose `daily_budget` sums to
  the campaign total ÷ days; every ad has seven coordinates and a unique name inside the campaign;
  adopting twice is refused; editing a bound group's budget writes exactly one `ads_action` with
  before and after and `sync_state='pending_manual'`, editing an unbound one writes none; a raise
  above `max_daily_amount` is refused.
