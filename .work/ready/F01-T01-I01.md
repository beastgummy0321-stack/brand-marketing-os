# Objective

Make `request_json.parts` the single authority for what a brief asks for, and stop branching on
`workbench_brief.kind`.

Settled in ARCHITECTURE.md §5.4 - implement exactly this, decide nothing:

`request_json` keys this module reads:
- `parts`: non-empty list, subset of `["copy","image_prompt","video_script","free"]`. Missing,
  empty, not a list, or containing an unknown name -> `ValueError("parts_unknown")`. It records what
  was **requested** and is never rewritten afterwards; what was actually **produced** is recorded by
  `workbench_output.part` (`_part_summaries` already reads it).
- `copy_length`: `"short"|"medium"|"long"`. Absent -> `"short"`. Present but not one of the three ->
  `ValueError("copy_length_unknown")`. Only meaningful when `"copy"` is in `parts`.
- `image_prompt_count` (1-30) required when `"image_prompt"` is in `parts`; `video_script_count`
  (1-5) required when `"video_script"` is in `parts`; both keep today's `count_out_of_range`.
- `promotion_note`: `str | None`, stored verbatim, not read by this issue.
- `use_brand_knowledge`, `free_text`, `product_ids`: unchanged.
- `on_image_texts` is **removed from the contract**: after this ticket nothing writes it (the form
  drops the field) and nothing reads it (the image-prompt job stops requiring on-image text). Delete
  the key from validation, from the route model and from the docstrings; do not leave a dead key.

`kind` is derived at submit time: more than one part -> `"ad_creative"`, otherwise the single part
name. It is written to the column for display only; nothing reads it to decide anything.

# Done

- `repository._parts_for(kind, request)` is replaced by reading `request["parts"]`; `submit_brief`
  derives `kind`, validates as above, and enqueues one job per requested part (same lock string and
  same per-part `count` argument as today). `parts` is always non-empty, so the "no part queued ->
  status done" branch goes away with it.
- `_CREATABLE_KINDS`, `_PARTS_BY_KIND` and `_validate_on_image_texts` are deleted. `create_brief`
  rejects nothing by kind and ignores any `kind` in the request body.
- `run_part` accepts any of the four part names (`ValueError("part_unknown")` only for a name
  outside the four), keeps `brief_closed` / `round_running` / count validation, and drops the
  adopted-headline precondition for `image_prompt` entirely. It does **not** modify
  `request_json.parts` - a brief may produce a part it never requested, and the output row is the
  record of that.
- `routes.py`: `NewBriefRequest.kind` and `NewBriefRequest`'s on-image-text handling are removed; the
  error tables lose `kind_unknown` and `on_image_texts_required` and gain `parts_unknown`
  (400, 「請選擇至少一種要生成的內容。」) and `copy_length_unknown` (400, 「文案長度只能是短版／中版／長版。」).
- **The one existing caller moves in this issue, so main is never red**: `app/schedule/jobs.py`'s
  `workbench.submit_brief(...)` call (around line 572) drops `"kind": "ad_creative"` and adds
  `"parts": ["copy"]` to its `request` dict. Nothing else in that call changes here - the node's
  `copy_length` and the period's `promotion_note` are added later by `F01-T02-I02`. Without this the
  new `parts_unknown` would be swallowed by that call site's bare `except Exception` (jobs.py:591)
  and tree expansion would silently produce zero briefs.
- `app/workbench/__init__.py`'s docstring documents the new `submit_brief` request shape - it is the
  contract the schedule module writes against.
- New `app/tests/test_workbench_parts.py`: a multi-part brief derives `kind='ad_creative'` and
  enqueues both parts; a single-part brief derives that part's name; `parts_unknown` and
  `copy_length_unknown` come back as 400; `run_part("image_prompt")` on a copy-only brief with no
  adopted output enqueues instead of raising, and leaves `request_json.parts` unchanged.
  `app/tests/test_workbench_api.py` has a fixture of the right shape - **copy it into the new file,
  do not import it**: that file is legacy and importing it would break the architecture checker.
- Assertions in `test_workbench.py` / `test_workbench_api.py` that encode the old kind rules move to
  the new contract - that is why this issue is a `legacy_migration`.

# Verify

`uv run pytest app/tests/test_workbench_parts.py -q` - the new file fails before the change (the
endpoint refuses `ad_creative`) and passes after. Then
`uv run pytest app/tests/test_schedule.py -q -k leaf` - the existing
`test_tree_success_submits_one_brief_per_leaf_and_stays_queued` still finds a queued brief per
deepest node, which is what proves the dispatch call site was moved with the contract.
