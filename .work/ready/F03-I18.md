# Objective

A campaign is allowed to have **no** success target. §0: it serves the **goal** link (the shape the
brief in F03-I03 writes and the verdict in F03-I12 reads); its input is the merged F03-I01 schema;
its output is `ads_campaign.success_target` nullable end to end (DB, repository, TypeScript); its
trace is the new migration file; it is **core**. This issue exists only to settle that contract
before F03-I03 writes drafts against it — it adds no behaviour of its own.

Decision (F03.md Decisions, 2026-09-12): a null `success_target` is a legitimate value, a made-up
number is not. The model returns `null` when it cannot defend a number from the data it was given
and says why in `success_basis`; the 結案 verdict treats null as 看不出; the strategy page shows
「尚未設定成功條件」.

# Done

- `supabase/migrations/20260913000002_ads_success_target_nullable.sql` — a **new** file (the applied
  `20260913000001_ads_tables.sql` is never edited), containing exactly:
  `ALTER TABLE ads_campaign ALTER COLUMN success_target DROP NOT NULL;`
  plus a header comment naming the module, this issue and the reason (「目標值可以是 null＝模型說不出
  有根據的數字；結案判 看不出」). **No CHECK constraint** — a target may be missing at any status,
  including a campaign that runs to the end and closes with 看不出; tying null to `status='draft'`
  would force the code to invent a number at publish time, which is the thing this feature forbids.
  `success_metric` stays NOT NULL: the campaign always says *what* it is judged on, only the number
  may be unknown.
- `app/ads/repository.py::create_campaign` — `success_target` becomes optional: `None` (or a missing
  key) is written through as SQL NULL. Everything else about the guard stays: a value that is
  present but not a number (a string, a bool — note `isinstance(True, int)` is true in Python, so
  reject `bool` explicitly) still raises `ValueError("success_target_unknown")`. Update the
  docstring so it states the new contract in one line. Do not touch the other required-field guards
  and do not change any other function in the file.
- `frontend/src/lib/adsApi.ts` — `CampaignDetail.success_target` becomes `number | null`. That is the
  only type change; nothing else in the file is re-shaped (`EntityBinding` and its users stay as
  F03-I01 left them). No component consumes this field yet, so no call site changes; if `tsc`
  reports one, fix it by rendering nothing rather than by widening another type.
- `app/tests/test_ads_model.py` — two falsifiers added next to the existing `create_campaign` tests
  (reuse `_campaign_payload`): a campaign created with `success_target=None` round-trips through
  `campaign_detail` with `success_target` still `None` (nothing fills it in, no exception); a
  campaign created with `success_target="便宜一點"` still raises `ValueError` with
  `success_target_unknown`. No new test file.
