# Objective
R6: the campaign budget cap (`constraints_json.budget`) becomes a soft warning the API enforces (Feature "Contracts → Budget scenarios"; rules in ads.md §6.32).

# Done
1. `budget.current_scenarios`／`reconcile_campaign` read the cap: `budget_cap`, per-row `over_cap`, the `cap` row, `recommended` moving to `cap` when the old recommendation is over; row labels per Contract. Works for stored pre-fix snapshots (read-time reconcile, as today).
2. `select_scenario` (and a custom total) over the cap without `confirm_over_cap: true` → 409 `over_cap_unconfirmed` with a message that states the amount over; with it → saved and `over_cap_confirmation` recorded. Within the cap, or no cap, behaves as today.
3. Edge tests: cap unset／0／negative (treated as no cap), total unknown (`null`), cap exactly equal to a total (not over), days unknown, custom total over.
4. The cap is editable after the wizard, in any campaign status (user ruling 2026-09-25: "不該定死"). Add `PUT /api/ads/brands/{b}/campaigns/{c}/strategy/budget-cap {budget_cap: int|null}`. A positive integer sets `constraints_json.budget`, null clears it, and 0, negative or non-integer is 422. It marks `field_sources.budget` as the user's. It never writes the platform, never changes `budget_planned` or the saved scenario, and never makes a handoff stale (the cap is an internal planning number). The next scenarios read reflects the new cap; a previously saved scenario that is now over the cap shows `over_cap` but stays saved. Tests cover set, clear, the 422 cases, a non-draft campaign, and a saved scenario becoming over the cap.
5. Frontend types: `BudgetScenarioRow.over_cap`, result `budget_cap`, `selectScenario(..., { confirmOverCap })`, `setBudgetCap(campaignId, value|null)`; `StrategyTab.test.tsx` factories set the new fields.
