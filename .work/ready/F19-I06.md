# Objective
The screens need a Chinese name for each result kind and the target page needs the list of kinds to choose from. Both I02 and I05 found that no such label or list exists anywhere; the frontend must not invent one. Add it once, in `app/ads`, platform-neutral.
# Done
1. New `app/ads/result_kinds.py`: `LABELS: dict[str, str]` for the shared result-kind vocabulary that adapters already emit (read `app/ads/adapters/*` read-only to enumerate the kinds actually produced — do not edit adapters, no platform name in this file), `label(kind) -> str` (unknown or `None` → the generic 「成果」, never a raw code), `options() -> [{"kind","label"}]` in a stable order.
2. `triage` items: `target` and `current` / `previous` views gain `result_label`. `GET/PUT …/target` response gains `result_label` and `result_kinds` (= `options()`). `PUT …/target` rejects a `result_kind` outside the vocabulary with the module's existing 4xx validation style (trust boundary); `null` stays allowed.
3. `frontend/src/lib/adsTriageApi.ts`: add the new fields to the types. Nothing else.
4. `frontend/src/components/ads/target/CampaignTargetPage.tsx`: card 1 becomes the segmented control from v7, options from `result_kinds`, saved through `putTarget`; delete the page's local kind→label map and use `result_label`. Update its vitest + the e2e spec (choose a kind, save, reload).
5. `docs/architecture/ads.md`: document the vocabulary file and the new fields beside the target and triage endpoint docs.
6. Tests: every kind an adapter can emit has a label (enumerate from the adapter tables so a new kind without a label fails the test); unknown → 「成果」; PUT with an unknown kind → 4xx and nothing stored.

The adapters' result kinds cannot be enumerated without editing an adapter, or an existing stored `result_kind` in test fixtures is outside the vocabulary — report.
