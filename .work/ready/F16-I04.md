# Objective
Give every campaign, system-built or imported, a resolvable target cost per result. Today `success_metric` is limited to
cpa, roas, purchases (`20260913000001_ads_tables.sql:22`) and imported campaigns have none ("未設定成功條件").
# Done
- The target cost lives in its OWN columns. Nothing in this feature ever writes `success_metric`, `success_target` or
  `success_basis` — overloading them silently corrupted close-out verdicts, learning cohorts, cold-start budgets, asset
  suggestions and the frontend metric label, all outside this issue's touch.
- A new migration `supabase/migrations/20260920000006_ads_campaign_target_columns.sql` (never edit the applied
  `..._0005`) adds `target_cost numeric NULL` and `target_basis text NULL` CHECK in (break_even, trailing_30, own),
  plus a CHECK that `target_cost` is stored only for basis `own` (break_even and trailing_30 are computed on read and
  store the basis only). In the same file it restores what `..._0005` widened: first assert no row uses
  `success_metric='cost_per_result'` (raise if any), then put the `success_metric` CHECK back to cpa|roas|purchases and
  drop the `cost_per_result`-specific basis CHECK. `result_kind` and `target_revision` from `..._0005` are kept.
- `targets.resolve(campaign)` (pure, no LLM) returns value, basis, result_kind and missing[]: a user-set value (stored
  `target_cost` with `target_basis='own'`) always wins; else break-even through the existing `budget.breakeven_cpa()` and
  `product_economics` when this campaign's own result is a purchase and a product is known (imported campaigns: explicit
  product choice, else missing contains "product"); else the trailing-30-day actual cost per result read from
  `aggregate()`'s `result_views`, labelled provisional, NULL-aware, surfacing `mixed_result_definition` /
  `needs_resync` in missing[]; nothing resolvable gives value None, never a default number, never zero.
- `result_kind` provenance: shared code never reads a Meta objective string. The adapter's objective→result-kind mapping
  is exposed through the existing reader/capability seam as one function ("result kind for this synced entity"), and
  import/sync fills `ads_campaign.result_kind` from the campaign-level entity ONLY when it is NULL — a user's later PUT
  choice is never overwritten by a re-sync. `_is_sales` then keys on `result_kind == 'purchase'` for imported campaigns
  and keeps the documented internal default.
- `GET` and `PUT /api/ads/brands/{b}/campaigns/{c}/target` with an optimistic revision like month budget; PUT writes only
  `target_cost`, `target_basis`, `result_kind` and `target_revision`, and accepts price or variable cost only by
  delegating to the existing product economics write path.
- Frontend API client functions and a `CampaignTarget` type only. `SuccessMetric` is NOT widened; the set-target screen
  belongs to phase 2.
# Verify
Targeted tests above: sales with and without cost, engagement trailing-30, no data, imported without product, user override.
Regression, from real-shaped fixtures rather than hand-injected dicts: a PUT leaves `success_metric`/`success_target`/
`success_basis` byte-identical, and close-out of an internal CPA campaign gives the same verdict before and after a PUT;
imported SALES + explicit product ⇒ break_even; imported ENGAGEMENT ⇒ trailing_30 from `result_views`; imported with an
unmapped objective ⇒ value None with missing[].
# Blocked if
Writing price or cost would require changing another module's table or public interface; then expose "missing" only and
block for a planner decision.
