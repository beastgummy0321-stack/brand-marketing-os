# Objective

The Campaign edit endpoint cannot produce a campaign the create endpoint would have refused. §0:
it serves the **goal** link (it protects what F03-I03 wrote); its input is the patch body and the
stored row; its output is the same `ads_campaign` row, minus three states it could previously be
put into; its trace is that a change to a platform-bound node is refused here and has to go through
an `ads_action` (§6.5) instead; it is **core**.

This is a planner gap found reviewing F03-I03, not a defect the worker introduced: F03-I03's `# Done`
asked for a plain field edit "nothing is bound to a platform yet" and never said what happens when
something *is* bound, or when only one of the two dates is sent. The contract is now in
`.work/features/F03.md` Decisions ("The draft PATCH cannot create a state the create path refuses").
Do not re-derive it — implement it.

# Done

All three in `app/ads/repository.py::update_campaign` where every caller already routes through
(`routes.py` is the only one), except the model-side filter which belongs in `app/ads/brief.py`:

- **Dates are validated on the merged row.** `update_campaign` computes the resulting
  `start_date` / `end_date` (patch value where present, stored value otherwise) and raises
  `ValueError("end_before_start")` when `end < start`. A patch that moves only `end_date` is the
  normal case, so validating the payload alone is not enough. `routes.py` maps the code to
  `brief.END_BEFORE_START_MESSAGE` (400).
- **A bound campaign's identity is not a field edit.** When the stored row's `local_state` is not
  `'unbound'`, a patch containing `name`, `start_date` or `end_date` raises
  `ValueError("campaign_bound")` → 400 with a readable Traditional Chinese message saying the
  Campaign is already paired with the platform and that the name / 投放期間 change has to go through
  the change flow that leaves an 異動紀錄. The other patchable fields (`objective`,
  `success_metric`, `success_target`, `success_basis`, `constraints_json`, `product_ids`) stay
  editable at **every** status — F03-I14's 成功條件 edit has to work on a campaign that is already
  running (a null `success_target` may be set late, F03-I18).
- **`context_json.product_ids` only ever holds ids that resolve.**
  - `app/ads/brief.py`: the ids the model returns are intersected with the brand's own product ids
    (`_products_context` already lists them — return them instead of collecting them twice); an id
    the model invented never reaches `context_json`.
  - `update_campaign`: a `product_ids` entry that is not one of this brand's products raises
    `ValueError("product_unknown")` → 400. Read the products through
    `app.brand_intelligence.repository.list_products` (the facade, §6.1) — no raw SQL against
    `product` from `app/ads`, `app/tests/test_architecture_boundaries.py` scans for exactly that.
- **Error codes are machine tokens.** `app/ads/routes.py`'s `_CREATE_CAMPAIGN_ERRORS` currently
  keys two entries by the Chinese sentence itself, so the API's `code` for a bad date is a Chinese
  sentence while every other code in the file is snake_case. `brief.py` raises
  `ValueError("dates_required")` / `ValueError("end_before_start")` and `routes.py` maps code →
  (status, message); the Chinese sentences stay exactly as they are, as `message` only. Keep
  `brief.DATES_REQUIRED_MESSAGE` / `brief.END_BEFORE_START_MESSAGE` as the message constants —
  `app/tests/test_ads_brief.py` asserts against them and the frontend reads `message`, never `code`.

# Verify

`uv run python -m pytest app/tests/test_ads_brief.py -q` — extend the existing file (same
FakeProvider setup, same style; the existing `BadDatesTest` asserts on the message constant, keep
it working). Four new falsifiers, each of which fails if the guard is removed:
1. a patch that moves `end_date` before the stored `start_date` is refused (and the stored row is
   unchanged);
2. a campaign whose `local_state` is `'bound'` (set it directly in the test's own `UPDATE`, no new
   repository function) refuses a `name` patch **and** still accepts a `success_target` patch;
3. a model reply naming a product id that does not belong to the brand leaves
   `context_json["product_ids"]` without it, and the draft is still created;
4. a patch carrying a foreign product id is refused with `product_unknown`.
