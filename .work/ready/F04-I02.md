# Objective

ARCHITECTURE.md §1 的第 2、3 條，兩個都在同一支檔案上、同一次改、同一組測試裡驗：

1. **大 prompt 不重送**。`gateway.run_task` 的重試迴圈（:252-280）失敗後原封不動再送一次同樣的
   `messages`；`max_retries=1` 掛在 16k／24k 輸入的呼叫點上（素材工作檯、判讀、建檔精靈），
   一次逾時就是再付一整份輸入的錢，而重送同一段內容多半也得到同一個結果。
2. **`llm_task.cost numeric(14,2)` 讓不到半分錢的呼叫記成 0.00**，而每月花費上限
   （`check_spend_cap` → `settings.org_ai_spent_this_month`）加總的就是這一欄——帳愈跑愈少。

§0 連結：**trace**（每次呼叫留下花了多少、為什麼）。`legacy_migration: true`：`app/llm/**` 是
legacy facade，這張票只在既有函式裡加一道上限＋改一個欄位精度，不搬呼叫端、不加新能力。

# Done

## 1. 超過門檻就不重試（一個地方，所有呼叫端）

在 `run_task()` 算 `max_attempts`（:252）的地方：先量這次要送出去的輸入大小
（`system` 的長度 ＋ 每則 message 的文字長度，content 是 list 時只加 `type == "text"` 的 `text`），
超過 `LARGE_PROMPT_CHARS`（新常數，**24000**，約 8k tokens 的保守換算，寫成模組層常數不要埋在
函式裡）就把 `max_attempts` 壓成 1。

- 被壓下來時，那一列 `llm_task` 失敗後的 `error` 尾端補一句人話：
  `（輸入過長，這次不自動重試——重送同樣的內容會再付一次同樣的錢，請直接再按一次。）`
  ——只補在被壓下來的情況，小 prompt 的錯誤訊息一個字不變。
- 呼叫端的簽章與 `TaskOptions` **不動**：`max_retries` 還是呼叫端說了算，這裡只是上限。
- 一行註解說明為什麼門檻用字元不用 token：gateway 拿不到 tokenizer，字元是保守的下界，
  而且這個判斷只需要分辨「大」與「小」。

## 2. `llm_task.cost` 精度

新檔 `supabase/migrations/20260913000003_core_llm_task_cost_precision.sql`（已套用的檔一律不改，
CLAUDE.md 鐵律）：

```sql
ALTER TABLE llm_task ALTER COLUMN cost TYPE numeric(14,6);
```

檔頭兩行註解：為什麼（`numeric(14,2)` 把不到半分錢的呼叫記成 0.00，每月上限加總的就是這一欄）、
以及這是 ALTER 不是 CREATE（`llm_task` 是既有的 core 表，本票沒有建任何新表）。

`gateway.py` 寫入 `cost` 的地方（:298-301 及截斷分支 :311-315）確認沒有自己 `round(…, 2)`；
有的話拿掉，交給欄位精度。沒有就不動。

## 3. 不要順手做的

不加 `cache_control`（那是 F04-I05 在真的重送同樣前綴的那一個呼叫點上做的）、不動
`input_context_hash` 的去重（它今天沒有消費端，加去重是另一個決定）、不改 `pricing.py` 的價目。

# Blocked if

- 本機 Supabase 沒起來（`supabase start`）導致 migration 套不上去：先起來再做；起不來就 release，
  不要把 ALTER 寫進任何已套用的檔。
- 壓 `max_attempts` 會讓既有測試紅（例如某個測試故意用大 prompt 驗重試兩次）：**不要改測試的
  意圖來配合**，release 並說明是哪一個測試、它在驗什麼。
