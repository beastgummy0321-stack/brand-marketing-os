# Objective

The JSON surface the four screens read and write, **including 核准整包** — the read side and the
write side of `completion`/`can_approve` are the same three lines of derivation, so they are one
issue and one review. The brief-shaped endpoints are **replaced**, not kept in parallel — their only
consumer is the page this feature retires. Shape rule unchanged (`routes.py` file header):
`require_actor` → `require_brand` → one repository call → wrap, and every `ValueError` a repository
function raises is translated by this route's own small error table. Nothing in `routes.py` decides
anything.

# Done

## Endpoints

All `/api/workbench`, brand-scoped; `GET /styles` stays as it is.

- `GET  /brands/{b}/packs?status=&q=&sort=` → `{"packs": [PackCard]}`. `status` ∈
  `all|pending|running|awaiting_approval|done` (default `all`), `q` matches pack name, set name and
  the pack's context labels, `sort` ∈ `updated|created|progress` (default `updated`); unknown value
  → `ValueError` → 400.
- `GET  /brands/{b}/packs/{p}` → `{"pack": PackDetail}`, 404 `pack_unknown`.
- `GET  /brands/{b}/sets/{s}` → `{"set": SetDetail}`, 404 `set_unknown`.
- `POST /brands/{b}/sets/{s}/products/{part}/run` `{count?}` → `{"set": SetDetail}`; reuses the
  existing run-a-part errors (`part_unknown`, `count_out_of_range`, `brief_closed`,
  `round_running`) and adds `pack_approved` → 409 「這個任務包已核准，選定已鎖定。」
- `POST /brands/{b}/sets/{s}/versions/{v}/select` and `DELETE` the same path →
  `{"set": SetDetail}`; `version_unknown` → 404, `pack_approved` → 409.
- `POST /brands/{b}/packs` → `{"pack": PackDetail}` — 自由創作's create. Body: `name?` (server
  falls back to 自由工作 #n, n = this brand's free-job pack count + 1), `free_text`, `product_id?`,
  `style_key`, `sets` with their `required_outputs` and their per-part generation `count`,
  `summary`. It goes through the same `submit_pack` contract as an upstream — no second write path.
  `source_kind` is forced to `"free_job"` here; a client may not pick it.
- `POST /brands/{b}/packs/{p}/completion` `{key, checked}` → `{"pack": PackDetail}`.
- `POST /brands/{b}/packs/{p}/approve` → `{"pack": PackDetail}`.
- `POST /brands/{b}/packs/{p}/close` → `{"pack": PackDetail}` (the ⋯ menu's 關閉任務包).

## Shapes

`repository` assembles them from the F02-I02 derivation helpers — no state logic in `routes.py`.
Every field exists because a reference image draws it. Part labels are **one map in the API**:
`copy`→文案, `image_prompt`→圖片, `video_script`→腳本 (`free` is retired from new packs,
`.work/features/F02.md` Decisions — it can never appear in `required_outputs`).

- `PackCard`: `id, name, subtitle, source_kind, source_label, status, sets_total, sets_done,
  progress_pct, next_step {set_id, set_name, part, label} | null, counts [{part, label, selected,
  required}], updated_at`. `next_step` = first set that is not 已完成, first of its products that is
  not 已選定; `null` when the pack is done.
- `PackDetail` = `PackCard` ＋ `created_at, source_ref, meta {platform, goal, sets_required},
  summary {situation, angle, style, audience, key_messages, reference_link}, completion [{key,
  label, ok, overridden}], can_approve, blocking_text, sets [{id, name, status, cells [{part, label,
  state, selected, required, text}]}]`.
  **`cells[].text` is the whole of the cell copy** — `已選定／需要` (2／5), `未生成`, `—` — produced
  by the F02-I02 derivation, never re-spelled in the browser (`.work/features/F02.md` Decisions).
- `SetDetail`: `id, pack_id, pack_name, name, status, chips [platform, style, size], siblings
  [{id, name, angle, status}], required_parts (dispatch order), products {part: {state, selected,
  required, generation_settings {…}, versions [{id, version_index, generation_round, selected_at,
  body}]}}, image_generation {connected: false}`. Versions are newest round first. The prompt-view
  payload and the port flag are filled in by F02-I05 — leave `image_generation.connected` hard
  `false` here and do not invent a provider.

## 核准整包 (`ARCHITECTURE.md` §5.5)

Approving closes the pack, locks its selections, and leaves a state the upstream can read. It never
calls the upstream and never blocks it: the signal is a read, not a callback, so the dependency
stays one-way (the workbench must not import `app.schedule`).

- 完成條件 is a fixed three-item checklist stored in `workbench_pack.completion_json`:
  1. `required_outputs_met` — **computed** from the F02-I02 derivation (every set 已完成);
     label 「完成所有素材組的必要文案與圖片」.
  2. `brand_rules_checked` — human tick, label 「確認內容符合品牌規範」.
  3. `ready_to_report` — human tick, label 「可核准整包並回報上游」.
  No brand-rule engine is built in this issue and none is implied: item 2 is a person saying they
  looked.
- `POST …/completion` ticks or unticks one key. Ticking `required_outputs_met` while it is
  computed-false records an **override** (`{"checked": true, "overridden": true, "at": …}`) — the
  repository accepts it; the warning the user sees is the frontend's job (F02-I08) and it is
  skippable. `key_unknown` → 400.
- `POST …/approve`: every check must be green or ticked, else 409 `completion_incomplete`
  「還有完成條件沒有滿足。」 On success `approved_at = now()`, pack status becomes 已完成, and
  selections lock: `select_version`, `deselect_version` and `run` all raise `pack_approved` → 409.
  Approving twice is idempotent, not an error. There is no un-approve — nobody has asked for one.
- `PackDetail.completion`, `can_approve` and `blocking_text` 「尚有 n 個素材組未完成」 come from the
  same derivation; no second copy of the rule.
- Public entry: `pack_for_source(conn, org_id, brand_id, source_kind, source_ref)` is exported from
  `app/workbench/__init__.py` with a docstring stating its shape (`id`, `name`, `status`,
  `approved_at`, `sets_total`, `sets_done`) — this is the whole of the 「可以下一步」 signal and
  F02-I04 is its only caller.
