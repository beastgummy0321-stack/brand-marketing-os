# Objective

全站跑最多次的模型呼叫是素材工作檯的 `workbench_copy`／`workbench_image_prompt`（實測 130 列，
平均輸入 ≈10k tokens 淨值）。`app/workbench/jobs.py::_compile_brand_context`（:49-68）**對
`request_json.product_ids` 的每一個 id 各編一次品牌上下文**，品牌層（規則／宣稱／品牌事實）因此
重複 N 次；而 `app/ads/assets.py:129` 派工時送的是**整個 Campaign 的所有商品 id**
（`campaign_product_ids`）。一個三商品的 Campaign＝每一則廣告的每一次生成都付三份品牌知識的錢。

修在源頭、在我們自己的模組裡：一個素材組就是一則廣告，一則廣告只有一個商品（ARCHITECTURE §5.4）。
派工時只送那一則廣告自己的商品。§0 連結：**artifact**（交棒出去的是一則廣告要的東西，不是整個
Campaign 的目錄）。

不改 `app/workbench/**`：工作檯那支迴圈對「真的有多個商品」的自由創作呼叫端還是對的，
它不是這次的成本來源。

# Done

`app/ads/assets.py::dispatch_pack` 的 `sets[].request.product_ids`：

- 改成 `[pid] if pid else []`，其中 `pid = ad.get("product_id") or fallback_product_id`
  ——跟同一個 dict 裡 `"product_id"` 用的是**同一個值**，不要各算一次（抽一個區域變數）。
- `product_id` 與 `fallback_product_id` 都是 `None` 時送 `[]`：工作檯那邊
  (`jobs.py:302-303`) 會落到 `use_brand_knowledge and product_ids` 為假的分支，品牌上下文整段
  不進 prompt。這是正確的——沒有商品就沒有商品層知識可談，**不要**為了填滿而送整個 Campaign 的
  商品。
- 三行註解說明為什麼（重複 N 份品牌層 ＋ 一則廣告只打一個商品 ＋ ARCHITECTURE.md §1 第 1 條）。

其他欄位一個字都不動（`summary`、`context`、`required_outputs`、`copy_length`、
`image_prompt_count`、`style_key`）。

# Blocked if

- `ad["product_id"]` 在既有資料裡幾乎都是 `None`，而 `fallback_product_id` 也是 `None`，
  導致所有既有 Campaign 的派工從此都沒有品牌知識——先去看 `plan.adopt_strategy` 有沒有在建
  `ads_ad` 時寫 `product_id`；如果它從來不寫，release 並回報（那是 F05 的素材分頁要處理的洞，
  不在這張票裡順手改 `plan.py`）。
