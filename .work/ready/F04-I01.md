# Objective

ARCHITECTURE.md §1「What an external model is allowed to cost」第 1 條：**每一個進 prompt 的
清單，上限只寫在一個地方**。今天 `app/llm/context_compiler.py::compile()` 只對規則套
`rule_cards`「rule_prompt_cap」（`_select_rules_for_prompt`，:40-57），宣稱（claims）與品牌／
產品事實一列不漏全部送出去（:127-153）。這支函式是全站每個部門任務的共同上游（ads brief、
素材工作檯、建檔精靈、品牌報告…），所以上限加在這裡一次，等於所有呼叫端都有上限——比每個部門
各自截斷少一份程式、也少一個會忘記的地方。§0 連結：**context**（每一條鏈都要先讀品牌知識）。

不是要改 schema、不是要改 `rule_prompt_cap` 卡、不是要動規則那一半的排序規則。

`legacy_migration: true` 的理由：`app/llm/**` 是 legacy（ARCHITECTURE.md §2），這張票在既有的
legacy facade 上加一道上限，不是把新能力放進 legacy，也不搬動任何呼叫端——範圍就是這支函式。

# Done

## 1. 事實與宣稱各自有上限，讀同一張卡

在 `compile()` 裡，規則之外的三份清單各自截斷，全部讀
`rule_cards.get_value(conn, brand_id, "rule_prompt_cap", "max_active_rules")` 的同一個值
（預設 20；讀一次，別呼叫三次）：

- `claims`（`format_claims()` 之前）：`claim_type == "forbidden"` 的**全部保留**（那是「絕對
  不能講」，截掉會讓模型講出不能講的話——這是安全邊界，不是成本），其餘（approved／high_risk）
  依 `confirmed_at`（沒有就 `created_at`）新到舊排序後取前 `cap` 條。
- `brand_facts`：依 `confirmed_at`（沒有就 `created_at`）新到舊取前 `cap` 條。
- `product_facts`：同上，各自一份 `cap`（品牌事實與產品事實不共用一個額度）。

`knowledge_item_ids` 只收**真的進了 prompt 的那些**列的 id——這個清單是稽核用的「這次餵了什麼」，
截掉的列不能留在裡面（否則 `llm_task` 說謊）。

## 2. 截斷要講出來，不要靜靜消失

被截斷的段落尾端補一行（只在真的有截斷時出現，沒截斷時一個字都不加，既有 prompt 不變）：

- 事實：`（另有 N 筆較舊的品牌事實沒有列出）` ／ `（另有 N 筆較舊的產品事實沒有列出）`
- 宣稱：`（另有 N 筆較舊的宣稱沒有列出）`，只加在「可以講」那一段，`forbidden` 段不加
  （它沒有截斷）。

理由寫成一行註解：模型看到「還有更舊的」跟看到「就這些」會做出不同的推論，靜默截斷會讓它以為
這就是品牌的全部。

## 3. 檔頭註解

檔案開頭的「硬性規則」清單新增第 6 條，說明事實／宣稱的上限與 `forbidden` 的例外，並註明
ARCHITECTURE.md §1 是它的出處。不要重寫既有五條。

# Blocked if

- `rule_cards` 沒有辦法在沒有 DB 連線時取值（既有測試 `test_rule_cards.py:43` 說可以，`conn=None`
  也回得出預設值）——如果實際上不行，release 並說明，不要在這裡自己寫一個常數當備援。
- 為了排序需要 `confirmed_at`／`created_at` 以外的欄位（例如某個 repository 的回傳沒有時間欄位）。
  照實 release，不要改 repository 的 SELECT 清單。
