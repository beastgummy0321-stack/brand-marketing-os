# Objective

The tenant boundary runs before field validation on **every** ads route. §0: it serves no new link —
it is the guard that makes every link's endpoint safe; its input is an unauthenticated or
wrong-tenant request; its output is 401 / 404 instead of 422; its trace is the two site-wide sweeps
going green again; it is core.

`harness integrate feature F03` found four ads routes answering **422** where the whole rest of the
backend answers 401 (no `Authorization`) or 404 (another org's brand):
`POST …/campaigns/{id}/strategy/scenario`, `POST …/campaigns/{id}/groups`,
`POST …/campaigns/{id}/ads`, `POST …/ads/{ad_id}/asset-ready`. Cause: their Pydantic body models
have fields with **no default**, so FastAPI's body validation rejects the request before
`web.require_actor` / `web.require_brand` ever run. A 422 on a missing `Authorization` header leaks
"this route exists and this is its body shape" to an anonymous caller and, worse, tells the sweeps
nothing about whether the guard is there at all.

# Done

- **The rule** (the existing convention — `app/workbench/routes.py` `NewFreePackRequest` /
  `CompletionRequest` carry it in a comment: 「租戶界線先於欄位驗證（既有慣例）：全部給預設值，
  真正的驗證在下面的 handler」): **every field of every request model in `app/ads/routes.py` has a
  default**, and the refusal for a missing/empty value is raised inside the handler (or by the
  domain function it calls), never by Pydantic. Write that rule once as a comment at the top of the
  models section of `app/ads/routes.py`, naming this issue, so the next model added does not
  re-open it.
- **Audit all of `app/ads/routes.py`, not only the four failing routes.** As measured 2026-09-13
  exactly four models violate the rule; `CreateCampaignRequest`, `PatchCampaignRequest`,
  `PatchGroupRequest`, `PatchAdRequest`, `PublishRequest`, `CloseCampaignRequest` already comply.
  The four:
  - `SelectScenarioRequest.scenario_key: str = ""` — `strategy.select_scenario` already raises
    `campaign_unknown` / `scenario_unknown`, so no new handler code.
  - `CreateGroupRequest`: `name: str = ""`, `role: str = ""`, `daily_budget: float | None = None`.
    `plan.create_group` already raises `name_unknown` / `role_unknown` / `daily_budget_invalid`;
    because the parameter is typed `float`, the handler refuses `None` **before** the call —
    `raise web.ApiError(400, "daily_budget_invalid", _GROUP_EDIT_ERRORS["daily_budget_invalid"][1])`
    — reusing the existing dict entry, never retyping the sentence (pyright would also reject
    passing `float | None`).
  - `CreateAdRequest`: `group_id: str = ""`, `name: str = ""`, `coordinates: dict = {}`.
    `plan.create_ad` already raises `group_unknown` / `name_unknown` / `coordinates_incomplete`.
  - `AssetReadyRequest.ready: bool | None = None`, with one new entry
    `"ready_invalid": (400, "請指定要勾選或取消。")` in `_AD_EDIT_ERRORS` and the same
    raise-from-the-dict shape in the handler (this is exactly what `set_pack_completion` does with
    `checked_invalid`).
- **No behaviour change for a well-formed request**, and **no message invented**: every code stays
  the snake_case machine token it already is and every sentence comes from the dicts already in the
  file. The only observable change for a malformed request is 422 → 400 with a 繁體中文 `message`;
  `frontend/src/lib/adsApi.ts` reads `message` only, so no frontend issue is affected and no
  frontend file is touched.
- **Do not** add a `dependencies=[Depends(require_actor)]` on the router and **do not** reorder the
  handler bodies: every ads handler is already `require_actor` → `require_brand` → one
  domain/repository call → wrap (the shape `app/ads/routes.py`'s own docstring declares). The bug is
  the model, not the ordering inside the handler.
- **`app/tests/test_ads_routes_guard.py`** (new, owned by `ads` via `app/tests/test_ads*.py`) is the
  falsifier that lives with the module. Copy the `TestClient` / imports header of
  `app/tests/test_ads_assets.py`; do not import anything the other ads tests do not already import.
  It enumerates `main.app`'s routes whose path starts with `/api/ads/` (walk the route table, do not
  hand-list paths — a route added later must be covered automatically) and asserts, for every
  method except HEAD/OPTIONS:
  1. with **no `Authorization` header** and `json={}`: status 401 and the body is the
     `{"error": …}` envelope;
  2. with a valid token for org A against a brand belonging to org B and `json={}`: status 404;
  3. plus three targeted cases proving the validation did not disappear with the defaults, against
     a real campaign of the caller's own brand: `POST …/groups` with `{}` → 400
     `daily_budget_invalid`; `POST …/ads` with `{}` → 404 `group_unknown`; `POST …/ads/{ad_id}/
     asset-ready` with `{}` → 400 `ready_invalid`.

# Blocked if

**Never weaken the sweeps.** Do not edit `app/tests/test_identity_auth.py` or
`app/tests/test_identity_tenant_routes.py` at all: no new entry in `_SWEEP_SKIP`, `SKIP` or
`_MINIMAL_BODIES` for any `/api/ads/` route, no lowering of the `checked > 90` / `checked > 80`
thresholds, no relaxing of the 401-envelope or 404 assertion. An ads route that cannot be made to
answer 401/404 with an empty body is a design problem in that route — stop and report it with the
path and the reason rather than listing it as an exception. Same for the new guard test: it must not
grow an exception list for a route someone could not fix.
