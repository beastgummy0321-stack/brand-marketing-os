# Objective
R2: a launch whose plan changed after approval gets a way out — see what changed, re-approve the current plan, or revert to the approved one (Feature "Contracts → Stale launch"; rules in ads.md §6.32).

# Done
1. `launch_stale` on `GET …/handoff`, computed on read by comparing `plan_json.launch_snapshot` with `change_control_launch.snapshot`; diff rows name the item (campaign／group／ad), field, before, after, with Chinese field labels; `changed_at` = latest update time of the changed rows when known, else null.
2. `POST …/handoff/launch/reapprove`: same `content_hash` guard and month-budget preflight as `approve`; creates the next launch set version from the current snapshot, supersedes the old one; handoff items whose expected fields are unchanged keep their verification, binding and evidence; changed or new items start pending; removed items drop.
3. `POST …/handoff/launch/revert`: writes the approved values of the diffed fields back to the plan rows in one transaction, after which `launch_stale` is null and the original approval stands; refuses with `revert_blocker` when a value cannot be restored exactly (e.g. a material revision that no longer exists).
4. New `app/tests/test_ads_launch_stale.py`: budget raised after approval (re-approve passes/fails preflight), ad renamed (revert), a verified item kept, a concurrent edit (hash mismatch → 409), revert with a blocker, a set that is not stale (both routes refuse).
5. Frontend `HandoffWorkspace` gains required `launch_stale`; listed factories set it.

# Verify
Issue verify plus manifest gates.

# Blocked if
A handoff item's verification cannot be carried to a new set without rewriting `ads_action` history another feature reads — stop and report.
