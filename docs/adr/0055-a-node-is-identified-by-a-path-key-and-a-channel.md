# A node is identified by a path key and a channel

2026-09-03, T3 station ①. Settled with the user, who twice sent the plan back: once for not
checking what the later tickets need, and once for writing Meta into the foundation.

## The problem this closes

Before this decision the codebase named a campaign-tree node **three different ways, none of
them able to survive**:

| where | how it names a node | what breaks |
|---|---|---|
| `llm_task.context_scope_json.bound_external_ids` (`app/schedule/routes.py:613`) | the level-1 node's **name**, as a dict key | two sibling nodes with the same name collapse into one; the map dies with the tree row, and `_latest_task_row` only ever reads the newest |
| `creative_slot.ad_node_name` + `source_tree_task_id` (T1b, shipped) | the level-3 node's **name** | `creative.py:138` compares with `set()`, so two same-named leaves are already indistinguishable today |
| `ad_set_period_membership.ad_set_external_id` (T2, shipped) | the platform's id, with **no link to a node at all** | the table has no writer; ADR 0053's overlap rule ships one level coarser than it was written for |

Verified on 2026-09-03: `llm_task`, `creative_slot`, `creative_candidate`,
`ad_set_period_membership` and `campaign_period` all hold **0 rows**. Every change below is
therefore a schema change with no data migration. This is the cheapest day it will ever be.

## 1. The identity is `node_key`

`node_key` is the node's position in the tree, 1-based, joined by dots: `'1'`, `'1.2'`,
`'1.2.3'`. It is generated by walking the tree in document order (depth-first, pre-order) — the
same order `_leaf_ad_node_names` and `_collect_nodes` already use, so the numbering is a
property of the frozen `rendered_output` and is recomputed identically on every read, exactly
like `tree_from_task_row` recomputes everything else.

Every table that names a node names it this way. **No table stores a node's name as its key.**

A `node_key` is only unique inside one channel's tree, so a row that carries one must also pin
the channel — either with its own `channel_id` (`channel_entity_map`, `period_node_membership`)
or through a column that already implies it (`creative_slot.source_tree_task_id` points at the
`llm_task` row whose frozen `context_scope_json.platform` *is* the channel). Adding a redundant
`channel_id` to `creative_slot` would force `ad_channel`'s lazy row creation into the creative
path, which generates before anything is bound; it is left off deliberately.

Rejected: a per-node UUID minted at expansion time. The tree is not stored — it is recomputed
from `rendered_output` on every read (`tree.py`'s frozen decision 1, `plan.py`'s
`plan_from_task_row` before it). A minted id would have to be stored somewhere, which means
storing the tree, which is the decision T2 and T1b were both built on top of.

## 2. The idempotency key carries the channel — this amends ADR 0050

ADR 0050 states the key as `unique(org_id, brand_id, node_key)`. That is Meta-only thinking and
**is corrected here**: the key is

```
unique(org_id, brand_id, channel_id, node_key)
```

`app/schedule/platform_objectives.json` already lists three platforms (`meta` enabled,
`google` and `tiktok` disabled) and a plan is generated **for one platform**
(`PlanRequest.platform`, validated at `routes.py:402`). A position-based key is not
channel-specific, so the Meta tree's `1.2` and the Google tree's `1.2` are the same key: the
second channel a brand runs would collide on its first write. Constitution rule 3 — the second
channel must be a switch, never a migration — makes fixing this later the wrong order.

## 3. Depth is a number, never the platform's word for the level

`channel_entity_map` carries `depth`, an integer on the same 1-based scale as the tree's
existing `budget_level`. It must **never** be a CHECK over `('campaign','adset','ad')`: those
are Meta's words. `tree.py` already refuses to hardcode them — `levels` is three strings the
agent returns ("平台自己對三層的叫法，外殼從不寫死") and `budget_level` says which of them
carries the budget (Meta 2, Google 1) — and T4's `ad_channel.spec` is specified to hold the
level **count**, so the number of levels is itself per-channel.

`depth` is a `GENERATED ALWAYS AS ... STORED` column computed from `node_key`'s segment count,
not a value the writer supplies. It is derived data, so the database derives it; there is no
way for it to drift from the key it describes. The CHECK has a lower bound and **no upper
bound** — a three-level cap belongs to `tree.py`'s validation, not to the schema.

## 4. Re-expanding the tree: the position keeps its binding only if the name still matches

A binding row stores `node_name_at_bind`. When a tree is re-expanded and a node at the same
`node_key` has a different name, the row is not reused: it moves to `local_state = 'orphaned'`
and the screen shows that node as unbound. Same position **and** same name → the binding is
kept, which is what makes "look at another version of the plan" cheap.

`local_state` carries all three values from day one: `mapped` · `orphaned` · `retired`.
It is ours. `external_status` is the platform's own word, stored verbatim — for Meta that is
`effective_status`, whose documented values are ACTIVE · PAUSED · DELETED · ARCHIVED ·
IN_PROCESS · WITH_ISSUES (developers.facebook.com/docs/marketing-api/reference/ad-campaign-group/,
read 2026-09-03). We never map it onto our own vocabulary; a channel we have not met yet will
have words we have not met yet.

Reading a tree never writes. The name comparison decides what the screen shows; only the bind
route changes `local_state`, and it does so by upserting on the idempotency key — which is what
that key is for.

**A rebinding overwrites, and no history is kept.** Constitution rule 7 forbids answering "what
was true then" with a current-state column, so this is a deliberate exception with a named
consumer test: nothing today reads "which entity was this node bound to last month". Spend is
read by the external id we currently hold. The day something needs the history — a node rebound
in the middle of a settled period, whose old entity's spend then belongs to nobody — the answer
is a `channel_entity_map_version` table shaped like `campaign_period_budget_version`, not a
column on this one. Written down so the first person to hit it does not rediscover it as a bug.

Rejected: reusing the position unconditionally (silently rebinds to an ad whose content was
replaced) and voiding every binding on re-expansion (re-matching the whole tree to look at a
second plan).

## 5. `ad_channel` is born here, per organisation, created on first use

`channel_entity_map.channel_id` is a real foreign key from day one, so `ad_channel` is created
by T3 rather than T4. T4 keeps the rest of it — the five capability flags, `spec`,
`last_data_at`, `data_lag_days` — and the credential table that replaces `meta_credential`.

**The table is per organisation**, because constitution rule 2 admits no exception and the
`org_id` gate admits exactly two documented tables (`organisation`, `app_user`,
`test_org_isolation_all_tables.py:20`), neither of which may be widened. The precedent is
`app_setting`: machine-wide settings, still `org_id NOT NULL`. The cost is that platform-wide
facts (a channel's level count, its minimum daily budget) will be stored once per organisation.
That cost is what rule 2 buys, and it is named here so nobody rediscovers it as a surprise.

Rows are created **lazily, on first use** — the first time an organisation binds anything on a
channel, `INSERT ... ON CONFLICT DO NOTHING`. No provisioning writer in another module, no
backfill over existing organisations, and T3's schema ticket stays genuinely dormant.

`ad_channel` is org-scoped and therefore brand-agnostic; its entry in
`BRAND_AGNOSTIC_EXCEPTIONS` carries that reason in writing, the same shape as `meta_credential`
before it. This is the list's documented purpose, not a widening of it.

The picker on the schedule form keeps reading `platform_objectives.json` until T4 moves it.
Two sources for "which platforms exist" would be one too many, so T3 **does not** migrate that
file; it only creates the table the foreign key needs.

## 6. `ad_set_period_membership` becomes `period_node_membership`

The table T2 shipped is renamed and repointed:

- `ad_set_period_membership` → `period_node_membership`
- `ad_set_external_id TEXT NOT NULL` → `node_key TEXT NOT NULL` (+ `channel_id`)

"Ad set" is Meta's word for the level that carries the budget. On Google that level is the
campaign. ADR 0053's rule was written about **the budget-carrying node**, not about ad sets, and
the table name should say what the rule says. The table holds 0 rows and has no writer, so the
rename costs one migration file today and a data migration on any later day.

ADR 0053 §4 is unchanged in substance: for a given node on a given day, the covering membership
whose period is shortest takes 100%; equal length splits by `allocation_weight`. What changes is
only that the subject is now nameable — which is what ADR 0053 said T3 would do.

## 7. Levels 1 and 2 are bound here; level 3 waits for T5

- **Level 1 (campaign)**: already possible — `graph.list_campaigns` exists.
- **Level 2 (the budget-carrying node on Meta, the ad set)**: bound here, because it is what
  gives `period_node_membership` a writer and refines ADR 0053's overlap rule from "the brand's
  spend that day" to "this node's spend that day". It needs one new read, verified against the
  official reference on 2026-09-03: `GET /{campaign_id}/adsets`
  ("Edge query from Ad Campaign to Ad Sets",
  developers.facebook.com/docs/marketing-api/reference/ad-campaign-group/adsets/), returning
  AdSet objects whose `id`, `name`, `campaign_id`, `status` and `effective_status` fields are
  documented at developers.facebook.com/docs/marketing-api/reference/ad-campaign/.
- **Level 3 (ad)**: the schema holds it — `depth` has no upper bound and the key is the same —
  but T3 does not bind it. Its only consumer is the seven-dimension coordinate link
  (`creative_candidate` → the published ad → `meta_entity_spend`), which is T5's job, and
  there are no real performance numbers to verify it against until T5 runs. Opening it is more
  rows, not a migration.

`creative_candidate.published_ad_external_id` (T1b, zero writers) is **not** the ad-level map.
`channel_entity_map` is the single place a node is tied to a platform entity; T5 decides whether
that column becomes a denormalised convenience or is dropped.

## 8. What stays Meta-specific on purpose

Ad-account tables stay one-per-channel: `meta_ad_account`, `brand_meta_ad_account`, and one day
`brand_google_ad_account`. ADR 0050 plans no generic account table, and inventing one here would
put T3 and T4 in the same file. `brand_meta_ad_account.allocation_weight` is therefore a
Meta-shaped column, deliberately.

The bind *action* is also Meta-specific — `_run_bind` calls `app.meta` directly, which the
schedule contract already allows. The channel adapter layer is T4's, not T3's.

## 9. Dormant columns, and what they will mean

- `brand_meta_ad_account.allocation_weight` — no writer, no reader in T3. It exists because one
  ad account bound to two brands would otherwise have the same day's spend counted twice by
  both. The application layer blocks the second brand today; the schema does not (ADR 0050).
- `learning_reset_at` — no writer in T3. Its meaning is fixed by
  `app/departments/ads/ads-core.md:47`: **pausing does not reset learning; editing the content
  does.** Written down here so the first writer does not invent a different rule.

## 10. Considered and rejected

Offered at the premise check and not chosen — recorded so they are not re-proposed:

- **Fix the JSON blob instead of adding a table** (key it by path, stop reading only the newest
  row). Cheapest, but it gives no idempotency key against creating a duplicate ad, nowhere to
  put the platform's status or the learning reset, and T5 would build this table anyway.
- **Do nothing this round.** The database holds 0 bindings, so the bug has never bitten a real
  user. Rejected because T2 and T1b have already shipped tables that are waiting on it.
- **Run a cheap experiment first** (bind a real campaign by hand, re-expand, watch it break).
  Rejected on cost: the Meta account binding was wiped by a `db reset` and would have to be
  rebuilt first.
- **Bind level 1 only** — the plan's own first recommendation, withdrawn after checking what T2
  and T1b left behind (see the table at the top).
- **Bind all three levels now.** Rejected: level 3's only consumer is T5, and it cannot be
  verified without real performance data.
- **`channel_id` as plain text now, foreign key added by T4.** Rejected against constitution
  rule 3 — that ALTER is a migration, and rule 3 says opening a deferred feature must not need
  one.
- **Move T4 ahead of T3.** Rejected: T4 also replaces the credential table, which is the
  permission path, and pulling it forward makes this round much longer.

## 11. An ad that belongs to no period falls back to the day's owner

ADR 0053 §4 promised T3 would refine the subject of the overlap rule from "the brand's spend that
day" to "this node's spend that day", and `period_node_membership` is the table that makes it
nameable. But a brand's Meta account also holds ad sets that were never built from a tree —
opened by hand, or left over — and a node-level settlement that counted only membership rows
would drop their spend, breaking the one invariant ADR 0053 says matters most: **the sum over all
periods equals the money actually paid to Meta.**

Settled by the user, 2026-09-03. Spend on a given day is split in two:

- **Registered** — an ad set with at least one membership covering that day goes to the period
  that owns *it* on that day, by ADR 0053 §4's rule applied to the memberships (shortest period
  wins, ties split by `allocation_weight`).
- **The remainder** — everything else that day goes to the period that owns *the day* at brand
  level, by ADR 0053 §4's rule applied to the periods' own date ranges. That is today's
  behaviour, unchanged, applied to what is left.

Both parts are clipped to the period's own `[start_date, end_date]`; a membership reaching
outside its period's dates never drags outside spend in. A day covered by no period is taken by
nobody, exactly as today.

**Revenue is not split this way.** `channel_revenue_summary` has no node dimension, and ADR 0053
already says attributing revenue to an ad is T5/T6's problem. Revenue keeps the brand-level rule
in full.

Rejected: showing unregistered spend as a separate "unassigned" figure. More honest in the
abstract, but it puts a number on the settlement screen that reconciles with nothing, and the
invariant above is the one the user actually settles against.

## 12. What we looked at (reuse-first §2)

- **Terraform's resource addressing.** Instances created with `for_each` are addressed by a
  stable key (`<TYPE>.<NAME>[<KEY>]`, "Terraform identifies instances by the map key or set
  member using the value provided to `for_each`",
  developer.hashicorp.com/terraform/language/meta-arguments/for_each, read 2026-09-03) rather
  than by position — the same shape as this decision's `node_key`. What we did **not** find, and
  therefore do not cite: an official page stating what happens when a positional collection is
  reordered. Our §4 name check is our own answer to that risk, not a copied one.
- **Nothing else found.** No open-source project was located that maps a generated ad plan onto
  a platform's live objects; the ad-platform SDKs we can read (Meta's Marketing API) define the
  platform side only. Recorded so the search is not repeated next month.
