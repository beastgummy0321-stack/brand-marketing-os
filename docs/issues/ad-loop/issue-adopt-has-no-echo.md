# 按下「採用」之後，系統再也不提這件事

Status: 2026-09-06 可用性演練量到（`docs/drills/`）。**三個角色全部撞到。** 底層是對的，
畫面是啞的——這條的成本很低，換到的信任很高。

成因：採用一條判讀建議會寫出一列 `rule`（`severity='soft'`，來源寫在 `content` 的文字裡），
下一次出方案時 `context_compiler` 真的會把它放進 prompt。三個角色的下一期方案都確實被影響了
（見 `issue-adopted-advice-can-invert.md` 的對照表）。**機制是通的，回音是零的**：

1. **重整就忘。** `DiagnosisPanel.tsx` 的 `adoptedIndexes` 是 `useState`，純前端狀態；沒有任何
   地方回讀「這條採用過沒有」。按完變「已採用」，F5 之後五條全部變回「採用」。
   後端其實有能力回答這件事——`_run_diagnosis_adopt()` 是先用 `rule_type`＋`content` 去查、
   查到就回既有那列（所以重複按不會寫出兩列），**同一組查詢鍵就能拿來標「這條已經採用過」**。
2. **下一期不說。** 方案、活動樹、素材三層都沒有一句「因為你採用了 X，這次才這樣排」。
3. **判讀不記得。** 第二次判讀完全不提上次採用的那條後來表現如何，五條標題全部重新來過。

使用者看到的（三個人各自的話）：
- 小杰：「**這個是畫面說謊**……還以為白按了。」
- Vivian（整趟最不能忍的一件事）：「按下採用變灰，重新整理後五個建議通通變回『採用』，
  一個『已採用』都沒留下。我以為系統記住了我的判斷，結果它連我剛做過的動作都留不住。」
- 阿明（解釋他為什麼只願意付 3,000～5,000 而不是更多）：「像在跟一個**每次都失憶**的顧問講話。」

`file:line`：`frontend/src/components/cockpit/DiagnosisPanel.tsx:39`（`adoptedIndexes` 是
`useState`）、`app/schedule/routes.py:521-546`（後端的冪等查詢，可重用成「已採用」的判定）。

做法（未裁決）：
- **最小一刀**：判讀回應多帶一個「這條已經採用過」的旗標，用後端既有那組查詢鍵算。route B，
  一顆欄位，半天以內。這一刀單獨就把三個人最刺的那個感受拿掉。
- 第二刀（要裁決）：下一期方案顯示「本次吃到你採用的 N 條」，`llm_task.input_context_ids_json`
  已經存著是哪幾條，不用新表。
- 第三刀（要裁決）：判讀輸入帶上「上次採用了什麼」，讓它能回答「那條後來怎麼樣」。
  這一刀跟 `issue-coordinates-lost-when-next-period-planned.md` 綁在一起——判讀現在連上一期的
  錢都看不到，先修那條才有得比。
