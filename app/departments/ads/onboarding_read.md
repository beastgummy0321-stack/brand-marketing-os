# 部門任務：開帳讀歷史（票 S2）

任務代號：ONBOARDING-READ-TASK-V1（本行是這份任務檔的識別行，請照樣保留，不要在回覆裡重複貼出）。

這個品牌過去在 Meta 上投過什麼、什麼奏效過，系統目前一無所知——可能是新客戶自己開的帳，
也可能是剛接手的舊帳。這次要做的，是讀這一個廣告活動（campaign）過去 Meta 現在還讀得到的
歷史：它的結構、它的素材、它逐日的成效，判斷出「對這個品牌來說，什麼方向是有效的」。這份
任務說明後面依序接的是：一段既有的方法論小節（判斷樣本夠不夠時查那一節，不要自己訂數字）、
品牌上下文、這次讀取範圍的既定事實（實際讀到的時間窗、用的是哪個歸因窗、哪幾天完全沒有
資料）、最後才是這個活動自己的結構與素材、外殼算好的期間總計、涵蓋範圍、逐日成效 CSV。

**外殼把形狀改乾淨，但絕不改寫摘要文案、絕不刪掉任何一個實體**（票 S2b）：金額到分、比率
到 2～3 位有效數字（Meta Ads Manager 自己顯示的精度，不是藏數字）；整個窗口加總是 0 的
`actions`／`action_values` 種類不送，送了什麼、省了什麼都在期間總計那節點名；興趣清單只列
前 10 個附「還有 N 個未列出」；名字只在對照表講一次，資料列只留短 id。
**成效表的一列是一個時間桶（月 ×（平日｜週末）），不是一天**：`spend_date` 空白＝那個桶的
加總，有值＝原封送出的那一天（每個桶附花費最高與轉換最高的那天）。桶的加總等於它取代的
那幾天加起來，一個數字沒變；`days_covered`／`days_with_data`／`days_with_roas`＝這個桶涵蓋
幾天、幾天有資料、ROAS 那格的分母幾天。**空白格是「沒回報」不是 0。** 整個窗口沒資料的桶
不進表，改在「涵蓋範圍」那節逐個點名——每個實體都會出現，一天資料都沒有的寫「有資料
0 天」，不會消失。
**廣告文案永遠逐字照登**——讀不出可信文案時你看到「保險絲觸發（理由）」加原始 JSON，
**括號裡那個理由要照著讀**：多半不是 Meta 沒給文案，而是同一則素材有兩套衝突的編碼、或版位
規則對不齊，外殼拒絕替你挑哪一半算數。沒做版位客製化的 Advantage+ 動態素材（最常見的形狀）
只給一組 body 清單跟一組 title 清單，配對是投遞時才決定的——你看到「bodies（N）」
「titles（M）」「media_ids（N）」三份各自逐字的清單，不是配好對的一則廣告。

## 這份資料本來就是破的——先知道它破在哪

- **廣告層級的 ROAS，大約三分之二的有花費日子都是空的**（測於 2026-08-30，這個使用者的
  真實帳號：91 天裡有花費的廣告日一共 560 個，其中只有 191 個有 `purchase_roas` 這個值）。
  ROAS 缺席不是例外，是常態。缺 ROAS 的地方，改看 `actions`（點擊、到達頁面、加入購物車、
  開始結帳……）判讀方向，而且要在結論裡老實講「這裡是看 actions 判讀的，不是看 ROAS」。
- **沒有那一列，不等於那天是零。** 逐日成效表裡有些（實體、日期）組合完全沒有出現——沒有
  投遞的日子，跟「投了但 Meta 沒回資料」，看起來一模一樣，我們自己也分不出來。把空白當成
  零、或把沒資料的日子當成投遞失敗的日子，都是這份任務不能犯的錯。

## 判讀時要守的幾條線

- **平台自己分配的預算，不是公平的實驗。** 如果一組廣告的曝光、預算是 Meta 的最適化系統
  自動決定的，而不是你們刻意做的對照，那它的表現差異可以當成一個值得注意的方向，但不能說
  「已經嚴格驗證」——這是方向，不是定論。
- **一兩筆訂單撐出來的天文數字 ROAS，是待測的假說，不是贏家。** 花費只有幾塊錢、訂單只有
  一到三筆卻衝出幾十倍 ROAS 的廣告，很容易被誤判成頭號功臣，實際上樣本小到一次退貨就會
  翻盤。看到這種數字，先把它歸類成「值得加碼小額測試的方向」，不要直接宣布它贏了。
- **再行銷（retargeting）跟開發新客（prospecting）本來就不是同一場比賽。** 再行銷素材的
  成效通常比新客素材漂亮，是因為它打的對象本來就比較熱，不是因為那則素材本身比較會打動
  陌生人。兩者放在一起比較時，要講清楚這個比較真正證明的是「後段承接有沒有價值」，還是
  「哪一則素材在公平競賽裡更會打動新客」，不要把前者講成後者。
- **兩個用不同歸因窗量出來的數字，不能直接放在一起比。** 既定事實小節會列出這次讀到的
  歸因窗有幾種；如果不只一種，任何跨組比較之前，先確認比較的兩邊是同一個歸因窗量出來的，
  量法不同就先講清楚，不要硬比。

## 樣本夠不夠用，查表，不要自己訂數字

要判斷「這個發現的樣本夠不夠支撐這個結論」，查方法論小節裡附的 A/B 測試方法論第 3 節
樣本數速查表——**不用自訂常數**，這份任務檔跟程式碼都不會給你任何一個「樣本數大於多少
才算顯著」的門檻。樣本明顯不夠時，誠實把結論標成方向性判讀，不要包裝成嚴謹結論。

## 交付內容

針對這個活動看得出來的每一個發現，給一條結論，包含：

- **text**：這個發現本身，讀者是看得懂中文但不懂投放術語的品牌經營者。
- **scope**：這個發現只對這個活動裡的某個產品成立，就填那個產品的 `product_id`；對整個
  品牌都成立就填 `"brand"`。看不準屬於哪個產品時，寧可填 `"brand"` 並在 sample_note 裡
  講清楚你的猶豫，不要用猜的。
- **confidence**：你自己的判斷用詞（例如「高」「中等」「方向性」），外殼不會拿這個字去比對
  任何門檻，也不會幫你算。
- **evidence**：支持這個結論的具體數字或比較，讓人不用重算就能檢查你講的話。
- **sample_note**：這個結論建立在多大、多完整的樣本上——用了幾天、幾筆訂單、有沒有缺
  ROAS 改看 actions，都寫在這裡。

寫完全部結論之後，**在回覆的最後**附上一個 fenced json 區塊，這個區塊必須是整段回覆真正
的最後一段內容，後面不能再接任何文字：

```json
{
  "conclusions": [
    {
      "text": "外送折扣碼的廣告在週末的每次點擊成本比平日低四成",
      "scope": "brand",
      "confidence": "moderate",
      "evidence": "8 個週末 vs 21 個平日，同一個廣告組合",
      "sample_note": "只有 12 天有購買追蹤，其餘用點擊數判讀"
    }
  ]
}
```

`conclusions` 的長度不限，看這個活動實際看出幾個站得住的發現就給幾條；`scope`／
`confidence`／`evidence`／`sample_note` 都是你自己的判斷，會原文照登在畫面上，不會被外殼
改寫或翻譯。

**數字請直接引用，不要自己加總。** 期間總計那一小節是外殼算好的——每個實體的花費、曝光、
點擊、CTR／CPC／CPM／ROAS／CPA，以及每一種 `actions` 的加總，都已經算完擺在那裡了。逐日
CSV 給你是為了讓你看得到分布與缺口，不是要你把它們加起來：2026-08-30 手跑這份任務時，
唯一一個出錯的數字就是把八天的內容瀏覽數心算成 344（實際是 342）。要引用總計就抄總計那一
節，要引用某一天就抄那一天，中間不要有心算。

你只要誠實給出你判斷下最合理的解讀（看不準就直說看不準，誠實優先於好看）。
